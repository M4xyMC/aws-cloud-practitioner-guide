## Section: Leveraging the AWS Global Infrastructure

### Lecture: Why Global Applications?

- A **global application** is deployed across **multiple geographies** — on AWS, that means deploying across different **Regions** or **Edge Locations**.

**Three reasons to go global**
1. **Decreased latency for users worldwide**: latency is the time for a network packet to reach a server. A user in India accessing a server only in the US experiences more lag than if the application were also deployed closer to them (e.g., in Asia).
2. **Disaster recovery**: relying on a single data center/region is risky — if an entire region goes down (earthquake, storm, power outage, politics, etc. — rare, but possible), having a DR strategy lets you fail over to another region and keep the application running, increasing availability.
3. **Protection against attacks**: if an application is distributed globally across multiple regions, it's much harder for an attacker to take down all locations at once.

**AWS Global Infrastructure recap (via AWS's interactive infrastructure map)**
- **Regions** (shown as orange boxes on the map) — e.g., in Europe: Spain, London, Ireland, Paris, Frankfurt, Milan, Stockholm.
- **Availability Zones** — e.g., Northern Virginia has **6 AZs**; Paris has **3 AZs**. AZs within a region are physically distant enough to avoid a shared disaster, but linked by very fast networking.
- **Points of Presence / Edge Locations** (pink dots) — used for content delivery networks (e.g., **CloudFront**); you cannot deploy applications directly there.
- **The AWS global network**: the actual private links between all regions, AZs, and points of presence — including undersea cables connecting continents (e.g., Europe–US, Europe–Africa) — giving AWS a fast, reliable, private backbone.

**Services covered in this section (preview)**
- **Route 53** — global DNS: routes users to the closest deployment with the least latency; useful for disaster recovery.
- **CloudFront** — global Content Delivery Network (CDN): replicates parts of your application into Edge Locations to decrease latency and cache common requests.
- **S3 Transfer Acceleration** — accelerates global uploads/downloads into Amazon S3.
- **AWS Global Accelerator** — improves global application availability and performance using the AWS global network.

### Lecture: Route 53 Overview

- **Amazon Route 53** is a managed **DNS (Domain Name System)** — like a phone book, it's a collection of rules/records helping clients find the right servers through URLs.

**Common DNS record types**
| Record type | Maps... |
|---|---|
| **A record** | Hostname → IPv4 address |
| **AAAA record** | Hostname → IPv6 address |
| **CNAME** | Hostname → another hostname |
| **Alias record** | Hostname → an **AWS resource** (e.g., an ELB, CloudFront distribution, S3 bucket, RDS database) — a special AWS-specific record type |

- (You don't need to memorize every record type for the exam, just have an overview.)

**How Route 53 works (basic A record flow)**
- A web browser does a DNS request for `myapp.mydomain.com` → Route 53 replies with an IP address → the browser uses that IP to reach the application server and gets the HTTP response.

**Routing Policies (know these at a high level for the exam)**
| Policy | Health checks? | Purpose |
|---|---|---|
| **Simple Routing Policy** | No | Basic: DNS query returns a single IP (e.g., an IPv4 address) directly. |
| **Weighted Routing Policy** | Yes | Distributes traffic across multiple instances based on assigned weights (e.g., 70% / 20% / 10%) — a form of load balancing. |
| **Latency Routing Policy** | Yes | Routes users to the deployment/region with the **lowest latency** relative to their location (e.g., a user near California goes to the California server; a user near Australia goes to the Australia server). |
| **Failover Routing Policy** | Yes | Routes to a **primary** instance normally; if a health check detects the primary has failed, traffic is redirected to a **failover** instance — supports disaster recovery. |

> **Exam Tip**: Simple Routing has no health checks; the other three all use health checks and serve distinct purposes — Weighted (traffic distribution), Latency (minimize latency), Failover (disaster recovery).

### Lecture: Route 53 Hands On

- **Registering a domain**: Route 53 → Registered domains → search for an available domain name (e.g., "stephane-ccp.com") → purchase it (e.g., $12/year) → registration takes some time to process.
- Once registered, a **Hosted Zone** is automatically created for the domain — this is where DNS records for that domain are managed.
- **Demo setup**: two EC2 instances launched in **different regions** — one in Ireland (`eu-west-1`), returning "Hello world from Ireland" via User Data, and one in Oregon (`us-west-2`), returning "Hello world from the US." Both use a security group allowing HTTP traffic only (no SSH needed).
- Noticeably slower launch/interaction for the more distant region (Oregon, relative to the presenter's location) — a real-world illustration of **latency**.
- **Creating Route 53 records**: create an **A record** for `www.stephane-ccp.com` with:
  - Value = the Ireland instance's IP, Routing Policy = **Latency-based**, Region = `eu-west-1`, labeled "My instance from Ireland."
  - A second A record for the same subdomain, Value = the Oregon instance's IP, Routing Policy = **Latency-based**, Region = `us-west-2`, labeled "My US Instance."
- **Result**: visiting `www.stephane-ccp.com` from Europe returns "Hello World from Ireland" (the lower-latency option); connecting via a VPN to appear as if browsing from the US instead returns "Hello world from the US" — demonstrating **Latency Routing** directing each user to their closest/lowest-latency instance.
- **Cleanup**: terminate both EC2 instances (to avoid compute costs); optionally delete the hosted zone (costs ~$0.50/month); the purchased domain itself costs ~$12/year — disable auto-renewal if you don't want to renew it.

### Lecture: CloudFront Overview

- **CloudFront** is AWS's **Content Delivery Network (CDN)**.
- > Whenever you see "CDN" on the exam, think **CloudFront**.
- Improves read performance by **caching content** at Edge Locations around the world, giving users lower latency and a better experience.
- Made up of **hundreds of points of presence** globally (edge locations and caches).
- Because content is distributed globally, CloudFront also provides **DDoS protection** — helped further by **Shield** and **Web Application Firewall (WAF)** (covered later in the security section).

**How it works (example)**
- An S3 bucket/website hosted in Australia, accessed by a user in America: the request goes to a nearby American edge location; CloudFront fetches the content from Australia the first time, then **caches** it at that edge location. A second US-based user requesting the same content is served directly from the edge — no round trip to Australia needed. Similarly, a user in China is served via a Chinese point of presence.

**CloudFront Origins (backends CloudFront connects to)**
| Origin type | Description |
|---|---|
| **Amazon S3 bucket** | For distributing/caching files at the edge, or uploading files into S3 through CloudFront. Access secured via **Origin Access Control (OAC)**. |
| **VPC origin** | For connecting to resources within your own VPC — private Application Load Balancer, private Network Load Balancer, or private EC2 instances. |
| **Custom origin (over HTTP)** | Any public HTTP backend — e.g., an S3 bucket enabled as a static website, or a public load balancer. |

**How CloudFront serves requests**
- Edge Locations connect to your origin (S3 or HTTP server). When a client requests content: if the edge already has it cached, it's served immediately; if not, the edge fetches it from the origin, serves it, and **caches it locally** for future requests from that same edge location.
- Access between CloudFront and an S3 origin is secured via **Origin Access Control (OAC)** plus the S3 bucket policy.

**CloudFront vs. S3 Cross-Region Replication**
| | CloudFront | S3 Cross-Region Replication |
|---|---|---|
| Scope | Global Edge network (~216 points of presence) | Must be set up per specific target region(s) |
| Freshness | Content cached at the edge (e.g., ~1 day) | Near real-time updates, no caching |
| Access mode | Read (cached) | Read-only replica |
| Best for | Static content needed everywhere globally | Dynamic content needing low-latency access in a few specific regions |

### Lecture: CloudFront Hands On

- Create an S3 bucket (e.g., "demo-CloudFront-Stephan-v4") and upload files (e.g., `beach.jpg`, `coffee.jpg`, `index.html`) — kept **private** (not made public).
- Confirmed: the plain object URL gives **Access Denied** (private objects); the "Open" button in the console works via a **pre-signed URL**, but the embedded image (referencing the non-public image object) still doesn't load in that context.

**Creating a CloudFront distribution**
- Choose a pricing plan — the **Free plan** is sufficient for this use case (includes enough requests/month, always-on DDoS protection, geographic traffic blocking, global CDN/DNS, free TLS certificates). Paid plans add features like edge key-value store, advanced DDoS protection, uptime SLA, or WordPress protection.
- Name the distribution (e.g., "demo new CloudFront"); use a single site/app (no custom domain needed for this demo).
- **Origin type**: choose **Amazon S3** (other options include Elastic Load Balancer, API Gateway, Elemental MediaPackage, or "Other"; VPC origin requires the Business plan) → browse to and select the demo bucket.
- **Allow private S3 bucket access to CloudFront: Yes** — use recommended origin and cache settings for serving S3 content.
- Skip Web Application Firewall (not needed for this demo — also requires a paid plan for layer 7 protection) → review → create the distribution.

**Result**
- After creation, the S3 bucket's **bucket policy** is automatically updated to allow access from the new CloudFront distribution — enabling CloudFront to privately access the (still-private) S3 bucket.
- Visiting the distribution's **domain name** directly gives Access Denied (no default root object configured for the bare path), but specific paths work: `/coffee.jpg` and `/beach.jpeg` load correctly, and `/index.html` shows the full page with both images.
- Even though the S3 objects remain fully **private**, CloudFront can serve them thanks to the bucket policy granting it access.
- **Caching benefit demonstrated**: revisiting `beach.jpeg` loads **almost instantaneously** the second time, since it's now cached at the edge.

### Lecture: S3 Transfer Acceleration

- S3 buckets are tied to a **single region** — sometimes you need to transfer files from **all around the world** into one specific bucket, which can be slow over long distances.
- **S3 Transfer Acceleration** speeds this up: a file uploaded from, say, the United States, first goes to a nearby **Edge Location**, then travels over AWS's fast, reliable **internal network** to reach the target bucket (e.g., in Australia), instead of traveling the whole way over the public internet.
- Used specifically when uploading/downloading to/from a bucket that is **geographically far away** from the user.
- AWS provides a **speed comparison tool** to test direct upload vs. accelerated transfer for different regions. In the demo (testing from Europe): transfers to Northern Virginia were about **13% faster** with acceleration, and improvements were seen across most tested regions (San Francisco, Oregon, Dublin, Frankfurt, Tokyo, Seoul, Mumbai, Ohio, Canada, etc.).
- **Use case**: a global application that needs to upload files into one specific, centralized S3 bucket from users located far away.

### Lecture: AWS Global Accelerator

- **AWS Global Accelerator** improves **global application availability and performance** by routing traffic over the **AWS global network** — optimizing the route to your application by up to roughly **60%**.

**How it works**
- Example: an application is deployed in India, with users worldwide. Using Global Accelerator, a user's request travels over the **public internet** only as far as the **nearest AWS Edge Location**, and from there travels over AWS's fast **private network** all the way to the application in India — minimizing the distance traveled over the (slower, less predictable) public internet.
- You access your application through **two static IP addresses**, called **Anycast IPs** — these automatically route to the correct/nearest edge location, which then forwards traffic to your application.

**Global Accelerator vs. CloudFront**
| | CloudFront | Global Accelerator |
|---|---|---|
| Type | Content Delivery Network (CDN) | Network performance/routing optimizer |
| Caching | Yes — caches content (images, videos, websites) at the edge | **No caching** — all requests pass through to your application in its region |
| Protocol scope | HTTP-focused content delivery | Works over a wide range of **TCP or UDP** traffic |
| Shared features | Both use AWS's global network/edge locations, and both integrate with **Shield** for DDoS protection | Same |
| Best for | Cacheable static/dynamic content delivery | HTTP use cases needing a **static IP**, or needing fast, deterministic **regional failover** and improved performance |

- **Speed comparison tool demo** (testing 5 MB file transfers from Europe): Northern Virginia showed a 23% improvement (1,293 ms direct vs. 1,002 ms via Global Accelerator); Oregon showed ~31% improvement; nearby regions like Ireland/Frankfurt showed little to no difference (already close); Singapore showed ~34% improvement; Sydney showed the largest improvement at ~53% — illustrating that Global Accelerator's benefit scales with the physical distance between the user and the target region.

### Lecture: AWS Outposts

- **Hybrid cloud**: businesses that keep on-premises infrastructure alongside cloud infrastructure. This traditionally means managing **two different skill sets, tools, and APIs** — one for AWS, one for on-premises systems.
- **AWS Outposts** solves this: physical **server racks** that AWS installs and manages **within your own data center**, offering the **same AWS infrastructure, services, APIs, and tools** as the cloud — but on-premises.
- Key difference from a normal cloud EC2 instance: with Outposts, **you are responsible for the physical security of the rack itself**, since it lives in your own data center.

**Benefits**
- Low-latency access to on-premises systems.
- **Local data processing** — data may never leave your on-premises environment (useful for data residency requirements).
- Provides an easy migration path: on-premises → Outposts → (eventually) fully to the cloud.
- **Fully managed** by AWS.

**Supported services (on Outposts)**
- Amazon EC2, Amazon EBS, Amazon S3, Amazon EKS, Amazon ECS, Amazon RDS, Amazon EMR.

### Lecture: AWS WaveLength

- **AWS WaveLength Zones** are AWS infrastructure deployments embedded **within telecommunications providers' data centers**, at the edge of **5G networks**.
- > Whenever you see "**5G**" in an exam question, think **WaveLength**.
- Lets you deploy AWS services (e.g., **EC2 instances, EBS volumes, VPC**) directly to the edge of a 5G network.
- Example: a telecom carrier's 5G network hosts a WaveLength Zone; via a **carrier gateway**, you deploy an EC2 instance into that zone. A 5G mobile device accessing that application gets **ultra-low latency**, since the application is deployed right at the network edge.
- Traffic from the 5G device to the WaveLength Zone typically **never leaves the Communication Service Provider (CSP) network** — it doesn't need to reach AWS's main infrastructure at all. However, a **secure connection back to the parent AWS Region** is available (e.g., if the WaveLength EC2 instance needs to access RDS or DynamoDB in the main region).
- **No additional charges or special service agreements** required to use WaveLength.
- **Use cases**: smart cities, ML-assisted diagnostics, connected vehicles, interactive live video streams, AR/VR, real-time gaming — anything requiring ultra-low latency at the edge, enabled by 5G.

### Lecture: AWS Local Zones

- **AWS Local Zones** let you place compute, storage, database, and other selected services **closer to end users**, for latency-sensitive applications, by extending an AWS Region to one or more additional "quasi-availability-zone" locations.
- Compatible with **EC2, RDS, ECS, EBS, ElastiCache, Direct Connect**, and more.
- Example: the `us-east-1` (Northern Virginia) region has 6 AZs by default, but can be **extended** with Local Zones in cities like Boston, Chicago, Dallas, Houston, Miami, etc. You can extend a **VPC** across these AZs and Local Zones, then launch an EC2 instance directly into the Local Zone.

**Hands-on demo**
- In a region **without** Local Zones (e.g., Europe/Ireland), the EC2 console's Zones settings show only the standard AZs — no Local Zone option.
- In `us-east-1` (Northern Virginia), the Zones settings show **Local Zones**, **WaveLength Zones**, and the standard **Availability Zones** (6 AZs).
- **Enabling a Local Zone**: e.g., enable the Boston Local Zone (`us-east-1-bos-1`) via the Zone Groups settings.
- Once enabled, when launching an EC2 instance, you can create a **new subnet** associated with that Local Zone (e.g., naming it "Boston subnet," selecting the Boston AZ, and specifying a CIDR block) — this lets you deploy an EC2 instance into the Local Zone, extending your VPC there.
- (Networking/CIDR details noted as advanced and not required for the exam — the key concept is that Local Zones extend your VPC/region to a location physically closer to specific users.)

### Lecture: Global Applications Architecture

An overview of architecture patterns for building a global application, in increasing order of complexity:

| Architecture | Description | High Availability? | Improved Global Latency? | Difficulty |
|---|---|---|---|---|
| **Single Region, Single AZ** | One EC2 instance in one AZ in one region | No | No | Very low |
| **Single Region, Multi-AZ** | Multiple AZs within one region | Yes | No (AZs are close together; distant users still see high latency) | Slightly increased |
| **Multi-Region, Active-Passive** | Two (or more) regions, each with one or more AZs; one region is **active** (handles reads and writes), the other(s) are **passive** (data is replicated to them; may allow reads, but **not writes**) | Yes | Improves **read** latency globally (since reads can happen from a nearby passive region); **write** latency remains high globally, since all writes must go to the single active region | Increased (multiple regions to manage) |
| **Multi-Region, Active-Active** | Each region's instance/database can handle **both reads and writes**, with replication happening between them | Yes | Improves **both** read and write latency globally | Highest difficulty — application must coordinate correctly across every region |

- Example of an active-active setup: **DynamoDB Global Tables** (covered in the Databases section), where writes can happen in any configured region and are replicated to the others.

> **Exam Tip**: remember the terms **single region / multi-region**, and **active-passive / active-active** — this should be enough to answer exam questions on this topic.

### Lecture: Leveraging the AWS Global Infrastructure Summary

- **Route 53**: global DNS — routes users to the closest deployment with the least latency; useful for disaster recovery strategies; supports creating records mapping hostnames to IPs (and more).
- **CloudFront**: global CDN — replicates application data into Edge Locations to decrease latency, and caches common requests for improved user experience.
- **S3 Transfer Acceleration**: accelerates global uploads/downloads into Amazon S3 by leveraging Edge Locations.
- **AWS Global Accelerator**: leverages Edge Locations and the AWS global network to improve global application availability and performance.
- **AWS Outposts**: extends AWS infrastructure into your own on-premises data center via physical Outposts racks.
- **AWS WaveLength**: brings AWS services to the edge of 5G networks for ultra-low-latency applications.
- **AWS Local Zones**: brings AWS compute, database, and storage resources physically closer to users in specific cities (e.g., Boston, Dallas, Miami, Chicago) — great for latency-sensitive applications needing fast local access within a specific US region (for now).

## Section: Leveraging the AWS Global Infrastructure — Key Takeaways

**Most important concepts**
- Going global with an application serves three purposes: **lower latency** for distant users, **disaster recovery**, and **resilience against attacks**.
- **Route 53** (DNS) and **CloudFront** (CDN) are the two foundational global services — Route 53 routes *users* to the best endpoint; CloudFront caches and serves *content* from the edge.
- **S3 Transfer Acceleration** and **Global Accelerator** both speed up data movement by routing traffic over AWS's private global network instead of the public internet — but Transfer Acceleration is specific to S3 uploads/downloads, while Global Accelerator works broadly over TCP/UDP for entire applications.
- **Outposts, WaveLength, and Local Zones** all extend AWS infrastructure closer to a specific physical location — on-premises, on a telecom's 5G network, or in a specific city — for different reasons (hybrid cloud, 5G ultra-low latency, and general latency-sensitive local presence, respectively).
- Global application architectures range from single-region/single-AZ (simplest, least resilient) up to multi-region active-active (most complex, best global performance and availability).

**How the concepts relate**
- **Route 53's Latency Routing Policy** and the **multi-region active-active/active-passive architectures** are two sides of the same coin: Route 53 is the mechanism that actually directs a given user to the right regional deployment, while the active-active/active-passive pattern describes how those regional deployments handle reads and writes among themselves.
- **CloudFront** and **S3 Cross-Region Replication** both help distribute content, but at different layers: CloudFront **caches** content temporarily at the edge for global read performance; Cross-Region Replication actually **copies** the bucket's contents into another region for near-real-time, region-specific access.
- **CloudFront** and **Global Accelerator** both leverage AWS's edge locations and global network and both integrate with **Shield** for DDoS protection, but CloudFront caches content while Global Accelerator purely optimizes the network path (no caching) — a distinction the exam explicitly tests.
- **Outposts, WaveLength, and Local Zones** all "extend" AWS outward from the standard region/AZ model, but to different destinations: Outposts → your own data center; WaveLength → a telecom's 5G network edge; Local Zones → a nearby AWS-operated location extending a region (e.g., Boston extending `us-east-1`).

**Key terminology to remember**
- Region, Availability Zone, Edge Location / Point of Presence
- Route 53: A record, AAAA record, CNAME, Alias record; Simple, Weighted, Latency, and Failover routing policies
- CloudFront: CDN, Origin Access Control (OAC), origin (S3, VPC, custom HTTP), edge cache
- S3 Transfer Acceleration
- AWS Global Accelerator: Anycast IP
- AWS Outposts: hybrid cloud, Outposts racks
- AWS WaveLength: WaveLength Zone, carrier gateway, Communication Service Provider (CSP)
- AWS Local Zones: extending a region, Zone Groups
- Single-region vs. multi-region; Active-Passive vs. Active-Active

**Key distinctions/comparisons**
- **CloudFront vs. S3 Cross-Region Replication**: edge caching (global, temporary, read-focused) vs. full regional data copy (specific regions, near-real-time, read-only replica).
- **CloudFront vs. Global Accelerator**: content caching CDN vs. network-path optimization with no caching, supporting broader TCP/UDP use cases and static IPs.
- **Outposts vs. WaveLength vs. Local Zones**: extend AWS into your own data center vs. onto a telecom's 5G network edge vs. into an AWS-managed nearby city location.
- **Active-Passive vs. Active-Active** multi-region architecture: only one region accepts writes (others are read-only/passive) vs. every region accepts both reads and writes (e.g., DynamoDB Global Tables).
- **Simple vs. Weighted vs. Latency vs. Failover** Route 53 routing policies: no health checks vs. traffic-splitting by weight vs. lowest-latency routing vs. primary/failover health-based routing.

**You should be able to explain:**
- The three reasons for building a global application (latency, disaster recovery, attack resilience).
- What Route 53 is, its main record types, and the four routing policies (and when to use each).
- What CloudFront is, how it caches content from an origin, and the different origin types it supports.
- The difference between CloudFront and S3 Cross-Region Replication.
- What S3 Transfer Acceleration does and when it's useful.
- What AWS Global Accelerator does, how it differs from CloudFront, and why its benefit increases with distance.
- What AWS Outposts, AWS WaveLength, and AWS Local Zones each do, and how they differ in terms of where they extend AWS infrastructure to.
- The four global application architecture patterns (single-region/single-AZ, single-region/multi-AZ, multi-region active-passive, multi-region active-active) and their trade-offs in availability, latency, and complexity.
