## Section: Other Services

### Lecture: Other Services - Section Intro

- This section covers **other AWS services** that could not be grouped with the previous ones and that students report as **occasionally but rarely appearing** on the exam.
- Lectures are **very short and brief**, mostly **without hands-on**, and the instructor deliberately includes **no summary lecture** at the end so services can be added over time.
- Approach: **one service, one definition** — don't stress about deeply understanding each service, **just remember the definition**.

### Lecture: WorkSpaces Overview

- **Amazon WorkSpaces** is a **managed Desktop as a Service (DaaS)** solution to easily provision **Windows or Linux desktops**.
- Purpose: **eliminate on-premises VDI (Virtual Desktop Infrastructure)** — if someone needs a Windows laptop "in the cloud", they use WorkSpaces.
- Characteristics:
  - **Fast** and **quickly scales to thousands of users**.
  - **Secure** — integrated with **KMS**.
  - **Pay-as-you-go** — you only pay for the actual usage of the desktops.
- Typical flow: a user at home provisions a **secure Windows desktop in AWS** and accesses their **cloud or corporate data center** from that virtual desktop, which can live **inside your VPC**.
- > **Exam Tip**: anything about **virtual desktops** or **managed Desktop as a Service** → **WorkSpaces**.
- > **Exam Tip (latency)**: to **minimize latency**, **deploy WorkSpaces as close as possible to your users**. Example: with corporate offices in **California and Paris**, deploy WorkSpaces in a **US region** for the California users and in a **European region** for the European users — as many WorkSpaces regions as you have user locations. This principle applies to **any application**, not just WorkSpaces: **deploy close to users to minimize latency**.

### Lecture: AppStream 2.0 Overview

- **Amazon AppStream 2.0** is a **desktop application streaming service** — **stream an application to any computer** without acquiring and provisioning infrastructure.
- The application is **delivered and accessible from within a web browser**.
- *Examples*: run **Blender** to create 3D models, or **Eclipse, Firefox, OpenOffice**, directly in a web browser.

**WorkSpaces vs. AppStream 2.0**

| | Amazon WorkSpaces | Amazon AppStream 2.0 |
|---|---|---|
| What you get | A **full VDI** — a complete **Windows or Linux desktop** | A **specific desktop application** streamed to your browser |
| Applications | Launch **as many applications as you want** inside the desktop | **One application** per stream, **application-focused** |
| How you connect | Via a **remote desktop application** | **Web browser** — no need to connect to a virtual desktop |
| Availability model | **On-demand or always on** | Streamed on demand |
| Device compatibility | Requires the desktop client | **Any device with a web browser** → more compatibility |
| Sizing | Desktop-level | **Configure an instance type per application** (e.g., more CPU/RAM/GPU for Photoshop) |

### Lecture: IoT Core Overview

- **IoT = Internet of Things** — a **network of internet-connected devices able to collect and transfer data**.
- **AWS IoT Core** lets you **easily connect IoT devices to the AWS Cloud** — that is the core thing to remember.
- **IoT devices** examples: a connected **car**, connected **light**, connected **fridge** — anything connected.
- Capabilities:
  - Devices can exchange data **securely and scalably** — **billions of devices, trillions of messages**.
  - IoT Core can act as a **pub/sub** so devices can exchange messages and communicate.
  - Your applications can **communicate with devices even when they are not connected**.
  - **Integrations** with **Lambda, Amazon S3, SageMaker** and others to add value.
- The IoT Core suite lets you **gather, process, analyze and act on data** created by IoT devices, to build **IoT applications**.

### Lecture: AppSync

- **AWS AppSync** builds a **backend for your mobile and web applications** — to **store and synchronize data in real time**.
- It leverages **GraphQL**, a technology from **Facebook**.
- > **Exam Tip**: if you see **GraphQL**, it heavily hints at **AWS AppSync**.
- Features:
  - **Client code for your APIs can be generated automatically** (thanks to GraphQL).
  - **Integrations with DynamoDB and Lambda** to build the GraphQL backend.
  - **Real-time subscriptions** — get data updates in real time in web and mobile applications.
  - **Offline data synchronization** if needed.
  - **Built-in security.**
- **AWS Amplify** can leverage AppSync in the background if you want to build a GraphQL backend with Amplify.

### Lecture: Amplify

- **AWS Amplify** is a **set of tools and services to develop and deploy scalable full-stack web and mobile applications**.
- It manages everything you need for web and mobile apps: **authentication, storage, APIs (REST or GraphQL), CI/CD, pub/sub, analytics, machine learning, monitoring**, and source code from **AWS, GitHub or other places**.
- Think of it as the **"Elastic Beanstalk for web and mobile applications"**.
- **Amplify Studio** lets you set up your **data, authentication, storage, functions, GraphQL API**, etc.
- Behind the scenes Amplify configures an **Amplify backend** built on existing AWS services: **Amazon S3, Amazon Cognito, AWS AppSync** (GraphQL backend), **API Gateway** (REST backend), **SageMaker, Lex, Lambda, DynamoDB** and more.
- In short: a **wrapper around all these services** aimed at helping you build **mobile/web application backends**.

### Lecture: AWS Infrastructure Composer

- **AWS Infrastructure Composer** lets you **visually design and build serverless applications quickly** on AWS.
- A **drag-and-drop tool** to create **infrastructure as code** very quickly **without being an expert**, and to configure how resources interact with each other.
- **Output**: it **generates infrastructure as code compatible with CloudFormation**.
- **Reverse direction**: you can **import CloudFormation or SAM templates** into Infrastructure Composer to **visualize** them.

**Hands-on notes**
- The demo shows an **API Gateway with 5 routes**, each connected to one of **5 Lambda functions**, plus a **DynamoDB table** — you can **visually see** that e.g. a `POST item` route connects to the `CreateItem` Lambda function.
- Clicking **Details** on a resource shows its **resource properties** (package type, runtime, architecture, …), all editable; you can also set up **permissions** (e.g., allow the function to write to DynamoDB) and see the DynamoDB table's **logical ID, partition key**, etc.
- Building new resources: drag a **Kinesis Stream** and a **Lambda function** from **Resources** and **connect them** so the function reads from the stream — as simple as that.
- Two resource groups are available: **enhanced components** (serverless-specific) and **standard IaC resources** (e.g., an Amplify app).
- Under **Templates** you see the **CloudFormation output template** for the canvas, in **YAML or JSON**, to copy into CloudFormation or save.

### Lecture: Device Farm Overview

- **AWS Device Farm** is a **fully managed service to test your web and mobile applications against real desktop browsers, real mobile devices and tablets**.
- Tests can be run **concurrently on multiple devices**, speeding up execution.
- You can **configure the devices**: **GPS, language settings, Wi-Fi, Bluetooth**, etc.
- It is a **real farm of actual devices** in the AWS cloud.
- *Use case*: as an Android or iOS developer you can make sure your app works across **thousands of different devices** with different screen sizes, and **catch bugs very early**.
- You can **interact with the devices**, and Device Farm returns **reports, logs and screenshots** so bugs can be handled in advance.

### Lecture: AWS Backup Overview

- **AWS Backup** is a **fully managed service to centrally manage and automate backups across AWS services**.
- Features:
  - **On-demand and scheduled** backups.
  - **Point-in-time recovery (PITR)**.
  - Define **retention periods**, **lifecycle management**, **backup policies**.
  - **Cross-region** backups and **cross-account** backups (backed by **AWS Organizations**).
- **How it works**: create a **backup plan** (frequency + retention policy) → **assign the resources** to be backed up → those resources are **automatically backed up into Amazon S3**.
- **Supported services**: **Amazon EC2, EBS, DynamoDB, RDS, EFS, Aurora, FSx, Storage Gateway**.
- > **Exam Tip**: anytime you see **backups**, think **AWS Backup**.

### Lecture: Disaster Recovery Strategies

Four strategies, ordered from **cheapest** to **most expensive**:

| Strategy | What is running in the cloud | Recovery action needed | Cost |
|---|---|---|---|
| **Backup and Restore** | **Only data backups** — the application is **not running** | **Restore** the data and start the application wherever you want | **Cheapest** (you only pay to back up data over time) |
| **Pilot Light** | Only the **core/critical functions** of the app (e.g., just the database), at a **minimal setup**, ready to scale — **no application servers** | **Upgrade the database type** and **start the application servers** | Slightly more expensive than backup and restore |
| **Warm Standby** | The **full version of the app**, but at **minimum size** | **Increase the size** of the app | Higher |
| **Multi-Site / Hot Site** | The **full version of the app at full size**, ready to be used no matter what | Essentially none — it's ready right away | **Most expensive** |

- > **Exam Tip**: the exam usually just asks **which one is the cheapest** — the answer is **Backup and Restore**. Know which is cheapest, which is most expensive, and **why**.
- **Multi-region disaster recovery**: if your instance is in **us-east-1** and a disaster strikes that region, you can **fail over all traffic to another region** (e.g., **eu-west-2**) using **Route 53**.
- Deeper coverage belongs to a dedicated disaster recovery course; this is enough for CCP level.

### Lecture: AWS Elastic Disaster Recovery (DRS)

- **AWS Elastic Disaster Recovery (DRS)** was formerly named **CloudEndure Disaster Recovery** (acquired by AWS, then renamed as a proper AWS service).
- Purpose: **quickly and easily recover your physical, virtual and cloud-based servers into AWS** for disaster recovery.
- *Use cases*: protect your **most critical databases** (**Oracle, MySQL, SQL Server**), **enterprise apps** (e.g., **SAP**), or protect data against a **ransomware attack**.
- **How it works**:
  1. An **AWS replication agent** installed in your corporate data center performs **continuous block-level replication** of your servers' disks (OS, apps, databases).
  2. Data replicates into a **low-cost staging environment in AWS** using small **EC2 instances and EBS volumes**.
  3. When a disaster strikes, you **fail over within minutes** from staging to production by creating **bigger EC2 instances and better EBS volumes**.
  4. When your data center is back online, you perform a **failback** — the system returns to your data center and normal operation resumes.

### Lecture: AWS DataSync

- **AWS DataSync** **moves large amounts of data from on-premises to AWS**.
- **Destinations**: **Amazon S3** (any storage class), **Amazon EFS**, **Amazon FSx for Windows** File Server.
- **Replication tasks can be scheduled regularly** — e.g., every hour, day or week.
- **After the first full load**, all subsequent tasks are **incremental**.
- > **Exam Tip**: look for the word **incremental** — it hints that **DataSync** is the right answer.
- **How it works**: run the **DataSync agent** on-premises → the agent connects to the DataSync service → data is sent to S3 / EFS / FSx for Windows.

### Lecture: Cloud Migration Strategies - The 7Rs

The **7 Rs** of cloud migration (described in an AWS blog; the exam may ask which strategy to use):

| Strategy | Meaning | Details / examples |
|---|---|---|
| **1. Retire** | **Turn off what you don't need** | Reduces the **attack surface** (better security with fewer active services), **saves 10–20% of costs**, lets you focus attention on resources that must be maintained |
| **2. Retain** | **Do NOT migrate** (still a valid migration decision) | Keep the resource on-premises because of **security, data compliance, performance, unresolved dependencies**, **no business value** in migrating, or excessive complexity |
| **3. Relocate** | **Move the app to its cloud version** without changing it | Move EC2 instances to a **different VPC, account or region**; or move on-premises **VMware software-defined data centers (SDDC)** to **VMware Cloud on AWS** — nothing changes |
| **4. Rehost ("lift and shift")** | **Rehost the application on AWS as-is** | Migrate applications, databases and data; migrate **physical, virtual, or other-cloud servers** into AWS. **No cloud optimization** — the app stays as is but uses cloud resources; can **save up to 30%** on cost. The **AWS Application Migration Service** does exactly this |
| **5. Replatform ("lift and reshape")** | Keep the **core architecture**, but adopt **cloud optimizations** | E.g., migrate a database to **RDS** or an app to **Elastic Beanstalk** — **save time and money** by moving to **fully managed or serverless** services. Moving a DB to RDS (rather than to EC2) brings **backups, resiliency, high availability**, etc. |
| **6. Repurchase ("drop and shop")** | **Move to a different product** while moving to the cloud | Move to a **SaaS** platform — **expensive in the short term but very quick to deploy**. E.g., CRM → **Salesforce.com**, HR → **Workday**, CMS → **Drupal** |
| **7. Refactor / Re-architect** | **Re-imagine the architecture using cloud-native features** | Done to improve **scalability, performance, security and agility**; e.g., **break a monolith into microservices**, move to a **serverless architecture**, use **Amazon S3** for data. **Most effort, but usually the biggest payoff** |

### Lecture: Application Discovery Service & Application Migration Service

- **Two situations when moving to the cloud**: **start fresh** in the cloud (no migration needed), or **migrate existing on-premises servers and data centers** (you must **plan** the migration).

**AWS Application Discovery Service — plan the migration**
- **Scans your servers** and gathers **server utilization data** and **dependency mapping** — essential to understand **how to migrate and what to migrate first**.
- **Two discovery types**:

| Type | How | Information gathered |
|---|---|---|
| **Agentless Discovery** (using a **Connector**) | No agent installed | **Virtual machines**, **configuration**, **performance history** — CPU, memory, disk usage |
| **Application Discovery Agent** | Agent runs **inside** the VMs | **More frequent updates and more detail**: system configuration, performance, **running processes**, and **details of all network connections between systems** → good for **dependency mapping** |

- Results can be viewed in **AWS Migration Hub**.

**AWS Application Migration Service (MGN) — perform the migration**
- Formerly **CloudEndure Migration**; the **simplest way to move from on-premises to AWS**.
- Provides **rehosting (lift-and-shift)**: convert **physical, virtual or other-cloud servers** to run **natively on AWS**.
- **How it works**: install a **replication agent** in your data center → **continuous replication** of your disks into **low-cost EC2 instances and EBS volumes** → when ready, perform a **cut over** from staging to production with **appropriately sized EC2 instances and EBS volumes**.
- Benefits: supports a **wide range of platforms, operating systems and databases**; **minimal downtime**; **reduced costs** (no need for complex engineering — the service automates it).

### Lecture: AWS Migration Evaluator

- **AWS Migration Evaluator** helps you **build a data-driven business case for migrating to AWS**.
- You first need a **clear baseline of what your organization runs today**.
- **How it works**:
  - Install the **Agentless Collector** to conduct a **broad-based discovery** of your infrastructure — takes a **snapshot of your on-premises footprint and server dependencies**.
  - Alternatively use the **data import feature** — a **tool and template** into which you shape data you already have.
  - **Analyze your current state**, **define the target state in AWS**, and **develop a migration plan**.
- Output: **quick insights** and **customized cost insights** so the migration is **cost efficient** and good for the business — i.e., a solid **business case**. **Expert guidance from AWS** on your business case is also available.

### Lecture: AWS Migration Hub

- **AWS Migration Hub** is a **central location to collect server and application inventory data** for the **assessment, planning and tracking of migrations to AWS**.
- Everything is **centralized**, which **accelerates migration** and helps **automate lift-and-shift**.
- **AWS Migration Hub Orchestrator** (sub-feature): use **pre-built templates** to save time and effort migrating **enterprise apps** such as **SAP** or **Microsoft SQL Server**.
- **Integrations** with services already seen: **Application Migration Service (MGN)** and **Database Migration Service (DMS)**.
- > **Exam Tip**: a **central location to discover, assess, plan and track your migration and modernization** → **Migration Hub**.
- Additional capabilities: **right-size your workload** and get **strategy recommendations**, **orchestrate migrations across multiple tools**, and **incrementally refactor applications** to move them to AWS.

### Lecture: AWS Fault Injection Simulator (FIS)

- **AWS Fault Injection Simulator (FIS)** runs **fault injection experiments on AWS workloads**.
- Based on **Chaos Engineering** — deliberately **stressing an application by creating disruptive events** (CPU skyrocketing, out-of-memory, database failure, …) to see **how the entire application stack reacts**. You are literally **creating chaos** in your infrastructure.
- **Why**: make sure the application is **truly solid**, and **uncover hidden bugs and performance bottlenecks**.
- **Supported services** (you don't need to know them all): **EC2** (terminate instances), **ECS** (stop tasks), **EKS** (stop a Kubernetes task), **RDS** (cause database failures) — more over time.
- **How it works**: create **experiments** (using **pre-built templates**) → choose what happens to which resources (EC2 instances, ECS clusters, RDS databases, …) → **start the experiment** so resources get disrupted → **observe how the application behaves** with **CloudWatch, EventBridge, X-Ray** or your tool of choice → **stop the experiment** and review results for **performance, observability or resiliency issues** → improve the application.

### Lecture: Step Functions

- **AWS Step Functions** builds a **serverless visual workflow** to perform **orchestration**, usually of **Lambda functions**.
- You **design a graph** where each step defines what happens next **on success or failure** — enabling **complex workflows** in AWS.
- **Built-in features**: **sequencing, parallel functions, conditions, timeouts, error handling**, and more.
- **Not limited to Lambda** — integrates with **EC2 instances, ECS tasks, on-premises servers, API Gateway, SQS queues, DynamoDB** and many other AWS services.
- **Human approval** can be implemented in a workflow — the workflow pauses, a human reviews the results, and answering **yes** continues while **no** fails the workflow.
- **Use cases**: **order fulfillment, data processing, web applications**, or any **complex workflow** that benefits from a **visual graph**.

### Lecture: Ground Station

- **AWS Ground Station** is a **fully managed service to control satellite communications, process data, and scale satellite operations**.
- It provides a **global network of satellite ground stations near AWS regions**, making it easier to get satellite data into the AWS cloud.
- **How it works**: the Ground Station service runs in the cloud, connects to satellites, and lets you **download satellite data into your AWS VPC within seconds** — into **Amazon S3 buckets** or **EC2 instances** — where you can process it as you wish.
- **Use cases**: **weather forecasting, surface imaging, communications, video broadcast**.

---

### Lecture: AWS Pinpoint

- **Amazon Pinpoint** is a **scalable two-way (inbound and outbound) marketing communication service**.
- **Channels**: **email, SMS, push notifications, voice, and in-app messaging** — **SMS** is one of the main use cases.
- Capabilities: **segment and personalize messages** with the right content per customer (create groups and segments), and **receive replies**. Scales to **billions of messages per day**.
- **Use cases**: run **campaigns** by sending **marketing email in bulk**, or sending **transactional SMS messages**.
- **Events** (text success, text delivered, replies, …) are delivered to **Amazon SNS, Kinesis Data Firehose, and CloudWatch Logs** — so you can build automation on top.

**Pinpoint vs. SNS / SES**

| Amazon SNS / SES | Amazon Pinpoint |
|---|---|
| **Your application** must manage each message's **audience, content and delivery schedule** | **Pinpoint manages** **message templates, delivery schedules, highly targeted segments and full campaigns** |
| A lot of work, not very scalable for marketing | The **next evolution** of SNS/SES for a **full-blown marketing communications service** |

## Section: Other Services — Key Takeaways

> Note: the instructor deliberately did **not** provide a summary lecture for this section — it is a "one service, one definition" list. The summary below organizes those definitions for study purposes.

**Most important concepts**
- **End-user computing**: **WorkSpaces** = full managed **desktop** (DaaS, replaces on-premises VDI); **AppStream 2.0** = stream a **single application** to a **web browser**.
- **Application development services**: **IoT Core** (connect IoT devices, pub/sub, billions of devices), **AppSync** (**GraphQL** backend with real-time sync and offline support), **Amplify** (full-stack web/mobile toolkit — "Elastic Beanstalk for web and mobile apps"), **Infrastructure Composer** (visually design serverless apps, generates **CloudFormation** IaC), **Device Farm** (test on **real** browsers/devices/tablets), **Step Functions** (serverless visual **orchestration** workflows with human approval).
- **Backup and disaster recovery**: **AWS Backup** centralizes and automates backups (PITR, cross-region, cross-account) into **S3**; the **four DR strategies** run from **Backup and Restore (cheapest)** through **Pilot Light** and **Warm Standby** to **Multi-Site/Hot Site (most expensive)**; **Elastic Disaster Recovery (DRS)** does **continuous block-level replication** into a cheap staging environment with **fail over in minutes** and later **failback**.
- **Migration**: the **7 Rs** (**Retire, Retain, Relocate, Rehost, Replatform, Repurchase, Refactor**) name the strategic choices; **Application Discovery Service** plans (agentless connector vs. discovery agent, dependency mapping), **Application Migration Service (MGN)** executes the **lift-and-shift**, **Migration Evaluator** builds the **business case**, **Migration Hub** is the **central tracking hub** (with **Orchestrator** templates), and **DataSync** moves bulk data on-premises → AWS with **incremental** transfers.
- **Resilience testing**: **Fault Injection Simulator (FIS)** applies **chaos engineering** to deliberately break resources and validate how the stack reacts.
- **Specialized services**: **Ground Station** (satellite communications into your VPC/S3/EC2) and **Pinpoint** (two-way marketing communications: email, SMS, push, voice, in-app).

**How the concepts relate**
- **Migration is a pipeline**: choose a strategy from the **7 Rs** → discover and map dependencies with **Application Discovery Service** → justify it with **Migration Evaluator** → execute with **Application Migration Service (MGN)** or **DMS** for databases, and **DataSync** for bulk data → track everything centrally in **Migration Hub**.
- **MGN and DRS are technically the same idea with different goals**: both install a **replication agent** and continuously replicate disks into low-cost EC2/EBS staging, then scale up on **cut over** (MGN, one-time migration) or on **fail over** (DRS, ongoing disaster recovery with failback).
- **DR strategy choice is a cost/readiness trade-off** — the same trade-off logic seen in pricing and high-availability decisions elsewhere in the course; **Route 53** performs the cross-region failover.
- **Amplify sits on top of many services** already covered — S3, Cognito, AppSync (GraphQL), API Gateway (REST), Lambda, DynamoDB, SageMaker, Lex — and **AppSync** itself sits on **DynamoDB and Lambda**.
- **Infrastructure Composer outputs CloudFormation**, tying visual design back to the infrastructure-as-code service from the deployments section; **FIS reports through CloudWatch, EventBridge and X-Ray** from the monitoring section; **Pinpoint emits events to SNS, Firehose and CloudWatch Logs**.
- **WorkSpaces and AppStream both address end-user access**, and the WorkSpaces latency guidance (**deploy close to your users**) is the same global-infrastructure principle used by CloudFront, Global Accelerator and Local Zones.

**Key terminology to remember**
- DaaS (Desktop as a Service), VDI (Virtual Desktop Infrastructure), application streaming, instance type per application
- IoT, pub/sub, connected devices; GraphQL, real-time subscriptions, offline data synchronization
- Amplify Studio, Amplify backend; drag-and-drop IaC, enhanced components, SAM template, YAML/JSON output
- Real device testing, concurrent test execution, reports/logs/screenshots
- Backup plan, retention period, lifecycle management, **point-in-time recovery (PITR)**, cross-region/cross-account backup
- Backup and Restore, Pilot Light, Warm Standby, Multi-Site / Hot Site; failover, failback, cut over
- Continuous block-level replication, replication agent, staging environment, CloudEndure (former names of DRS and MGN)
- Incremental transfer (DataSync); DataSync agent
- The 7 Rs: Retire, Retain, Relocate, Rehost (lift and shift), Replatform (lift and reshape), Repurchase (drop and shop), Refactor/Re-architect; SDDC, VMware Cloud on AWS, SaaS, microservices
- Agentless Discovery / Connector vs. Application Discovery Agent, dependency mapping, server utilization data
- Chaos engineering, fault injection experiment, pre-built templates
- Step Functions: sequencing, parallel, conditions, timeouts, error handling, human approval
- Ground Station, satellite ground stations; Pinpoint: segments, campaigns, transactional SMS, message templates

**Key distinctions/comparisons**
- **WorkSpaces vs. AppStream 2.0**: full desktop (VDI replacement, remote desktop client, on-demand or always on) vs. a single streamed application in a **web browser** (any device, per-application instance type).
- **AppSync vs. Amplify**: the **GraphQL data backend** vs. the **full-stack toolkit** that can use AppSync underneath.
- **Infrastructure Composer vs. CloudFormation**: visual drag-and-drop design that **generates** (or visualizes) templates vs. the IaC engine that deploys them.
- **DR strategies, cheapest → most expensive**: **Backup and Restore** (nothing running) < **Pilot Light** (core functions only, minimal) < **Warm Standby** (full app, minimum size) < **Multi-Site/Hot Site** (full app, full size).
- **AWS Backup vs. Elastic Disaster Recovery**: scheduled/on-demand backups with retention and PITR across AWS services vs. **continuous replication of whole servers** (including on-premises/physical/virtual) for rapid failover.
- **Application Migration Service (MGN) vs. Elastic Disaster Recovery (DRS)**: one-time **migration** ending in a **cut over** vs. ongoing **disaster recovery** with **fail over and failback**.
- **Application Discovery Service vs. Migration Evaluator vs. Migration Hub**: discover servers and dependencies vs. build the **cost/business case** vs. **centrally assess, plan and track** the migration.
- **Agentless Discovery vs. Discovery Agent**: VM configuration and performance history vs. deeper in-VM detail including running processes and **network connections** for dependency mapping.
- **Rehost vs. Replatform vs. Refactor**: no changes (lift and shift, up to 30% savings) vs. keep the core architecture but adopt managed/serverless services vs. re-architect with cloud-native features (most effort, most payoff).
- **Retire vs. Retain**: switch off what you don't need vs. deliberately leave it on-premises.
- **DataSync vs. AWS Backup**: move/synchronize large data sets on-premises → AWS (incremental, scheduled) vs. centrally manage and automate backups of AWS resources.
- **Pinpoint vs. SNS/SES**: managed **campaigns, segments, templates and schedules** vs. your application handling audience, content and delivery itself.
- **Step Functions vs. SQS/SNS**: visual **orchestration** of multi-step workflows with branching, retries and human approval vs. simple decoupling via queues/topics.

**You should be able to explain:**
- The difference between WorkSpaces and AppStream 2.0, and how to minimize WorkSpaces latency for users in different parts of the world.
- What IoT Core, AppSync (and its GraphQL link), Amplify, Infrastructure Composer, Device Farm and Step Functions each do.
- What AWS Backup manages, which services it supports, and where the backups land.
- The four disaster recovery strategies in cost order, what runs in each, what recovery requires, and which is cheapest and most expensive.
- How Elastic Disaster Recovery works end-to-end (replication agent → staging → fail over → failback).
- What DataSync is for, its destinations, and why "incremental" is the exam hint.
- All seven Rs of cloud migration with an example of each.
- Which service to use to discover, justify, execute and track a migration — and the difference between agentless and agent-based discovery.
- What chaos engineering means and what FIS lets you do.
- What Ground Station and Pinpoint are for, and how Pinpoint differs from SNS and SES.
