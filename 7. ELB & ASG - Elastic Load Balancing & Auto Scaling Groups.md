## Section: ELB & ASG - Elastic Load Balancing & Auto Scaling Groups

### Lecture: High Availability, Scalability, Elasticity

**Scalability**: the ability of an application to handle greater loads by adapting. Two kinds:

**Vertical scalability**
- Increasing the **size** of an instance.
- *Analogy:* upgrading a junior call-center operator into a senior operator, who can handle more calls due to more experience.
- Example: moving an application from a `t2.micro` to a `t2.large`.
- Very common for **non-distributed systems**, such as databases — to boost performance, you increase the size of the database server.
- There is a **hardware limit** to how far you can vertically scale (though these limits can be very high today).

**Horizontal scalability**
- Increasing the **number** of instances/systems for an application, rather than the size of one.
- *Analogy:* adding more call-center operators as call volume grows (e.g., scaling from 1 operator up to 6).
- Implies a **distributed system** — for a call center, each operator can independently handle calls.
- Very common for web applications / modern applications; easy on AWS thanks to EC2 and **Auto Scaling Groups**.

**High Availability**
- Goes hand-in-hand with horizontal scaling.
- Means running your application/system across **at least two Availability Zones**.
- *Analogy:* a call center in New York and a second one in San Francisco — if a power outage takes down New York, San Francisco can still take calls. San Francisco will be busier, but the business survives the disaster.
- Goal: survive a data center loss/disaster (e.g., earthquake, power outage).

**Summary table**

| Concept | Meaning | AWS mechanism |
|---|---|---|
| Vertical scaling | Increase (**scale up**) or decrease (**scale down**) instance size | Change instance type, e.g., `t2.nano` (0.5 GB RAM, 1 vCPU) up to `u-12tb1.metal` (12.3 TB RAM, 448 vCPUs) |
| Horizontal scaling | Increase (**scale out**) or decrease (**scale in**) the number of instances | Auto Scaling Group + Load Balancer |
| High Availability | Run instances of the same application across multiple AZs | Auto Scaling Group in multi-AZ mode + Load Balancer in multi-AZ |

> **Exam Tip:** the exam may test whether you can distinguish **scalability**, **elasticity**, and **agility**:
> - **Scalability**: the ability of a system to accommodate a larger load, either by making the hardware stronger (**scale up**) or by adding nodes (**scale out**).
> - **Elasticity**: a more cloud-native concept — once a system is scalable, elasticity means the system has **automatic scaling** built in, so it scales based on the load it's actually receiving. This enables pay-per-use pricing that matches server count to demand, optimizing cost. Elasticity is a **key concept in AWS**.
> - **Agility**: **not** related to scalability or elasticity — this is a deliberate exam distractor. Agility means new IT resources are "only a click away," reducing the time to provision resources from weeks to minutes, letting an organization iterate and move faster.

### Lecture: Elastic Load Balancing (ELB) Overview

- A **load balancer** is a server that forwards incoming traffic to multiple downstream servers — in AWS, these downstream servers are typically EC2 instances, called **backend EC2 instances**.
- **Elastic Load Balancing (ELB)** is AWS's **managed** load balancing service.
- Architecture: users talk to the load balancer (the single publicly exposed endpoint); the load balancer distributes ("balances") requests across multiple backend EC2 instances — as more users connect, traffic is spread across more of the backend instances.

**Why use a load balancer**
- Spreads load across multiple downstream instances.
- Exposes a **single point of access** (a DNS hostname) for your application.
- Seamlessly handles failures of downstream instances via regular **health checks** — if an instance is unhealthy, the load balancer stops sending it traffic (effectively hiding the failure).
- Can provide **SSL termination** (HTTPS) for your website easily.
- Can operate across **multiple Availability Zones**, making your application highly available.

**Managed vs. self-managed**
- Being a managed service, ELB requires no server provisioning by you — AWS handles upgrades, maintenance, and high availability of the load balancer itself.
- Running your own load balancer on EC2 is possible and cheaper up front, but requires significantly more effort: maintenance, integration, OS management, patching, etc.

**Four kinds of load balancers (know the differences for the exam)**

| Load Balancer | OSI Layer | Protocol(s) | Key characteristic |
|---|---|---|---|
| **Application Load Balancer (ALB)** | Layer 7 | HTTP / HTTPS (also gRPC) | Look for: HTTP routing features, static DNS/URL |
| **Network Load Balancer (NLB)** | Layer 4 | TCP / UDP (also TLS over TCP) | Look for: **ultra high performance** — millions of requests/second, ultra-low latency; provides a **static IP** via an Elastic IP |
| **Gateway Load Balancer (GWLB)** | Layer 3 | Uses the GENEVE protocol on IP packets | Look for: routing traffic to firewalls / intrusion detection / deep packet inspection appliances |
| **Classic Load Balancer (CLB)** | Layer 4 & 7 | — | Older generation, being **retired in 2023**; replaced by ALB and NLB — instructor notes it likely won't appear on the exam anymore |

**Architecture per type**
- **ALB**: users access the load balancer over HTTP/HTTPS/gRPC → ALB routes traffic to downstream targets (e.g., EC2 instances).
- **NLB**: same overall shape as ALB, but traffic arrives over TCP/UDP → forwarded to downstream targets; also gives a static IP.
- **GWLB**: more complex — it does **not** balance load directly to your application. Instead, it balances traffic to **third-party security virtual appliances** running on EC2 instances (for firewalling, intrusion detection, or deep packet inspection). Traffic flow: client → GWLB → virtual appliance EC2 instance(s) analyze the traffic → sent back to the GWLB → forwarded on to the actual application.

### Lecture: Application Load Balancer (ALB) Hands On

**Setup**
- Launch two EC2 instances: Amazon Linux 2, `t2.micro`, no key pair needed (SSH not required — EC2 Instance Connect can be used if needed), an existing security group ("Launch Wizard 1," allowing HTTP + SSH), basic storage, and the same EC2 User Data script used previously to stand up a "Hello World" web server.
- Confirmed each instance independently returns "Hello World" via its own public IP.
- Goal: expose a **single URL** to access both instances and balance load between them → requires a **Load Balancer**.

**Creating an Application Load Balancer**
- Name it (e.g., "DemoALB").
- Scheme: **internet-facing**; Address type: IPv4.
- **Network mapping**: choose a VPC and select the Availability Zones the load balancer should be deployed across (deployed across all AZs in this demo).
- **Security Group**: create a dedicated one for the load balancer (e.g., "demo-sg-load-balancer") allowing **HTTP inbound from anywhere**; remove the default security group so only the dedicated one remains.
- **Listeners and Routing**: configure HTTP on port 80, routed to a **Target Group**.
- **Target Group**: a logical grouping of EC2 instances (targets) that the load balancer sends traffic to.
  - Create one (e.g., "demo-tg-alb"), protocol HTTP, port 80, HTTP version 1, default health check settings.
  - Register both EC2 instances as targets on port 80.
- After creation, the ALB moves through a "provisioning" state before becoming "active."

**Verifying load balancing**
- Once active, the ALB provides a **DNS name** — visiting it in a browser returns "Hello World," and **repeated refreshes alternate the response between the two backend instances**, proving the load balancer is actively distributing traffic.
- The **Target Group** shows both targets as "healthy" when both instances are responding correctly.
- **Health check behavior demonstrated**: stopping one instance causes the target group to detect it as unhealthy after a short delay — subsequent requests to the ALB are then served only by the remaining healthy instance.
- Restarting the stopped instance moves it through an "initial" health check state before returning to "healthy," after which the ALB resumes distributing traffic to both instances again.

### Lecture: Auto Scaling Groups (ASG) Overview

- **Motivation**: real-world load fluctuates over time (e.g., shopping traffic is higher during the day than at night). The cloud lets you create and remove servers very quickly to match this changing demand.

**Goals of an Auto Scaling Group (ASG)**
- **Scale out**: add EC2 instances to match increased load.
- **Scale in**: remove EC2 instances to match decreased load.
- Ensure a defined **minimum** and **maximum** number of machines are running at any time.
- Automatically **register/deregister** instances with a Load Balancer as they are created or removed.
- Detect **unhealthy** instances, terminate them, and replace them with new healthy ones.

**Benefit**: significant cost savings — the system runs at the optimal capacity at all times, which is a core expression of the cloud's **elasticity** principle.

**Key ASG settings**
- **Minimum size** (e.g., 1 instance).
- **Desired capacity** — usually equal to the actual/current size of the ASG.
- **Maximum size**.

- An ASG works hand-in-hand with a Load Balancer: as the ASG scales out, new instances are automatically registered with the load balancer, which begins sending them traffic; as it scales in, instances are deregistered.

### Lecture: Auto Scaling Groups (ASG) Hands On

- **First**: terminate the original two standalone EC2 instances, since the ASG will manage its own instances going forward.

**Creating the ASG**
- Name it (e.g., "DemoASG").
- Requires a **Launch Template**, which defines how the ASG creates EC2 instances — very similar to normal instance launch settings: AMI (Amazon Linux 2), instance type (`t2.micro`), no key pair, an existing security group (e.g., "launch-wizard-1"), default EBS storage, and an EC2 User Data bootstrap script.
- **Instance type requirements**: the launch template's instance type can be overridden here, but wasn't in this demo.
- **Network**: choose a VPC and multiple Availability Zones (3 AZs selected in the demo) with an AZ distribution strategy (e.g., "balanced best effort" — the default).
- **Load Balancing**: attach the ASG to an existing Load Balancer's **Target Group** (e.g., "demo-tg-alb") so new instances are automatically registered as targets.
- **Health checks**: EC2 health checks are always enabled by default. You can additionally enable **ELB health checks**, so instances the load balancer deems unhealthy are automatically terminated by the ASG.
- **Group size**: set Desired Capacity (e.g., 2), Minimum Capacity (e.g., 1), Maximum Capacity (e.g., 2, adjustable — e.g., to 4).
- **Automatic scaling policies**: not configured in this basic demo (covered in the next lecture).
- **Instance maintenance policy**: left as "No Policy" to keep things simple.

**Observed behavior after creation**
- The ASG initially shows "Updating capacity" while it launches instances to reach the desired capacity (e.g., from 0 to 2).
- The **Activity** tab logs scaling events (e.g., launching new instances because desired capacity increased).
- New instances appear in the EC2 console as "pending," then running — and are fully managed by the ASG.
- New instances are automatically registered in the associated Target Group — initially "unhealthy" until fully booted, then "healthy."
- **Speeding up health checks** (for demo purposes): Target Group → Health Checks settings → Advanced Settings → set healthy threshold to 2 and interval to 5 seconds (the timeout must be less than the interval — e.g., 2 seconds).
- Once healthy, the Load Balancer's DNS name serves "Hello World" from both ASG-managed instances.

**Self-healing demonstration**
- Manually terminating one ASG-managed instance triggers the ASG to detect that the running count has dropped below the desired capacity.
- The ASG automatically launches a replacement instance — logged as "an instance was launched in response to an unhealthy instance needing to be replaced."
- This illustrates the ASG's **self-healing** capability, and sets up the concept of automatic scaling policies (covered next), which adjust desired capacity automatically based on load.

### Lecture: Auto Scaling Groups (ASG) Strategies

| Strategy | Description |
|---|---|
| **Manual Scaling** | Manually updating the ASG's size (e.g., changing desired capacity from 1 to 2, or back). |
| **Dynamic Scaling — Simple / Step Scaling** | Triggered by a CloudWatch alarm; you define the trigger and how many units to add or remove. Example: if average CPU utilization > 70% for 5 minutes → add 2 units of capacity. Example: if average CPU utilization < 30% for 10 minutes → remove 1 unit of capacity. |
| **Dynamic Scaling — Target Tracking Scaling** | A simpler way to define a scaling policy: specify a target metric value, and AWS automatically scales the ASG to maintain it. Example: keep average CPU utilization across the ASG at ~40%. |
| **Scheduled Scaling** | Anticipates scaling needs based on known/predictable usage patterns ahead of time. Example: increase minimum capacity to 10 instances at 5 PM every Friday, anticipating a traffic spike (e.g., sports betting activity before a game). |
| **Predictive Scaling** | Uses **Machine Learning** to forecast future traffic based on historical patterns, and automatically provisions the right number of EC2 instances ahead of time to match the predicted demand. Useful for workloads with recurring, time-based patterns (e.g., a daily traffic peak lasting a few hours). Requires no manual intervention. |

> **Exam Tip:** Predictive Scaling is explicitly called out as appearing on the exam — remember it's the ML-powered, forecast-based strategy.

### Lecture: Section Cleanup

- **Important:** terminating the ASG-managed EC2 instances directly does **not** work — the ASG will simply detect the reduced capacity and recreate them.
- **Correct cleanup order:**
  1. Delete the **Auto Scaling Group** itself (type "Delete" to confirm) — this also removes its managed EC2 instances.
  2. Delete the **Application Load Balancer** (Actions → Delete, confirm).
  3. The **Target Group** does not need to be deleted manually — it doesn't cost any money, and it will simply become empty once the ASG and load balancer are gone.
- End result: fully cleaned up, remaining within the free tier.

### Lecture: ELB & ASG Summary

- **High Availability**: application runs across multiple Availability Zones.
- **Vertical scaling**: increasing the size of an instance.
- **Horizontal scaling**: increasing the number of instances.
- **Elasticity**: the ability to scale up and down automatically based on demand.
- **Agility**: a cloud concept — being able to create and delete resources very quickly, enabling faster work.
- **Load Balancers (ELB)**: distribute traffic across backend EC2 instances; can span multiple AZs; support health checks to ensure backend instances are healthy.
- **Four types of load balancers**: Classic (old, retired), Application Load Balancer (HTTP, Layer 7), Network Load Balancer (very high performance, TCP, Layer 4), Gateway Load Balancer (Layer 3, routes traffic through virtual appliances).
- **Auto Scaling Groups**: implement elasticity — spread load across multiple AZs, scale EC2 instances based on system demand, and replace unhealthy instances.
- There is a **tight integration between ASG and ELB** — together they achieve high availability, scalability, elasticity, and agility in the cloud.

## Section: ELB & ASG - Key Takeaways

**Most important concepts**
- **Scalability** (vertical: bigger instances; horizontal: more instances), **High Availability** (multi-AZ), **Elasticity** (automatic scaling to match demand), and **Agility** (fast resource provisioning) are related but formally distinct concepts frequently tested on the exam.
- **Elastic Load Balancing (ELB)** is AWS's managed load balancing service, distributing traffic across backend EC2 instances, performing health checks, and enabling high availability across multiple AZs.
- Four load balancer types exist — **ALB** (Layer 7, HTTP/HTTPS/gRPC), **NLB** (Layer 4, TCP/UDP, ultra-high performance, static IP), **GWLB** (Layer 3, routes to security virtual appliances), and the retired **Classic Load Balancer**.
- **Auto Scaling Groups (ASGs)** automatically scale EC2 instance counts (out/in) between a minimum and maximum, replace unhealthy instances, and integrate tightly with a load balancer for automatic target registration/deregistration.
- ASG **scaling strategies** range from fully manual to fully automated: Manual, Dynamic (Simple/Step, Target Tracking), Scheduled, and Predictive (ML-based).

**How the concepts relate**
- **Horizontal scaling** (more instances) is what makes **High Availability** achievable, since instances can be spread across multiple AZs.
- An **ASG** is the mechanism that implements horizontal scaling (and thus elasticity) for EC2 — it decides when to scale out/in — while an **ELB** is the mechanism that distributes traffic across whatever instances currently exist and reports their health.
- The ASG relies on the **Target Group** (owned by the load balancer) to know which instances should currently receive traffic — when the ASG launches or terminates an instance, it automatically registers/deregisters it from the Target Group.
- **Scaling strategies** (Simple/Step, Target Tracking, Scheduled, Predictive) are the "brains" that decide *when* and *by how much* the ASG should scale out or in — turning a static ASG into a truly elastic system.

**Key terminology to remember**
- Vertical scaling (scale up/down) vs. Horizontal scaling (scale out/in)
- High Availability, Elasticity, Agility
- Elastic Load Balancer (ELB), backend/target EC2 instances, health checks, SSL termination
- Application Load Balancer (ALB), Network Load Balancer (NLB), Gateway Load Balancer (GWLB), Classic Load Balancer (CLB)
- Target Group, Listener
- Auto Scaling Group (ASG), Launch Template, Desired/Minimum/Maximum capacity
- Dynamic Scaling (Simple/Step Scaling, Target Tracking Scaling), Scheduled Scaling, Predictive Scaling
- CloudWatch alarm (as a scaling trigger)

**Key distinctions/comparisons**
- **Vertical vs. Horizontal scaling**: bigger machine vs. more machines; vertical has a hardware ceiling, horizontal requires a distributed system.
- **Scalability vs. Elasticity vs. Agility**: capability to handle more load vs. automatic scaling to match demand vs. speed of provisioning resources (a deliberate exam distractor unrelated to the other two).
- **ALB vs. NLB vs. GWLB vs. CLB**: HTTP/HTTPS Layer 7 vs. ultra-high-performance TCP/UDP Layer 4 (with static IP) vs. Layer 3 traffic routing to security appliances vs. retired legacy load balancer.
- **Manual vs. Dynamic vs. Scheduled vs. Predictive Scaling**: human-triggered vs. metric/alarm-triggered vs. time-of-day-triggered vs. ML-forecast-triggered.
- **Simple/Step Scaling vs. Target Tracking Scaling**: explicitly defined trigger + fixed capacity adjustment vs. a single target metric value that AWS automatically maintains.

**You should be able to explain:**
- The difference between vertical and horizontal scaling, and how each maps to AWS services.
- What High Availability means in AWS and why it requires multiple Availability Zones.
- The formal exam definitions of Scalability, Elasticity, and Agility, and why Agility is a distractor.
- Why and how a load balancer is used, including the benefits it provides (single access point, health checks, SSL termination, cross-AZ distribution).
- The differences between the four load balancer types and the exam keywords associated with each.
- How to configure a basic Application Load Balancer with a target group, and how health checks affect routing.
- What an Auto Scaling Group does, its key settings (min/desired/max capacity), and how it integrates with a load balancer.
- How an ASG self-heals by replacing unhealthy or terminated instances.
- The five ASG scaling strategies and when each would be used, including why Predictive Scaling is ML-based.
- The correct order of operations for cleaning up an ASG + load balancer setup (delete the ASG first, then the load balancer).
