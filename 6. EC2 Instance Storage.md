## Section: EC2 Instance Storage

### Lecture: EBS Overview

- **EBS = Elastic Block Store** — a **network drive** that can be attached to EC2 instances while they run.
- **Persists data** even after the EC2 instance is terminated (as long as the volume itself isn't deleted) — you can recreate an instance, mount the same EBS volume, and get your data back.
- At the CCP level, an EBS volume can only be **mounted to one instance at a time**.
- An EBS volume is bound to a specific **Availability Zone (AZ)** — it cannot be attached to an instance in a different AZ than the one it was created in.
- **Analogy:** think of an EBS volume as a **network USB stick** — it can be "unplugged" from one machine and "plugged into" another, but the connection is over the network rather than physical, so there can be some latency.
- Because it's a network drive, an EBS volume can be **quickly detached from one EC2 instance and attached to another** — very useful for failover scenarios.
- EBS is a **provisioned** resource — you must specify capacity in advance:
  - **Size** (in GB).
  - **IOPS** (I/O Operations Per Second) — defines performance.
  - You're billed for the capacity you provision, and can increase it over time.
- One EC2 instance **can** have multiple EBS volumes attached (like multiple "network USB sticks" plugged into one machine) — but at the CCP level, one EBS volume cannot be attached to more than one instance.
- EBS volumes can be created and left **unattached**, and attached to an instance later, on demand.

**Delete on Termination attribute**
- Controls what happens to an attached EBS volume when its EC2 instance is **terminated**.
- **Default for the root volume:** enabled (Yes) — the root volume is deleted when the instance is terminated.
- **Default for any additional attached EBS volumes:** disabled (No) — they persist after instance termination.
- This setting can be toggled by the user.
- > **Exam Tip:** A common exam scenario is choosing to **disable** "Delete on Termination" for the root volume specifically to preserve data after an instance is terminated.

### Lecture: EBS Hands On

- View volumes attached to an instance: Instance → **Storage** tab — shows the root device and any additional block devices.
- Clicking a volume opens the **Volumes** interface (also accessible directly via the left sidebar → **Volumes**).
- **Creating a new volume:** choose a type (e.g., GP2, GP3), a size (e.g., 2 GB), and an **Availability Zone** — the AZ **must match** the AZ of the instance you intend to attach it to (found under the instance's Networking details).
- **Attaching a volume:** select the (available, unattached) volume → **Actions → Attach Volume** → choose the target instance.
- **Demonstrated AZ restriction:** creating a volume in a *different* AZ than the target instance and attempting to attach it **fails** — confirms EBS volumes are strictly AZ-bound.
- **Deleting a volume:** Actions → Delete Volume — happens almost instantly, illustrating the speed/flexibility of the cloud.
- **Delete on Termination demonstrated:** terminating the EC2 instance automatically deletes its root volume (which had "Delete on Termination" = Yes), while a manually-created second volume (Delete on Termination = No, and not the root) survives the instance's termination and remains available afterward.

### Lecture: EBS Snapshots Overview

- A **snapshot** is a backup of an EBS volume, taken at any point in time.
- Purpose: restore the volume's state later — even if the original EBS volume is later deleted.
- It's not strictly necessary to detach the volume before snapshotting, but it's **recommended** for a clean, consistent backup.
- **Snapshots can be copied across Availability Zones or Regions** — this is the mechanism used to "move" data across AWS's global infrastructure.

**Process to move an EBS volume to a different AZ:**
1. Take a snapshot of the volume while it's attached to an EC2 instance in AZ-A (optionally stop the instance first for a cleaner snapshot).
2. The snapshot exists at the **region** level (not tied to a single AZ).
3. Restore a **new** EBS volume from that snapshot in a different AZ (AZ-B).
4. Attach the new volume to an EC2 instance in AZ-B.

**Two features to know:**
| Feature | What it does |
|---|---|
| **EBS Snapshot Archive** | Moves a snapshot to a cheaper "archive" storage tier — **75% cheaper**, but restoring from archive takes **24–72 hours**. Best for snapshots you don't need to restore urgently. |
| **Recycle Bin for EBS Snapshots** | By default, deleted snapshots are gone permanently. Setting up a Recycle Bin retains deleted snapshots for a configurable period (**1 day to 1 year**) before permanent deletion — protects against accidental deletion. |

### Lecture: EBS Snapshots Hands On

- **Create a snapshot:** select a volume → Actions → Create Snapshot → add a description (e.g., "DemoSnapshots") → Create.
- View all snapshots: left sidebar → **Snapshots**.
- **Copy a snapshot to another region:** right-click → Copy Snapshot → choose a destination region — useful for a **Disaster Recovery** strategy (keeping backups in a separate AWS region).
- **Create a new volume from a snapshot:** Actions → Create Volume from Snapshot → choose size/type, a target AZ (which can differ from the original), optional encryption, and tags. This is the practical demonstration of "copying" an EBS volume across AZs via a snapshot.
- **Recycle Bin demo:** create a Retention Rule (e.g., "DemoRetentionRule") — select the resource type (EBS Snapshots), the scope (apply to all resources), the retention period (e.g., 1 day), and the Rule Lock setting (locked or unlocked, determining if the rule itself can later be deleted).
- **Storage Tiers:** a snapshot defaults to the "Standard" tier; it can be moved to the Archive tier for cost savings, with the 24–72 hour restore delay noted earlier.
- **Deletion + recovery demo:** deleting a snapshot with the Recycle Bin enabled removes it from the Snapshots list, but it then appears under **Resources** (the Recycle Bin) — from there it can be recovered ("Recover Resources") and restored back to the Snapshots list.

### Lecture: AMI Overview

- **AMI = Amazon Machine Image** — represents a customization of an EC2 instance (its own software configuration, OS setup, monitoring tools, etc.).
- Using a custom AMI gives **faster boot and configuration time**, since the desired software is already prepackaged into the image.
- AMIs are built for a specific region but **can be copied across regions** to leverage AWS's global infrastructure.

**Three sources of AMIs for launching an instance:**
1. **Public AMI** — provided by AWS (e.g., the Amazon Linux 2 AMI used throughout this course).
2. **Your own AMI** — built and maintained by you.
3. **AWS Marketplace AMI** — created (and often sold) by a third-party vendor; you can also sell your own AMIs on the Marketplace.

**AMI creation process:**
1. Launch and customize an EC2 instance.
2. **Stop** the instance (to ensure data integrity).
3. Build an AMI from it — this also creates EBS snapshots behind the scenes.
4. Launch new instances from that custom AMI (potentially in a different AZ/region).

---

### Lecture: AMI Hands On

- **Demo setup:** launch an instance (Amazon Linux 2, `t2.micro`, an existing security group, default storage) with a User Data script that installs the Apache **HTTPD** web server but **stops short** of creating the index/HTML file — the goal is to bake a base image with the web server installed but not yet configured with content.
- Important: even once the instance shows "running," you must **wait** for the User Data script to finish executing before the installed software is actually available.
- **Create an AMI from the running instance:** right-click the instance → **Image and templates → Create Image** → name it (e.g., "demo image") → Create Image.
- The new AMI appears under **AMIs** (left sidebar) with a "pending" status until creation completes.
- **Launch a new instance from the custom AMI:** during instance launch, choose the **"My AMIs"** tab → select the custom AMI. This time, the User Data script only needs to write the HTML/index file (since HTTPD is already installed as part of the AMI) — resulting in a **much faster boot-up**, since software installation is skipped.
- This demonstrates the core value of AMIs: pre-baking software/configuration into an image significantly speeds up subsequent instance launches (this scales to security software, application prerequisites, etc.).
- Cleanup: terminate both demo instances afterward.

### Lecture: EC2 Image Builder Overview

- **EC2 Image Builder** automates the **creation, maintenance, validation, testing, and distribution** of virtual machine (or container) images / AMIs.

**Process:**
1. EC2 Image Builder automatically creates a **"Builder EC2 instance."**
2. That instance builds components and customizes software (e.g., install Java, update the CLI, update the OS, install firewalls, install your application — whatever you define).
3. An **AMI is created** automatically from that instance.
4. EC2 Image Builder automatically creates a **"test EC2 instance"** from the new AMI and runs user-defined tests (e.g., is the AMI working? is it secure? is the application running correctly?) — tests can be skipped if not needed.
5. Once validated, the AMI is **distributed** — including to **multiple regions**, enabling truly global application deployment.

- Can be run on a **schedule** (e.g., weekly), triggered when packages are updated, or run manually.
- EC2 Image Builder itself is a **free service** — you only pay for the underlying resources it uses: the EC2 instances it creates during the build/test process, and the storage of the resulting AMI(s) wherever they're created or distributed.

### Lecture: EC2 Instance Store

- An alternative to network-attached storage (EBS): the **EC2 Instance Store** is a **hardware disk physically attached** to the underlying physical server hosting your EC2 instance.
- Used for very **high I/O performance and throughput** — higher performance than EBS.
- **Key limitation:** EC2 Instance Store is **ephemeral** — if the instance is **stopped or terminated**, the data stored on it is **lost**.
- Not suitable for durable, long-term storage — use **EBS** for that instead.
- Good use cases: **buffers, caches, scratch data, or temporary content.**
- Additional risk: if the underlying physical server/hardware fails, data on the Instance Store is lost too — backing it up (if needed) is entirely the user's responsibility.
- **Performance example:** I3-type instances with an Instance Store can reach roughly 3.3 million random read IOPS and 1.4 million random write IOPS, versus up to ~32,000 IOPS for a `gp2` EBS volume — illustrating the large performance gap.
- > **Exam Tip:** whenever an exam question describes a "very high performance hardware-attached volume" for an EC2 instance, think **EC2 Instance Store**.

### Lecture: EFS Overview

- **EFS = Elastic File System** — a managed **Network File System (NFS)**.
- Key difference from EBS: EFS can be mounted to **hundreds of EC2 instances at the same time** (a shared network file system), versus EBS's one-instance-at-a-time limitation.
- EFS works **only with Linux** EC2 instances.
- EFS works **across multiple Availability Zones** — instances in different AZs (within the same region) can mount and share the *same* EFS volume simultaneously.
- Characteristics: highly available, scalable, but relatively **expensive** — about **3x the price** of a `gp2` EBS volume.
- Pricing model: **pay-per-use** — no need to provision capacity in advance (e.g., storing 20 GB means you only pay for 20 GB).

**EBS vs. EFS**

| | EBS | EFS |
|---|---|---|
| Instance attachment | One instance at a time, within one specific AZ | Hundreds of instances at once, across multiple AZs |
| Moving across AZs | Requires a snapshot + restore as a new (unsynced) copy in another AZ | Natively shared — the same files are visible to all mounted instances at once |
| OS support | Any | Linux only |
| Relative cost | Lower (baseline) | ~3x EBS `gp2` cost |
| Capacity planning | Must provision size/IOPS in advance | Pay-per-use; no advance capacity planning |

> **Exam Tip:** This EBS vs. EFS distinction is directly tested on the exam.

**EFS Infrequent Access (EFS-IA)**
- A cost-optimized **storage class** for files that aren't accessed often.
- Up to **92% lower cost** compared to EFS Standard.
- **Lifecycle Policy:** automatically moves files to EFS-IA based on how recently they were last accessed (e.g., "move to EFS-IA after 60 days without access").
- Files are automatically moved back to EFS Standard as soon as they're accessed again.
- Fully **transparent to applications** — an application doesn't need to know or care which storage class a given file is currently in.

### Lecture: Shared Responsibility Model for EC2 Storage

| Responsibility | Owner |
|---|---|
| Infrastructure | AWS |
| Replicating data across multiple hardware (per EBS/EFS technical specs), so a single hardware failure doesn't impact the customer | AWS |
| Replacing faulty hardware (e.g., a failing EBS drive) | AWS |
| Ensuring AWS employees cannot access customer data | AWS |
| Setting up backup and snapshot procedures/guidelines | **Customer** |
| Setting up data encryption (an extra protective layer) | **Customer** |
| Any data written to the disk | **Customer** |
| Understanding and managing the risks of using EC2 Instance Store (ephemeral storage, hardware failure) and backing it up as needed | **Customer** |

### Lecture: Amazon FSx Overview

- **FSx** is a managed service for getting **third-party, high-performance file systems** on AWS — an alternative when EFS or S3 don't fit your needs.
- Three current offerings: **FSx for Lustre**, **FSx for Windows File Server**, and **FSx for NetApp ONTAP** — this lesson focuses on the first two as the most important for the exam.

**FSx for Windows File Server**
- A fully managed, highly reliable, and scalable **Windows-native shared file system**, built on Windows File Server.
- Meant for **Windows** workloads.
- Typically deployed across **two Availability Zones**.
- Supports native Windows protocols: **SMB** and **Windows NTFS**.
- Can be mounted by Windows clients on-premises (via SMB) as well as by Windows-based EC2 instances.
- Integrates with **Microsoft Active Directory** for user security.
- Accessible from AWS directly, or from your on-premises infrastructure.

**FSx for Lustre**
- A fully managed, high-performance, and scalable file storage system for **High Performance Computing (HPC)**.
- > **Exam Tip:** whenever you see "storage for HPC," think **FSx for Lustre**.
- Name origin: derived from "**L**inux" + "cl**uster**" = **Lustre**.
- Use cases: machine learning, big data analytics, video processing, financial modeling.
- Extremely high performance: hundreds of GB/s of throughput, millions of IOPS, sub-millisecond latency.
- Can connect to on-premises data centers or directly to AWS compute instances.
- Behind the scenes, FSx for Lustre can store data on an **Amazon S3 bucket**.

### Lecture: EC2 Instance Storage Summary

- **EBS**: network drives, attached to one EC2 instance at a time, mapped to a specific AZ; **snapshots** enable backups or transferring data across AZs.
- **AMI**: ready-to-use EC2 instance images with the customizations you want.
- **EC2 Image Builder**: automates building, testing, and distributing AMIs.
- **EC2 Instance Store**: a high-performance hardware disk attached to an EC2 instance; data is lost if the instance is stopped or terminated.
- **EFS**: a network file system (NFS); can attach to hundreds of instances within a region — no AZ lock, works at the region level.
- **EFS-IA**: a cost-optimization storage class for infrequently accessed EFS files.
- **FSx for Windows**: a network file system for Windows servers.
- **FSx for Lustre**: a file system for High Performance Computing (HPC) on Linux.

### Lecture: Section Cleanup

- Practical walkthrough of cleaning up AWS resources after the section, to avoid unwanted charges (even within the free tier).
- The EC2 Dashboard lists all resources running in a region (e.g., instances, volumes, key pairs, snapshots, security groups).
- **Key pairs and security groups don't incur cost** — safe to leave as-is.
- **Terminate all running EC2 instances**: select → right-click → Terminate.
- **Delete leftover EBS volumes** manually — root volumes tied to "Delete on Termination" are removed automatically, but other volumes must be deleted by hand.
- **Delete snapshots**: Actions → Delete. Note: a snapshot **"in use by an AMI" cannot be deleted** until that AMI is deregistered first.
- **Deregister AMIs** (via the AMI console) before deleting their associated snapshots.
- End state confirmed: no running instances, no EBS volumes, no snapshots, and no AMIs remaining.

## Section: EC2 Instance Storage — Key Takeaways

**Most important concepts**
- EC2 offers multiple storage options, each suited to different needs: **EBS** (network block storage, one instance at a time, AZ-bound), **EC2 Instance Store** (ephemeral, hardware-attached, ultra-high performance), **EFS** (shared network file system across many instances/AZs, Linux only), and **FSx** (managed third-party file systems for Windows or HPC workloads).
- **AMIs** package a customized EC2 instance (OS + software configuration) for fast, repeatable instance launches; **EC2 Image Builder** automates the AMI creation/testing/distribution pipeline.
- **Snapshots** are the mechanism for backing up EBS volumes and for moving data across Availability Zones or regions.
- The **Shared Responsibility Model** for storage: AWS handles infrastructure, hardware replication/replacement, and internal access control; the customer handles backups, encryption, data content, and the risks of ephemeral storage.

**How the concepts relate**
- An EBS volume is tied to a single AZ → to move its data to another AZ, you take a **snapshot** (which exists at the region level) and **restore a new volume** from it in the target AZ — this is a copy, not a live sync.
- A customized, running EC2 instance can be turned into an **AMI** (which itself relies on EBS snapshots behind the scenes) → that AMI can be **launched repeatedly** (even in other regions) for fast, consistent instance provisioning → **EC2 Image Builder** automates this entire AMI lifecycle (build → test → distribute) on a schedule.
- Choosing between storage types comes down to the shape of the workload: need the **fastest possible local disk** and can tolerate data loss on stop/terminate → **Instance Store**; need **durable, single-instance** block storage → **EBS**; need a file system **shared across many Linux instances/AZs** → **EFS**; need a managed **Windows or HPC-optimized** file system → **FSx**.
- **Delete on Termination** and the **Recycle Bin**/**Snapshot Archive** features are all about controlling data lifecycle and cost — deciding what's preserved, for how long, and at what price tier.

**Key terminology to remember**
- EBS (Elastic Block Store), IOPS, Delete on Termination
- EBS Snapshot, EBS Snapshot Archive, Recycle Bin (for snapshots/AMIs)
- AMI (Amazon Machine Image): public, custom, and Marketplace AMIs
- EC2 Image Builder: Builder instance, test instance, distribution
- EC2 Instance Store: ephemeral storage
- EFS (Elastic File System), NFS (Network File System), EFS-IA (Infrequent Access), Lifecycle Policy
- FSx, FSx for Windows File Server (SMB, NTFS, Active Directory), FSx for Lustre (HPC)

**Key distinctions/comparisons**
- **EBS vs. EFS**: single-instance/single-AZ block storage vs. shared, multi-AZ, multi-instance (hundreds) network file system; EFS costs ~3x more than `gp2` EBS but requires no capacity planning.
- **EBS vs. EC2 Instance Store**: durable network storage that survives instance stop/termination (if not set to delete) vs. ephemeral, hardware-attached storage that is lost on stop/termination but offers much higher IOPS.
- **EFS Standard vs. EFS-IA**: frequently-accessed files vs. infrequently-accessed files (up to 92% cheaper), moved automatically via a lifecycle policy, transparently to applications.
- **FSx for Windows File Server vs. FSx for Lustre**: Windows-native shared file system (SMB/NTFS, Active Directory integration) vs. Linux-based high-performance file system for HPC workloads.
- **Snapshot Standard tier vs. Archive tier**: standard availability vs. 75% cheaper storage with a 24–72 hour restore time.
- **Customer responsibility vs. AWS responsibility** under the Shared Responsibility Model for storage.

**You should be able to explain:**
- What EBS is, how it's provisioned, and why it's AZ-bound.
- How the "Delete on Termination" attribute works for root vs. additional volumes.
- How EBS snapshots work, including how they're used to move a volume across AZs/regions, and what the Snapshot Archive tier and Recycle Bin do.
- What an AMI is, the three sources of AMIs, and the AMI creation process — plus why booting from a custom AMI is faster than reinstalling software each time.
- What EC2 Image Builder automates and why it's useful at scale.
- What EC2 Instance Store is, why it's ephemeral, and what workloads it's (and isn't) suited for.
- The core differences between EBS and EFS, and what EFS-IA is used for.
- The two main FSx offerings and when each is used.
- The Shared Responsibility Model as it applies specifically to EC2 storage.
- Why and how to clean up unused AWS storage resources (instances, volumes, snapshots, AMIs) to avoid unnecessary costs.
