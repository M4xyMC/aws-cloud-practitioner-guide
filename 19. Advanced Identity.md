## Section: Advanced Identity

### Lecture: Security Token Service (STS) Overview

- **AWS STS (Security Token Service)** has been used **behind the scenes** throughout the course and is **at the center of AWS**.
- Purpose: **create temporary, limited-privilege credentials to access AWS resources** — short-term credentials like an access key and secret access key, but with a **configurable expiration period**.

**How it works**
1. A user has access to a **role** and wants to use it.
2. The user **assumes the role** with an **STS API call**.
3. STS returns **temporary security credentials**: an **access key**, a **secret key**, and a **session token** — all **limited in time**.
4. The user accesses AWS resources with those three credentials, using the permissions of the assumed role.

**Use cases**
- **Identity federation** — manage identities in **external systems** and give them **STS tokens** to access AWS resources.
- **IAM roles for cross-account or same-account access.**
- **IAM roles for EC2 instances** — behind the scenes a script **refreshes the EC2 credentials** using STS.
- > **Exam Tip**: whenever you see "create **temporary, limited-privilege credentials**" → **STS**.

### Lecture: Cognito Overview

- **Amazon Cognito** provides **identity for the users of your web and mobile applications** — potentially **millions** of them.
- **You should NOT create IAM users for them.** **IAM users are only for people who belong to your company and need to use AWS directly.**
- Cognito keeps its **own internal database of users** (potentially millions), and your **mobile and web applications integrate a login with Cognito**.
- Cognito also powers the **"log in with Facebook, Google, Twitter"** buttons you see on websites — clicking them redirects to Google/Facebook and back.
- > If you are building a **web or mobile application** and need a way to **manage users on AWS** → **Cognito**.

### Lecture: Directory Services Overview

**Microsoft Active Directory (AD) — the on-premises concept**
- Found on **any Windows Server with AD Domain Services**.
- It is a **database of objects**: **user accounts, computers, printers, file shares, security groups**.
- Provides **centralized security management** — create accounts and assign permissions in one place.
- *Example*: with a Windows laptop on the corporate network, a **Domain Controller** stores that "John" has a given password. Because all company machines are connected to the Domain Controller, John can use the **same username/password on any of them** — seamless login across many machines and services.
- In short: a way to manage **users, computers, printers**, etc., usually **on-premises**.

**AWS Directory Services — three flavors**

| Flavor | What it is | Join with on-premises AD? | MFA |
|---|---|---|---|
| **AWS Managed Microsoft AD** | Create **your own Active Directory in AWS**; manage users **locally** | Yes — **establish a trust** with an existing on-premises AD so the two trust each other | **Supported** |
| **AD Connector** | A **proxy** that **redirects requests originating from AWS to your on-premises AD**; the **users live on the on-premises AD** | Requests are proxied to the on-premises AD | **Supported** |
| **Simple AD** | **Not** Microsoft Active Directory — an **AD-compatible managed directory** in AWS; a **standalone directory in the cloud** | **Cannot** be joined with an on-premises AD | — |

- > **Exam Tip**: the details of the three flavors are for the **Solutions Architect Associate/Professional** exams. At Cloud Practitioner level, all you need to know is that **Directory Services is the answer whenever you hear "Active Directory" or "Microsoft Active Directory"**.

### Lecture: AWS IAM Identity Center

- **AWS IAM Identity Center** is the **successor to AWS Single Sign-On (SSO)** — if you see either name at the exam, the feature is **single sign-on**.
- **One login for all your AWS accounts in your organization** — this is mostly what the exam tests.
- It also provides one login across:
  - **Business cloud applications**
  - **SAML 2.0-enabled applications**
  - **EC2 Windows instances**
- The user logs in once and gets access to everything you defined for them.

**Identity providers (where user data is stored)**
- A **built-in identity store** inside IAM Identity Center, **or**
- A **third-party identity store** such as **Microsoft Active Directory**, **OneLogin**, or **Okta**.

**What it looks like**
- You log in through **one URL** with **one username and password** → you reach the **AWS IAM Identity Center portal** listing the accounts in your organization → click an account → **Management Console** → direct access to that account's console.
- Benefit: **remember one login instead of one per account**, and manage users **centrally** rather than per account.
- > **Exam Tip**: anytime you see **one login / one access to multiple AWS accounts** → **IAM Identity Center**.

## Section: Advanced Identity — Key Takeaways

**Most important concepts**
- Identity in AWS is **audience-based**: **IAM** for your company's own people who use AWS directly, **Cognito** for the (potentially millions of) **end users of your web/mobile apps**, **Directory Services** for **Microsoft Active Directory** integration, and **IAM Identity Center** for **single sign-on across many AWS accounts**.
- **STS** is the underlying mechanism for **temporary, limited-privilege credentials** — access key + secret key + **session token**, with a configurable expiration. It powers **role assumption**, **identity federation**, **cross-account access**, and the automatic credential refresh for **IAM roles on EC2 instances**.
- **Do not create IAM users for application end users** — that is exactly what **Cognito** exists for.
- **AWS Directory Services** has three flavors distinguished by **where the users live** and whether they can **join an on-premises AD**: **AWS Managed Microsoft AD** (users in AWS, trust with on-premises possible), **AD Connector** (proxy; users stay on-premises), **Simple AD** (standalone, AD-compatible, no on-premises join).
- **IAM Identity Center** (formerly **AWS Single Sign-On**) gives **one login** for **all organization accounts**, business cloud apps, **SAML 2.0** apps and **EC2 Windows instances**, backed by either its **built-in identity store** or a **third-party provider** (Active Directory, OneLogin, Okta).

**How the concepts relate**
- **STS is the plumbing beneath IAM roles**: every time a role is assumed — by a user, by an EC2 instance, or across accounts — STS is issuing the temporary credentials.
- **IAM Identity Center sits on top of AWS Organizations**: the "one login for all your accounts" benefit only makes sense because Organizations groups those accounts together.
- **Directory Services and IAM Identity Center connect**: an existing **Microsoft Active Directory** can be the identity source for IAM Identity Center, letting a company reuse its corporate identities in AWS.
- **Cognito vs. IAM vs. Directory Services** answers the same question at three scales — application users, cloud engineers, and corporate employees/devices.

**Key terminology to remember**
- STS, temporary credentials, access key / secret key / **session token**, expiration period, assume role, identity federation
- Amazon Cognito, user database for web/mobile apps, social login (Facebook, Google, Twitter)
- Microsoft Active Directory (AD), AD Domain Services, Domain Controller, database of objects (users, computers, printers, file shares, security groups), centralized security management
- AWS Managed Microsoft AD, **trust** relationship, AD Connector (proxy), Simple AD, MFA support
- AWS IAM Identity Center (formerly AWS Single Sign-On), single sign-on, identity store, SAML 2.0, OneLogin, Okta

**Key distinctions/comparisons**
- **IAM users vs. Cognito users**: employees/people in your company using AWS directly vs. **end users of your web and mobile applications** (millions possible).
- **Long-term IAM credentials vs. STS credentials**: permanent access keys vs. **short-lived, limited-privilege** credentials with a session token and expiration.
- **AWS Managed Microsoft AD vs. AD Connector**: a **real Active Directory hosted in AWS** with locally managed users (can trust an on-premises AD) vs. a **proxy** with **no users in AWS** — authentication is forwarded to the on-premises AD.
- **AD Connector vs. Simple AD**: proxy to an existing on-premises AD vs. a **standalone, AD-compatible** directory in the cloud that **cannot** join an on-premises AD.
- **Microsoft AD (on-premises) vs. AWS Directory Services**: a Windows Server-based directory you run yourself vs. AWS-managed options to extend or replicate it in the cloud.
- **IAM Identity Center vs. IAM**: **one login across many accounts and applications**, managed centrally vs. per-account users, groups, roles and policies.

**You should be able to explain:**
- What STS does, what the returned credentials consist of, and three situations where it is used.
- Why application end users should be managed in Cognito rather than as IAM users.
- What Microsoft Active Directory is and what kinds of objects it stores.
- The three AWS Directory Services options and the key difference between them (where users live, on-premises join, MFA).
- What IAM Identity Center is, its former name, what it provides single sign-on to, and which identity providers it can use.
- Which identity service to choose for a given scenario: company staff using AWS, app end users, corporate Active Directory integration, temporary credentials, or one login across many accounts.
