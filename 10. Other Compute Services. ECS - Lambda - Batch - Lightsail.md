## Section: Other Compute Services: ECS, Lambda, Batch, Lightsail

### Lecture: What is Docker?

- **Docker** is a software development platform used to **deploy applications**.
- Traditionally, apps are installed directly on a machine (e.g., Linux) to run. With Docker, you package your app into a **container** — a special unit that can run on **any operating system** easily and behaves the **exact same way regardless of where it runs**.
- Benefits: no compatibility issues, predictable behavior, less work, easier to maintain/deploy; works with any programming language, OS, or technology; containers can be **scaled up and down in seconds**.
- Example: a single EC2 instance could run multiple containers side-by-side — e.g., one running Java code, one running Node.js code, one running a MySQL database, another running Java — all on the same instance.

**Docker Images and Repositories**
- You build **Docker images**, which define how a container will run.
- Images are stored in **Docker Repositories**:
  - **Docker Hub** — a public repository with base images for many technologies/OSes (e.g., Ubuntu, MySQL, Node.js, Java).
  - **Amazon ECR (Elastic Container Registry)** — a **private** Docker repository on AWS for storing your own private Docker images (covered in the next lecture).

**Docker vs. Virtual Machine (EC2)**
- Docker is a form of virtualization, but resources are **shared with the host** — meaning many containers can run on **one server**.
- **EC2 architecture**: Infrastructure (AWS) → Host OS → Hypervisor (not accessible to you) → each EC2 instance gets its own **Guest OS** + application. Each new instance requires its own full guest OS.
- **Docker architecture**: Infrastructure → Host OS (the EC2 instance) → **Docker Daemon** → many **lightweight containers** run on top of the Docker Daemon, without each one needing its own full OS/VM.
- This makes Docker very versatile, easy to scale, and easy to run.
- Note: you don't need deep Docker knowledge for the exam — this is background before covering ECS.

### Lecture: ECS, Fargate & ECR Overview

**ECS (Elastic Container Service)**
- Used to launch **Docker containers** on AWS.
- Requires you to **provision and maintain the infrastructure yourself** — you must create EC2 instances **in advance**.
- AWS handles starting/stopping the containers on those instances, and ECS integrates with an **Application Load Balancer** for web applications.
- Architecture: multiple EC2 instances (created by you in advance) run various containers managed by the ECS service; ECS intelligently decides which EC2 instance to place each new container on.
- > **Exam Tip**: "run Docker containers on AWS" → think **ECS**.

**Fargate**
- Also used to launch Docker containers on AWS, but **no infrastructure to provision** — no EC2 instances to create/manage.
- A **serverless** offering: AWS runs the containers you need based on the CPU/RAM specification you provide, without you knowing (or needing to know) exactly where.
- Much simpler to use than ECS since there are no EC2 instances to manage.

**ECR (Elastic Container Registry)**
- A **private Docker registry** on AWS, used to store the Docker images that ECS or Fargate will run.
- Example flow: store application images in ECR → Fargate looks at these images and creates/runs containers from them.

> **Exam Tip**: know the distinction between **ECS vs. Fargate vs. ECR** — that's the core exam-relevant knowledge here.

### Lecture: Amazon EKS

- **EKS (Elastic Kubernetes Service)** lets you launch and manage **Kubernetes clusters** on AWS.
- **Kubernetes** is an open-source system for managing, deploying, and scaling **containerized applications** (usually Docker containers, but can support other container types).
- Containers/pods in an EKS cluster can be hosted on **EC2 instances** or on **Fargate** (for a fully serverless setup).
- In an EKS cluster with EC2-based nodes, launching a Docker container on the Kubernetes cluster automatically launches **pods** onto the EC2 instances (EKS nodes).
- **Why use EKS**: launching and managing Kubernetes yourself is difficult — a managed service like EKS makes this much easier.
- **Why use Kubernetes at all**: it is **cloud-agnostic** — it can run on multiple clouds or even on-premises, so learning Kubernetes lets you launch containers anywhere (AWS, Azure, GCP, etc.), not just on AWS.
- > **Exam Tip**: the word **Kubernetes** → think **Amazon EKS**.

### Lecture: Serverless Introduction

- **Serverless** is a paradigm where developers **don't manage servers** — they just deploy code or functions.
- Serverless was pioneered as **Function as a Service (FaaS)** with **AWS Lambda** — you deploy your code, and each function is run independently by the Lambda service.
- Today, "serverless" broadly refers to anything **managed** where the user doesn't see/manage the underlying servers — this includes serverless databases, messaging, storage, etc.
- **Important clarification**: serverless does **not** mean there are no servers — there are servers behind the scenes, but as an end user, you don't manage, provision, or even see them.
- **Serverless services already used earlier in this course**:
  - **Amazon S3** — infinite scaling, no servers managed by the user; you just upload files.
  - **DynamoDB** — you create a table without provisioning a server; it auto-scales based on load.
  - **Fargate** — you send Docker containers, and Fargate automatically finds a way to run them (unlike ECS, which requires you to create EC2 instances).
- This section covers **Lambda**, the pioneer of serverless services, which allows you to run functions in the cloud.

### Lecture: Lambda Overview

- With **EC2**, you have a virtual server bounded by fixed memory/CPU, running continuously (even when unused); scaling requires an Auto Scaling Group, adding/removing servers over time (can be slow/complex).
- With **Lambda**, there are no servers — just **virtual functions**, limited in execution **time**, intended for **shorter executions**. They run **on demand**: when needed, they run; when not needed, they don't run, and you're **not billed**. Scaling is automated as part of the Lambda service.

**Benefits**
- **Pricing**: pay **per request** and **per compute time**.
- **Generous free tier**: **1 million** Lambda invocations and **400,000 GB-seconds** of compute time, per month.
- Integrated with the whole AWS suite of services.
- **Event-driven**: functions are invoked by AWS only when something happens (an event) — a reactive service (important for the exam).
- Supports many programming languages; easy monitoring via **CloudWatch**.
- Easy to allocate more resources per function — up to **10 GB of RAM**; increasing RAM also improves CPU and network performance.

**Supported languages**
- Node.js/JavaScript, Python, Java, C# (.NET Core), PowerShell, Ruby, and others via a **Custom Runtime API** (e.g., Rust, Golang).
- Containers can also be used on Lambda, but this requires implementing the **Lambda Runtime API**.
- > **Exam Tip**: to run **container images** (especially Docker images), **ECS or Fargate is always preferred over Lambda** on the exam, even though Lambda does support some level of customized Docker images. The most important languages to remember for Lambda are **Node.js and Python**.

**Common use case 1 — Serverless thumbnail creation**
- User uploads an image (e.g., a beach photo) to an S3 bucket → this triggers a **Lambda function** → the function creates a **thumbnail** (a smaller version) and pushes it back into S3 → it also pushes metadata about the thumbnail (image size, name, creation date, etc.) into **DynamoDB**.
- Fully **event-driven** and fully **serverless** — S3, Lambda, and DynamoDB all require no server provisioning, so this pattern scales very well.

**Common use case 2 — Serverless CRON job**
- A CRON job runs a script on a defined **schedule** (e.g., every hour, every day, every Monday) — normally run on a Linux machine.
- Since we're serverless (no EC2 instance to provision), use **CloudWatch Events / EventBridge** to trigger the Lambda function on the desired schedule (e.g., every hour) — no servers involved anywhere in this pattern.

**Pricing**
- **Per call**: first **1 million** invocations free, then **$0.20 per 1 million requests**.
- **Per duration**: free tier includes **400,000 GB-seconds** of compute time (e.g., 400,000 seconds at 1 GB RAM, or 3.2 million seconds at 128 MB RAM); after that, **$1 per 600,000 GB-seconds**.
- > **Exam Tip**: Lambda pricing is based on **calls (requests) and duration** — remember this for the exam.

### Lecture: Lambda Hands On

- Demo starts with an interactive illustration (AWS's `/lambda/begin` visual) showing:
  - A Lambda function can be written in several languages (.NET, Java, Node.js, Python, Ruby, or a custom runtime).
  - Lambda **responds to events** from many sources (e.g., streaming analytics, mobile/IoT device data, photos dropped into an S3 bucket) — reacting to them in real time.
  - Lambda **scales seamlessly**: as more event sources/invocations are added, more function instances run in parallel automatically, without managing any servers.
  - Costs stay free at first (thanks to the free tier), then accumulate as invocation volume increases.

**Creating a function**
- Use a blueprint: "Hello World," language **Python**, function name (e.g., "HelloWorld").
- **Execution role**: similar in concept to an EC2 instance role, but for Lambda — create a new role with basic Lambda permissions.
- The console auto-generates starter function code with a **handler** function that receives an event (e.g., `key1`, `key2`, `key3` values) and returns a value (e.g., `value1`).
- **Testing**: click "Test" with a sample JSON input — the function returns successfully with `value1` (from the test event's `key1`). Removing a key the code expects causes the function to **fail** (demonstrating basic error handling awareness).
- Test events can be **saved** (e.g., named "HelloWorld") for repeated testing.

**Monitoring**
- The **Monitor** tab shows invocation statistics via **CloudWatch** (takes a little time to populate).
- **View CloudWatch Logs** shows the actual execution logs, including successful runs and errors — useful for debugging functions directly from CloudWatch.

**Configuration**
- **General configuration**: memory allocation (small to large), ephemeral storage, timeout (how long to run before failing), and the execution role.
- The default execution role only grants permission to write to **CloudWatch Logs**; additional permissions (e.g., to access S3) would need to be added to that IAM role.
- **Permissions tab**: shows a summary of what the role allows (e.g., 3 CloudWatch Logs actions), viewable by resource or by action.
- **Triggers**: currently none configured in the demo, but many event sources are available (AWS services and partner events) — **Amazon S3** is called out as one of the main use cases (requires selecting a bucket and event types).

### Lecture: API Gateway Overview

- **Amazon API Gateway** is used to build a **serverless HTTP API**.
- Example use case: serverless technologies (Lambda + DynamoDB, for CRUD operations) need to be exposed to **external clients** — but a Lambda function isn't exposed as an API by itself.
- **API Gateway** exposes it: the client talks to API Gateway, which proxies the request to your Lambda function(s), which execute the necessary logic/transformations on your data.
- API Gateway is a **fully managed, serverless, fully scalable** service that lets developers easily **create, publish, maintain, monitor, and secure** APIs in the cloud.
- Supports **RESTful APIs** and **WebSocket APIs** (for real-time streaming of data).
- Supports security, user authentication, API throttling, API keys, and monitoring.
- > **Exam Tip**: "create a serverless API" → think **API Gateway** (paired with **Lambda**).

### Lecture: Batch Overview

- **AWS Batch** is a fully managed **batch processing** service, able to run **hundreds of thousands of batch computing jobs** on AWS efficiently.
- A **batch job** has a **start and an end** (as opposed to a continuous/streaming job that runs indefinitely) — e.g., a job that starts at 1:00 AM and finishes at 3:00 AM.
- Batch **dynamically launches EC2 instances or Spot Instances** to match the load needed to run your batch jobs — it provisions the right amount of compute/memory for your batch queue; you just submit/schedule jobs into the queue, and Batch handles the rest.
- Batch jobs are defined using a **Docker image**, and can be run on **ECS, EKS, or Fargate**.
- Because Batch automatically scales the right number of instances, it provides significant **cost optimization**, letting you focus on the batch jobs rather than infrastructure.

**Example workflow**
- Users submit images to an S3 bucket → this triggers a batch job → Batch automatically spins up an ECS cluster (of EC2 or Spot Instances) sized to the batch queue's load → these instances run Docker images that process the job (e.g., applying a filter to the image) → the result is pushed back to another S3 bucket.

**Batch vs. Lambda**
| | AWS Lambda | AWS Batch |
|---|---|---|
| Time limit | 15 minutes | No time limit (runs on EC2 instances) |
| Runtime | Limited set of supported languages | Any runtime, as long as packaged as a Docker image |
| Storage | Limited temporary disk space | Storage from the underlying EC2 instance (EBS volume or EC2 Instance Store) — much larger |
| Server model | Serverless | Not serverless — relies on actual (AWS-managed) EC2 instances, though auto-scaling is handled for you |

### Lecture: Lightsail Overview

- **Amazon Lightsail** is a bit of an "oddball" — a **standalone** service offering virtual servers, storage, databases, and networking **all in one place**, with **low and predictable pricing**.
- It's a **much simpler alternative** to using EC2, RDS, ELB, EBS, Route 53, etc., separately.
- Intended audience: people with **little to no cloud experience** who don't want to learn the intricacies of networking, storage, servers, etc. It's not the tool for learning "how AWS really works."
- Supports monitoring and notifications for Lightsail resources.

**Use cases**
- Deploying simple web applications (templates for LAMP stack, Nginx, MEAN, Node.js).
- Simple websites (WordPress, Magento, Plesk, Joomla, etc., deployable easily).
- Development and test environments.

**Limitations**
- Has a concept of **high availability**, but **no auto-scaling**, and **limited AWS integrations**.

> **Exam Tip**: Lightsail is the right answer only when the scenario describes someone with **no cloud experience** needing to get started quickly with **low, predictable pricing** and minimal configuration. Otherwise, Lightsail will almost always be the **wrong answer** (a distractor) on the exam.

### Lecture: Lightsail Hands On

- The Lightsail console looks completely different from the rest of AWS, since it has little integration with core AWS services.
- **Creating an instance**: choose a region/AZ (limited options compared to EC2); choose an **instance image** (like an AMI, but simplified) — e.g., a **blueprint** such as "OS Only" or an app like **WordPress** (launches a ready-to-go WordPress site with one click).
- Optional **launch script** (equivalent to EC2 User Data), and the option to change the SSH key pair — but these advanced options are mostly hidden by default.
- **Instance plans**: far less customization than EC2 — no EC2 instance types shown, just simple plans with a flat price (e.g., $3.50/month, first month free) showing RAM, vCPU, and disk space directly. Plans range up to $160/month (32 GB RAM, 8 vCPU, 640 GB SSD, 7 TB network transfer).
- Creating an instance shows **no security groups, no networking configuration, no EBS volumes** — deliberately simplified.
- **Creating a database**: similarly simplified compared to RDS — choose region/AZ, database type, credentials, standard vs. high-availability, and a price tier (e.g., first month free, then $15/month).
- **Networking and Storage** sections also exist (e.g., load balancers, extra storage/snapshots), all in a simplified form.
- **Connecting**: Lightsail provides a **browser-based SSH terminal** directly to the instance — no separate key/terminal setup needed.
- Visiting the instance's public IP shows the deployed WordPress site working out of the box.
- **Exam framing**: Lightsail is good to know about, but is rarely the "correct" service on the exam — more often it's a **distractor**. It is not something typically used in real AWS jobs (as a developer, SysOps practitioner, or solutions architect).
- **Cleanup**: delete the instance when done to avoid ongoing charges.

### Lecture: Other Compute - Summary

- **Docker**: a container technology for running applications.
- **ECS**: run Docker containers on EC2 instances that **you provision in advance**.
- **Fargate**: run Docker containers **without provisioning infrastructure** — serverless, since you don't manage EC2 instances.
- **ECR**: a private repository to store Docker images used by ECS/Fargate.
- **Batch**: run batch jobs on AWS across a set of managed EC2 instances — Batch actually runs on top of the **ECS** service under the hood.
- **Lightsail**: a simple, low/predictable-pricing service for basic applications and databases — most likely a **distractor** on the exam.
- **Lambda**: a serverless **Function as a Service**, with seamless scaling (from one invocation to thousands per second) and fully reactive/event-driven behavior.
  - Priced by: **runtime × memory provisioned**, and by the **number of invocations**.
  - Supports many programming languages; does **not** support arbitrary Docker images (use ECS/Fargate for that) unless the image implements the Lambda Container Runtime API.
  - Maximum invocation time: **15 minutes**.
  - Use cases: creating thumbnails for images uploaded to S3, running a serverless CRON job.
- **API Gateway**: exposes Lambda functions as HTTP APIs, with added capabilities like security, throttling, and API keys.

## Section: Other Compute Services — Key Takeaways

**Most important concepts**
- **Docker** packages applications into portable, lightweight **containers** that run consistently across environments, sharing the host's OS resources rather than requiring a full guest OS per instance.
- AWS offers multiple ways to run containers: **ECS** (you manage the underlying EC2 instances), **Fargate** (serverless — no instances to manage), and **EKS** (managed **Kubernetes**, works across clouds). **ECR** stores the container images used by these services.
- **Serverless** means the user never manages, provisions, or sees the underlying servers — even though servers exist behind the scenes. S3, DynamoDB, Fargate, and Lambda are all serverless examples covered in this course.
- **AWS Lambda** is the pioneering **Function as a Service** — short-lived, event-driven, on-demand functions, priced by invocation count and duration/memory.
- **API Gateway** exposes Lambda functions (or other backends) as HTTP/WebSocket APIs.
- **AWS Batch** runs long-running or resource-intensive **batch jobs** (Docker-based) across automatically managed EC2/Spot instances — not serverless, but still low-maintenance.
- **Lightsail** is a simplified, all-in-one AWS offering aimed at cloud beginners — mostly an exam distractor.

**How the concepts relate**
- **ECS, Fargate, and EKS** are all ways to *run* containers, differing mainly in **who manages the underlying compute** (you, for ECS and EKS-on-EC2; nobody/AWS, for Fargate and EKS-on-Fargate) and in **orchestration technology** (AWS-native ECS/Fargate vs. the open-source, cloud-agnostic Kubernetes via EKS).
- **ECR** is the common image storage layer that feeds into ECS, Fargate, and (indirectly) Batch, since Batch jobs are defined as Docker images and Batch itself runs on top of ECS.
- **Lambda** and **API Gateway** work together to build serverless HTTP APIs — Lambda provides the compute/logic, API Gateway provides the client-facing HTTP/WebSocket interface, security, and throttling.
- **Lambda vs. Batch** represent two ends of the "serverless vs. managed-but-not-serverless" spectrum for running code on a trigger: Lambda for short (≤15 min), lightweight, event-driven tasks; Batch for long-running, resource-heavy, Docker-based jobs with no time limit.
- **Lightsail** sits outside the rest of AWS's compute ecosystem entirely — it deliberately hides networking, security groups, and instance types to simplify things for beginners, at the cost of flexibility and integration with the rest of AWS.

**Key terminology to remember**
- Docker, container, Docker image, Docker Hub, Docker Daemon
- ECS (Elastic Container Service), Fargate, ECR (Elastic Container Registry)
- EKS (Elastic Kubernetes Service), Kubernetes, pods, nodes
- Serverless, Function as a Service (FaaS)
- Lambda: invocation, execution role, handler, event-driven, Custom Runtime API, Lambda Container Runtime API
- API Gateway: RESTful API, WebSocket API, throttling, API keys
- AWS Batch: batch job, job queue, compute environment
- Lightsail: blueprint, instance plan

**Key distinctions/comparisons**
- **ECS vs. Fargate**: you provision/manage EC2 instances in advance vs. fully serverless, no infrastructure management.
- **ECS/Fargate vs. EKS**: AWS-proprietary container orchestration vs. open-source, cloud-agnostic Kubernetes orchestration.
- **Lambda vs. Batch**: 15-minute max runtime, limited languages, serverless, small temp storage vs. no time limit, any Docker-packaged runtime, managed (not serverless) EC2/Spot instances, larger storage via EBS/Instance Store.
- **Lambda vs. ECS/Fargate for containers**: Lambda supports only specially-adapted container images (via the Lambda Container Runtime API); arbitrary Docker images should run on ECS or Fargate instead.
- **Lightsail vs. EC2/RDS/ELB/etc.**: drastically simplified, low/predictable pricing, minimal configuration and integrations vs. full-featured, highly configurable core AWS services.

**You should be able to explain:**
- What Docker is and how it differs from running full virtual machines (EC2 instances).
- The differences between ECS, Fargate, and ECR, and when each is used.
- What Amazon EKS is, what Kubernetes is, and why someone might choose Kubernetes over AWS-native orchestration.
- What "serverless" actually means, and which services covered so far in the course are serverless.
- How AWS Lambda works: its event-driven model, supported languages, pricing model (calls + duration), and common use cases (thumbnail generation, serverless CRON jobs).
- What API Gateway is used for and how it pairs with Lambda.
- What AWS Batch is, how a batch job differs from a continuous/streaming job, and how Batch compares to Lambda.
- What Amazon Lightsail is, its use cases, its limitations, and why it's typically an exam distractor rather than a correct answer.
