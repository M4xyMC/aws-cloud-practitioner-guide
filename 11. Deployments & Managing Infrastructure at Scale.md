## Section: Deployments & Managing Infrastructure at Scale

### Lecture: CloudFormation Overview

- **CloudFormation** is a **declarative** way to outline your AWS infrastructure — you describe *what* you want (most AWS resources are supported), and CloudFormation figures out *how* to create it.
- Example: declare "I want a security group, two EC2 instances using it, an S3 bucket, and a load balancer in front of them" → CloudFormation automatically creates all of it, in the right order, with the exact configuration specified.

**Benefits of CloudFormation**
- **Infrastructure as Code**: you never manually create resources — every change goes through **code review**, a great operational practice for the cloud.
- **Cost advantages**:
  - Every resource in a stack gets a shared tag, making cost tracking easier.
  - You can **estimate costs** directly from CloudFormation templates.
  - Enables **automated cost-saving strategies** — e.g., deleting a whole stack (and its resources) at 5:00 PM and recreating it at 8:00/9:00 AM, saving money by not running resources overnight.
- **Productivity**:
  - Ability to **destroy and recreate infrastructure on the fly**.
  - Can **generate diagrams** for your templates.
  - **Declarative programming**: you don't need to figure out the creation order (e.g., DynamoDB table vs. EC2 instance) — the template figures it out.
- **Don't reinvent the wheel**: leverage existing templates and documentation available online; CloudFormation supports **almost all AWS resources** covered in this course, and unsupported resources can be handled via a **custom resource**.

**Visualizing templates**
- The **Infrastructure Composer** service can visualize a CloudFormation template — e.g., for a WordPress stack, you can see all resources (ALB Listener, database security group, SQL database, various security groups, launch configuration, application balancer, etc.) **and** the relationships/links between them.

> **Exam Tip**: CloudFormation is used for **Infrastructure as Code**, and for **repeating an architecture** across different environments, regions, or AWS accounts.

### Lecture: CloudFormation Hands On

- Demo requires being in the **US East (N. Virginia) / us-east-1** region, since the demo template is region-specific (its AMI ID is scoped to that region).
- **Creating a stack**: Create Stack → "Use an existing template" → upload a template file (e.g., `0-just-EC2.yaml`), which defines a single EC2 instance resource ("My Instance") with properties: Availability Zone (`us-east-1a`), an AMI ID (region-scoped), and instance type `t2.micro`.
- Uploaded templates can be opened in **Application Composer** for a **visual representation** — showing the canvas with, e.g., a single EC2 instance component (double-clickable to inspect). The template can also be viewed as YAML or JSON.
- Continue stack creation: provide a stack name (e.g., "demoCloudFormation"), no parameters needed (none defined in this simple template), add a tag (e.g., `CFDemo`), skip permissions/other advanced options, then **Submit**.
- Result: CloudFormation creates the EC2 instance defined in the template — confirmed in the EC2 console (correct instance type and AMI). The instance also receives **automatic tags from CloudFormation** (stack name, logical ID, stack ID) plus the custom tag (`CFDemo`) specified during stack creation.

**Updating a stack**
- Update the stack, replacing the template with a more advanced one (e.g., `1-ec2-with-sg-eip.yaml`), which adds: a parameter for the security group description, an EC2 instance with **two security groups**, an **Elastic IP** attached to the instance, an SSH security group (port 22), and a server security group (port 80 open to everyone, port 22 open to a specific IP).
- Applying the update prompts for the new parameter (e.g., security group description = "demo description").
- **Change Sets**: CloudFormation previews exactly what will change before applying the update — e.g., new Elastic IP and security groups being **added**, and the EC2 instance being **modified** with a "**Replacement: true**" flag (meaning the old instance will be **deleted** and a **new one created** — important to know if the old instance held data).
- CloudFormation intelligently determines the correct order of operations: it creates the new security groups first, then updates/replaces the EC2 instance, then creates and attaches the Elastic IP — and finally cleans up (terminates) the old EC2 instance.
- The updated architecture (EC2 instance + Elastic IP + 2 security groups) can again be viewed visually in Application Composer.

**Cleanup**
- **Do not** manually delete resources created by CloudFormation — instead, either update the template, or click **Delete** on the stack, and CloudFormation will delete all stack resources **in the correct order** automatically.

### Lecture: CDK Overview

- **AWS CDK (Cloud Development Kit)**: lets you define cloud infrastructure using a **familiar programming language** (JavaScript, TypeScript, Python, Java, .NET) instead of writing raw CloudFormation YAML/JSON directly.
- Your CDK code is **compiled by the CDK CLI** into a standard CloudFormation template (JSON or YAML), which can then be deployed via CloudFormation.
- Benefit: you can write your **infrastructure code and application runtime code in the same language** — great for Lambda functions or Docker containers on ECS/EKS.

**Example workflow**
1. Write a CDK application (e.g., in Python) defining a Lambda function, a DynamoDB table, or other AWS services.
2. Run the CDK CLI to compile this into a **generated CloudFormation template**.
3. Apply/deploy that template via CloudFormation.

- Benefits of using a programming language over raw templates: **type safety**, more familiar constructs, faster development, code reuse, and support for programming constructs like `for` loops.
- Example given: CDK code (in JavaScript/TypeScript) defining a VPC, an ECS cluster, and an Application Load Balancer with a Fargate service — the CDK CLI compiles these into a deployable CloudFormation template.

### Lecture: Beanstalk Overview

- Typical web application architecture (**3-tier**): users → Load Balancer (across multiple AZs) → EC2 instances managed by an Auto Scaling Group → a database (e.g., RDS for relational data) and/or an in-memory cache (e.g., ElastiCache for session/cache data).
- This architecture can be built manually or via CloudFormation, but there's a developer-friendlier option: **Elastic Beanstalk**.
- As a developer, you often don't want to manage infrastructure (databases, load balancers, etc.) — you just want to **deploy code** and have it scale.

**Elastic Beanstalk**
- A **developer-centric view** of deploying an application on AWS — behind the scenes it still uses the same components (EC2 instances, Auto Scaling Group, Elastic Load Balancer, RDS, etc.), but presents them as **one unified, easy-to-understand view**, while still allowing configuration control of all components.
- Classified as **Platform as a Service (PaaS)** — you only worry about the code.
  - (Recap: IaaS = infrastructure as a service; PaaS = platform as a service, e.g., Beanstalk; SaaS = software as a service, other AWS services.)
- Using Beanstalk itself is **free** — you pay only for the underlying resources (instances, etc.) it provisions.
- As a **managed service**, Beanstalk handles: EC2 instance configuration and OS, the deployment strategy/execution, capacity provisioning via Auto Scaling Group, load balancing, and application health monitoring/responsiveness.
- **Your responsibility as a developer**: just the **application code**.

**Three Beanstalk architecture models**
| Model | Description | Best for |
|---|---|---|
| **Single instance** | One EC2 instance only | Development environments |
| **Load Balancer + ASG** | Load balancer in front of an Auto Scaling Group | Production / pre-production web applications |
| **ASG only (no load balancer)** | Standalone Auto Scaling Group | Non-web applications in production, e.g., background workers |

- **Supported platforms**: Go, Java, .NET, Node.js, PHP, Python, Ruby, Packer, Docker, Multi-Docker, Preconfigured Docker (not required to memorize the full list for the exam).

**Health monitoring**
- Beanstalk includes a full monitoring suite: a **health agent** runs on each EC2 instance and pushes metrics to **CloudWatch**; Beanstalk also checks application health and publishes health events, all viewable within the Beanstalk dashboard.

### Lecture: Beanstalk Hands On

- Creating an application: choose **Web server environment** (vs. **Worker environment**, used for processing tasks off a queue) → name the application (e.g., "My Application") → name the environment (e.g., "My Application Dev") → Beanstalk auto-generates a domain name for accessing the app.
- **Platform**: choose a managed platform (e.g., Node.js), using default/latest options.
- **Application code**: use a sample application (or your own code, if available).
- **Presets**: recommended configuration values for **Single instance** (free-tier eligible), **High availability** (with a load balancer), or **Custom configuration**. This demo uses **Single instance** for simplicity.
- **Service access**: create a **service role** for the Beanstalk environment itself, and an **EC2 instance profile** for Beanstalk compute — both auto-configured with recommended permissions (e.g., "AWS Elastic Beanstalk service role").
- Skipping optional networking/advanced steps, going straight to Review → Submit creates the environment.
- **Behind the scenes**: Beanstalk uses **CloudFormation** to provision everything — visible directly in the CloudFormation console (a stack is created with its own events log). Application Composer can visualize what's being created (launch configuration, security groups, Elastic IP, wait condition/handle, etc.).
- **Resulting resources** (verified in their respective consoles): a security group, an Elastic IP, an EC2 instance (e.g., `t3.micro`) with a public IP, and an **Auto Scaling Group** managing that single instance.
- Once launched successfully, visiting the generated domain name shows a default success page: "Congratulations, you are now running Elastic Beanstalk on this EC2 instance."

**Beanstalk console features**
- **Upload a new version**: deploy new application code, automatically rolled out to the environment's instances.
- **Health**: health check status for all instances.
- **Logs**: view application logs.
- **Monitoring**: metrics for the application/environment.
- **Alarms / Managed updates**: manage how/when Beanstalk updates the environment.
- **Configuration**: view/modify environment configuration settings.
- You can create **multiple environments** for the same application (e.g., "My Application Dev" and "My Application Prod") to represent different stages.

**Beanstalk vs. CloudFormation (reasoning)**
- Beanstalk is centered around **code and environments for that code**; CloudFormation is used to deploy stacks of **arbitrary infrastructure** of any kind.
- **Cleanup**: delete the application (Actions → Delete Application) to remove everything Beanstalk created (Auto Scaling Group, EC2 instance, Elastic IP, etc.) when finished.

### Lecture: CodeDeploy Overview

- **CodeDeploy** is another way to automatically deploy applications — but it's **independent** of Beanstalk or CloudFormation.
- Purpose: help upgrade an application from **version 1 to version 2** across many servers.
- Works with **both**:
  - **EC2 instances** — many instances can be upgraded from v1 to v2.
  - **On-premises servers** — same upgrade capability for servers outside AWS.
- Because it supports both EC2 and on-premises, CodeDeploy is a **hybrid service**.
- Requirements: you must **provision the servers ahead of time** yourself, and install/configure the **CodeDeploy agent** on them to assist with upgrades.
- Value proposition: enables a smooth transition from on-premises to AWS, since the **same deployment mechanism** works for both on-premises servers and EC2 instances.
- > Key exam takeaway: CodeDeploy automatically upgrades applications (EC2 or on-premises) from version 1 to version 2, from a single interface.

### Lecture: CodeCommit Overview

- Before pushing application code to servers, you need to store it — typically in a **code repository** backed by **Git**.
- A well-known public offering is **GitHub**; AWS's competing product is **CodeCommit**.
- **CodeCommit** is a way to store your code within AWS, in a **version-controlled Git-based repository**.
- Benefits: makes collaboration on code easy between developers; code changes are automatically **versioned** and can be **rolled back**.
- Being **fully managed**, CodeCommit is **scalable and highly available**; because it lives within your AWS account, it's **private, secure**, and integrated with other AWS services.

---

### Lecture: CodeBuild Overview

- **CodeBuild** allows you to **build your code in the cloud** — source code is compiled, tests are run, and the output is a ready-to-deploy **package/artifact**.
- **Workflow**: code stored in CodeCommit → CodeBuild retrieves it, runs a build script you define, builds the code → produces a ready-to-deploy artifact (which could then be deployed by, e.g., **CodeDeploy**).

**Why use CodeBuild**
- Fully managed and **serverless**.
- Continuously scalable, highly available, and secure.
- **Pay-as-you-go** pricing — you only pay for the time your code is actually being built.
- No servers to manage — AWS automatically builds your code every time you push an update to your repository (e.g., CodeCommit).

---

### Lecture: CodePipeline Overview

- **CodePipeline** connects services like CodeCommit and CodeBuild together, **orchestrating** the steps needed to automatically push code to production.
- Example pipeline: take code → build it → test it → provision servers → deploy the application onto them (can be more complex).
- Relates to **CI/CD** (**C**ontinuous **I**ntegration and **C**ontinuous **D**elivery): every time a developer pushes code to a repository, it's automatically built, tested, and deployed.

**Example pipeline flow**
- CodePipeline (orchestration layer) → pulls code from **CodeCommit** → builds it with **CodeBuild** → deploys it with **CodeDeploy** → potentially into an **Elastic Beanstalk** environment (just one possible configuration among many).

**Why use CodePipeline**
- Fully managed.
- Compatible with many services: CodeCommit, CodeBuild, CodeDeploy, Elastic Beanstalk, CloudFormation, GitHub, other third-party services, and custom plugins.
- Enables **fast delivery and rapid updates** — it is at the core of CI/CD on AWS.

> **Exam Tip**: "orchestration of a pipeline" → think **AWS CodePipeline**.

### Lecture: CodeArtifact Overview

- Software packages often depend on other packages — these are **code dependencies**, and managing them is called **artifact management**.
- Traditionally, teams set up their own artifact management infrastructure (e.g., on S3 or custom EC2 software) — complex to maintain.
- **AWS CodeArtifact** is a secure, scalable, and cost-effective managed **artifact management service**.
- Compatible with common dependency management tools: **Maven, Gradle, npm, yarn, twine, pip, NuGet** — these can talk directly to CodeArtifact to store/retrieve dependencies.
- Fits into the pipeline: after code is pushed to CodeCommit and built by CodeBuild, CodeBuild can retrieve dependencies directly from **CodeArtifact**.
- > **Exam Tip**: useful when a team needs an artifact management system / a place to store code dependencies.

### Lecture: Systems Manager (SSM) Overview

- **AWS Systems Manager (SSM)** helps manage a fleet of **EC2 instances and on-premises systems at scale** — like CodeDeploy, it's a **hybrid** AWS service (works across both AWS and on-premises).
- Provides operational insights about your infrastructure's state, plus access to a suite of 10+ products/features (not all required for the exam).

**Most important features for the exam**
- **Automated patching** of servers/instances for compliance.
- **Run Command**: execute a command across your entire fleet of servers directly from SSM.
- **SSM Parameter Store**: securely store configuration/parameters (covered in a later lecture).
- Works across **Linux, Windows, macOS, and Raspberry Pi**.

> **Exam Tip**: "patch your fleet of EC2 instances or on-premises servers" or "run a command consistently across all your servers" → think **SSM**.

**How SSM works**
- Requires installing the **SSM Agent** on each managed system (small background program). By default, it's pre-installed on Amazon Linux and some Ubuntu AMIs.
- The SSM Agent (installed on both EC2 instances and on-premises VMs) reports back to the SSM service in AWS — this dual EC2/on-premises support is what makes SSM a **hybrid service**.
- Once the agent is installed and reporting, SSM can run commands, patch instances, or configure them consistently across the fleet.
- If an instance can't be controlled by SSM, it's usually an agent issue.

### Lecture: SSM Session Manager

- **SSM Session Manager** lets you start a **secure shell** on EC2 instances (and on-premises servers) **without SSH access, a bastion host, or SSH keys**.
- Because SSH isn't needed, **port 22 can remain closed** on the instance — a security improvement.
- Supports **Linux, macOS, and Windows**; session logs can be sent to **Amazon S3 or CloudWatch Logs** for auditability.

**How it's set up (demo)**
1. Launch an EC2 instance (Amazon Linux 2, `t2.micro`) with **no key pair** and with **SSH traffic disabled** — the security group allows **no inbound traffic at all** (no HTTP, HTTPS, or SSH).
2. Attach an **IAM instance profile/role** to the instance that grants it permission to talk to the SSM service — created using the **"Amazon SSM Managed Instance Core"** policy (e.g., named "demo EC2 role for SSM"). This is required for the instance to be managed by SSM.
3. Once the instance boots, it appears in **Systems Manager → Fleet Manager** as a **managed node** (shows SSM Agent status, OS platform, agent version, etc.).
4. Use **Session Manager** to "Start a session" on the managed instance — this opens a secure shell, even though the security group has **zero inbound rules**.
5. Inside the shell, commands like `ping google.com` and `hostname` work normally — confirming a fully functional secure shell was established without SSH.

**Three ways to access an EC2 instance (recap across lectures)**
| Method | Requires port 22 open? | Requires SSH keys? |
|---|---|---|
| Traditional SSH (terminal) | Yes | Yes |
| EC2 Instance Connect | Yes (temporary key uploaded automatically) | No (temporary, auto-managed) |
| **SSM Session Manager** | **No** | **No** |

- Session history is logged and viewable afterward. Cleanup: terminate the session, then terminate the EC2 instance.

### Lecture: SSM Parameter Store

- **SSM Parameter Store** securely stores **configuration and secrets** on AWS — e.g., API keys, passwords, configuration values.
- **Serverless**: nothing to provision; scalable, durable, and easy to use.
- **Secure**: access to each parameter is controlled via **IAM**.
- **Version tracking**: configurations/parameters can evolve over time, with version history maintained.
- **Optional encryption**: values can be stored as plain text or encrypted (via **KMS**) as needed.
- Enables centrally managing configuration for many applications in one place.

**Hands-on demo**
- Create a parameter: name (e.g., "demo-parameter"), **tier** (Standard is free; Advanced is the paid tier), **type**:
  - **String** — a plain text value or list of values.
  - **SecureString** — encrypted value (used for sensitive data like API keys/passwords).
  - (Also supports a data type of Text or an AMI-type "image" value for EC2.)
- The demo uses a simple **String** (for simplicity) with a value like "my-configuration-parameter."
- Once created, the parameter can be retrieved, and if edited, **previous versions are tracked** for history.
- Cleanup: delete the parameter when done.

### Lecture: Deployment Summary

- **CloudFormation**: AWS-only, Infrastructure as Code, works with almost all AWS resource types; templates make infrastructure repeatable across regions/accounts.
- **Elastic Beanstalk**: AWS-only, Platform as a Service (PaaS), limited to certain languages or Docker; deploys code consistently onto a known architecture (e.g., load balancer + EC2 + RDS).
- **CodeDeploy**: deploys/upgrades applications onto servers — works on both EC2 and on-premises infrastructure, making it a **hybrid** service.
- **Systems Manager (SSM)**: also a hybrid service — patches, configures, and runs commands at scale across servers.

**Developer services**
- **CodeCommit**: stores code in a private, version-controlled Git repository (comes up on the exam).
- **CodeBuild**: builds and tests code in AWS, serverlessly.
- **CodeDeploy**: deploys code onto servers (grouped with both deployment and developer services since they overlap conceptually).
- **CodePipeline**: orchestrates a full pipeline — from code, to build, to test, to deployment, to provisioning.
- **CodeArtifact**: stores software packages and dependencies on AWS.
- **CDK**: defines cloud infrastructure using a programming language (JavaScript, TypeScript, Java, Python, etc.), compiled into a CloudFormation template.

## Section: Deployments & Managing Infrastructure at Scale — Key Takeaways

**Most important concepts**
- **CloudFormation** is the foundational Infrastructure-as-Code service in AWS — declarative, repeatable, and supporting nearly all AWS resources; the **CDK** lets you generate CloudFormation templates using a familiar programming language instead of YAML/JSON.
- **Elastic Beanstalk** is a developer-centric **PaaS** that abstracts away infrastructure management (EC2, ASG, ELB, RDS) so developers can focus purely on code, while still using CloudFormation under the hood.
- The **Code* suite** (CodeCommit, CodeBuild, CodeDeploy, CodePipeline, CodeArtifact) covers the full software delivery lifecycle: **store** code → **build/test** it → **deploy** it → **orchestrate** the whole pipeline → manage **dependencies**.
- **CodeDeploy** and **Systems Manager (SSM)** are both **hybrid services**, working across both EC2 instances and on-premises servers.
- **SSM** provides fleet-wide management (patching, running commands), **Session Manager** provides secure, keyless/SSH-less shell access, and **Parameter Store** provides secure, centralized configuration/secrets storage.

**How the concepts relate**
- **CDK** compiles into **CloudFormation** templates — they are two different authoring experiences for the same underlying Infrastructure-as-Code engine.
- **Elastic Beanstalk** itself uses **CloudFormation** behind the scenes to provision its EC2 instances, ASG, load balancer, and Elastic IP — Beanstalk is essentially a curated, developer-friendly wrapper around a CloudFormation-managed architecture.
- A typical CI/CD flow strings the Code* services together: code is stored in **CodeCommit**, built/tested by **CodeBuild** (which may pull dependencies from **CodeArtifact**), deployed by **CodeDeploy** (to EC2 or on-premises, or into a **Beanstalk** environment), all **orchestrated** by **CodePipeline**.
- **SSM Session Manager** relies on the broader **SSM** infrastructure (the SSM Agent + an IAM role granting the instance access to SSM) — this is the same underlying mechanism that also enables patching and running commands at scale.
- **SSM Parameter Store** complements the deployment pipeline by giving applications (and the pipeline itself) a secure, centralized place to retrieve configuration values and secrets.

**Key terminology to remember**
- CloudFormation: stack, template, declarative, change set, custom resource, Application/Infrastructure Composer
- CDK (Cloud Development Kit): CDK CLI, compiles to CloudFormation
- Elastic Beanstalk: PaaS, environment, single instance / load-balanced+ASG / ASG-only architecture models, health agent
- CodeDeploy: hybrid service, CodeDeploy agent, v1 → v2 upgrade
- CodeCommit: Git-based, version control, private repository
- CodeBuild: serverless build/test service, pay-as-you-go
- CodePipeline: orchestration, CI/CD (Continuous Integration / Continuous Delivery)
- CodeArtifact: artifact management, code dependencies (Maven, Gradle, npm, yarn, twine, pip, NuGet)
- Systems Manager (SSM): hybrid service, SSM Agent, Fleet Manager, managed node, automated patching, Run Command
- SSM Session Manager: secure shell without SSH/port 22/bastion host
- SSM Parameter Store: String vs. SecureString, KMS encryption, version tracking

**Key distinctions/comparisons**
- **CloudFormation vs. CDK**: raw declarative YAML/JSON templates vs. writing infrastructure in a familiar programming language that compiles down to CloudFormation.
- **CloudFormation vs. Elastic Beanstalk**: deploy *any* arbitrary infrastructure stack vs. a developer-centric, opinionated PaaS view centered on code and a known web-app architecture.
- **CodeDeploy vs. CodePipeline**: deploys/upgrades an application on existing servers vs. orchestrates the entire multi-step pipeline (build → test → deploy → provision).
- **CodeDeploy vs. Systems Manager**: both hybrid (EC2 + on-premises), but CodeDeploy is about deploying application version upgrades, while SSM is about fleet-wide operational management (patching, running commands, configuration).
- **Traditional SSH vs. EC2 Instance Connect vs. SSM Session Manager**: requires port 22 + SSH keys vs. requires port 22 + temporary auto-managed keys vs. requires **neither** port 22 nor SSH keys (IAM-role-based access instead).
- **SSM Parameter Store String vs. SecureString**: plain text configuration values vs. KMS-encrypted sensitive values (API keys, passwords).

**You should be able to explain:**
- What CloudFormation is, its core benefits, and what a "change set" shows during a stack update.
- What the CDK is and how it relates to CloudFormation.
- What Elastic Beanstalk is, why it's classified as PaaS, its three architecture models, and what a developer is (and isn't) responsible for.
- What CodeDeploy does and why it's considered a hybrid service.
- What CodeCommit, CodeBuild, CodePipeline, and CodeArtifact each do, and how they fit together into a CI/CD pipeline.
- What Systems Manager (SSM) is used for, and why it's also a hybrid service.
- How SSM Session Manager provides secure instance access without SSH, and why that's more secure than traditional SSH or EC2 Instance Connect.
- What the SSM Parameter Store is used for, and the difference between a String and a SecureString parameter.
