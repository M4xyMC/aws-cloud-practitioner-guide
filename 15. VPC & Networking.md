## Section: VPC & Networking

### Lecture: VPC Overview

- **VPC = Virtual Private Cloud.** This section is a **crash course** — VPC is genuinely complicated and must be known in depth only for the **AWS Certified Solutions Architect Associate** and **AWS Certified SysOps Administrator Associate** certifications.
- At **Cloud Practitioner** level you need a **high-level** understanding of what each component is used for. Topics covered:
  - VPC, Subnets
  - Internet Gateways, NAT Gateways
  - Security Groups, Network ACL (NACL)
  - VPC Flow Logs, VPC Peering, VPC Endpoints
  - Site-to-Site VPN, Direct Connect
  - Transit Gateway
- > **Exam Tip**: VPC represents **less than one or two questions** on the CCP exam, and the questions are **high-level**.
- The hands-on uses the **default VPC** that AWS creates for you — a VPC is **not** built from scratch in this course.

### Lecture: IP Addresses in AWS

**IPv4**
- The familiar protocol — **4.3 billion addresses**.
- **Public IPv4**: usable on the internet; makes the resource **publicly reachable from anywhere**.
  - An EC2 instance gets a public IPv4. **Stop the instance → the public IPv4 is released. Start it again → it gets a NEW public IP at launch.**
- **Private IPv4**: e.g., `192.168.1.1`. Usable **only on a private network** such as your internal AWS VPC — **not publicly accessible**.
  - The private IPv4 **stays the same for the entire EC2 instance lifetime**, even across stop/start.

**Elastic IP**
- A way to attach a **fixed public IPv4** to an EC2 instance, so stopping and starting the instance keeps the **same public IPv4** — desirable in some cases.
- Downside: if the instance stays stopped for a long time, the Elastic IP is being paid for and used for nothing.

**Pricing**
- **Every public IPv4 in AWS costs $0.005 per hour** — this includes both Elastic IPs and normal public IPv4 addresses.
- AWS is effectively pushing users toward **IPv6**.

**IPv6**
- Newer internet protocol version with **3.4 × 10^38 addresses** (38 zeros — far more addresses).
- **Every IPv6 address in AWS is public — there is no private range for IPv6.**
- **IPv6 addresses are free in AWS** — so to expose services on the internet with **no IP cost**, you must use IPv6.

| | Public IPv4 | Private IPv4 | Elastic IP | IPv6 |
|---|---|---|---|---|
| Reachable from internet | Yes | No | Yes | Yes (all IPv6 is public) |
| Changes on stop/start | Yes (released, new one on start) | No (fixed for instance lifetime) | No (fixed) | — |
| Cost | $0.005/hour | Free | $0.005/hour (even unused) | **Free** |

### Lecture: VPC, Subnet, Internet Gateway & NAT Gateways

**VPC**
- A **private network to deploy your resources in** (e.g., EC2 instances).
- A VPC is **linked to a specific region** — multiple regions means multiple VPCs.
- A VPC has a **CIDR range** — the range of IP addresses allowed inside the VPC.

**Subnets**
- A **subnet is a partition of the VPC's network** and is **associated with one Availability Zone**.
- **Public subnet** — accessible from the internet; the internet can reach it directly.
- **Private subnet** — **not** accessible from the internet.
- **Route Tables** define access to the internet and access between subnets so resources can communicate.

**What goes where**

| Public subnet | Private subnet |
|---|---|
| EC2 instances (as created earlier in the course), **load balancers** | **Databases** — they don't need internet access, so keeping them private is **more secure** |

- Example of a complete VPC: AWS Cloud → Region → VPC (with a CIDR range) → spans 2–3 Availability Zones. With 2 AZs each holding one public and one private subnet you get **1 VPC, 2 AZs, 4 subnets (2 public, 2 private)**, and EC2 instances can be launched in each.

**Internet Gateway (IGW)**
- Lets VPC instances **connect directly to the internet**.
- The IGW is attached to the **VPC**; the **public subnet has a route to the internet gateway**.
- **As soon as a subnet has a route to an internet gateway, it is a public subnet.**

**NAT Gateway / NAT Instance**
- Purpose: give instances in a **private subnet** access to the internet (e.g., to download OS updates or files) **while remaining private** — they stay unreachable from the internet.
- **NAT Gateway = managed by AWS**; **NAT Instance = self-managed**.
- Implementation: create the NAT Gateway/Instance **in the public subnet**, add a route from the **private subnet → NAT Gateway**, and from the **NAT Gateway → Internet Gateway**.

### Lecture: VPC, Subnet, Internet Gateway & NAT Gateways - Hands On

- The **default VPC** already exists with **1 VPC and 3 subnets**.
- **VPC details** show the **IPv4 CIDR** — e.g., `172.31.0.0/16`. Using a CIDR calculator (cidr.xyz) this yields **65,536 IPs** with a defined first and last usable IP; this tells you how many network interfaces you can have.
- You can **edit CIDRs** to add more IPv4 CIDRs later (if you need more addresses) as well as IPv6 CIDRs.
- **Subnets**: the three default subnets each have a different **/20** CIDR (`…0.0/20`, `…16.0/20`, `…32.0/20`), each with **4,096 IP addresses** — a smaller partition of the VPC range. AWS reports **4,091 available** addresses per subnet (some are reserved). **Each subnet corresponds to a different Availability Zone** (e.g., eu-west-1b, eu-west-1c).
- **Launching an EC2 instance**: under Network settings, the network is the default VPC and the **subnet is selectable** — choosing the eu-west-1a subnet launches the instance in that subnet. The instance's **private IPv4** (e.g., `172.31.28.181`) falls inside that subnet's CIDR, and the subnet's available-IP count drops by one. **The instance's private IP comes from the subnet it was launched in.**
- **Why the instance also got a public IPv4**: `Internet Gateways` shows an IGW created and **attached at the VPC level**. Each subnet's **route table** (the same one is associated with all three subnets) contains:
  - traffic to the **VPC's CIDR → local** (all private traffic remains private);
  - **all other destinations → the internet gateway** (e.g., resolving google.com gives an IP outside the CIDR, so it routes out through the IGW).
- Therefore **any instance launched in a subnet whose route table points to an internet gateway is a public instance** — which is why the demo instance received a public IPv4.
- The default VPC has **no private subnets**. To create one you would create a **route table without an internet gateway route** (covered only in more advanced courses). To give such private subnets internet access for updates you would create a **NAT gateway** and associate it with the right subnets.
- Cleanup: terminate the instance.

### Lecture: Security Groups & Network Access Control List (NACL)

**NACL (Network ACL) — first line of defense**
- A **firewall controlling traffic to and from the subnet** — it operates at the **subnet level**.
- Can define **ALLOW and DENY** rules.
- Rules **can only reference IP addresses**.
- Filters traffic in and out of the subnet **before it reaches the EC2 instance**.

**Security Groups — second line of defense**
- A **firewall controlling traffic to and from an EC2 instance** — operates at the **EC2 instance / ENI level**.
- Can define **ALLOW rules only**.
- Rules can reference **IP addresses or other security groups**.

**Security Group vs. NACL**

| | Security Group | Network ACL |
|---|---|---|
| Level | **Instance level** | **Subnet level** |
| Rules | **ALLOW only** | **ALLOW and DENY** |
| Return traffic | Automatically allowed regardless of rules → **stateful** | Must be **explicitly allowed** by rules → **stateless** |
| Rules can reference | IP addresses **and other security groups** | **IP addresses only** |

- > **Exam Tip**: the first three differences above (level, allow/deny, stateful vs. stateless) are what you really need for the exam; the simplest version is **NACL = subnet level, Security Group = EC2 instance level**.

**Hands-on notes**
- Security groups can be viewed from either the **VPC console** (`Security → Security groups`) or the EC2 console; inbound rules are visible per group.
- **Network ACLs**: a VPC has a **default NACL**, associated at the **subnet level** (in the default VPC it is associated with all three subnets).
- The **default NACL rules**:
  - **Inbound rule 100** — allow **all traffic, all ports, all protocols, from anywhere**.
  - **Last rule `*`** — **DENY** (the `*` means "last"). Since rule 100 matches first, everything is allowed in.
  - **Outbound** is the same: all traffic allowed out.
- Rules are evaluated by **rule number order**. Example: adding rule 200 to allow only **HTTPS (443) from anywhere** and removing rule 100 would allow only HTTPS in and **deny everything else** — a firewall applied at the subnet level.

### Lecture: VPC Flow Logs & VPC Peering

**VPC Flow Logs**
- A **log of all the IP traffic going through your interfaces**.
- Three levels: **VPC Flow Log**, **Subnet Flow Log**, **Elastic Network Interface (ENI) Flow Log** — e.g., to see traffic in and out of your EC2 instances.
- Use: **monitor and troubleshoot connectivity issues** — a subnet that cannot reach the internet, a subnet that cannot reach another subnet, or the internet not being able to access a subnet. The flow log captures these so you can find the root cause.
- Captures traffic information not only for EC2 but also for **Elastic Load Balancers, ElastiCache, RDS, Aurora**, etc.
- **Destinations**: **Amazon S3**, **CloudWatch Logs**, **Amazon Data Firehose**.
- Flow log creation options (hands-on): name, **filter** (all traffic / accepted only / rejected only), **maximum aggregation interval** (1 minute or 10 minutes), **destination** (CloudWatch Logs — requires a log group and an IAM role; S3 bucket; Kinesis Firehose, in the same or a different account), and the **log record format**.
- **Log record fields** include: version, account ID, interface ID, source address, destination address, source port, destination port, protocol, packets, bytes, start, end, action, log status.

**VPC Peering**
- Connects **two VPCs privately using the AWS network**, making them behave **as if they were part of the same network**.
- **Requirement: the IP address (CIDR) ranges must NOT overlap.** If they overlap, the peering connection cannot be established.
- **VPC peering is NOT transitive.** If A↔B and A↔C are peered, **B and C still cannot talk** — you must create a separate peering connection between B and C.
- Hands-on: `Peering connections → Create peering connection` → name it, select the **local (requester) VPC**, then select the **accepter VPC** — which can be in **your account or another account**, and in **the same region or another region** (e.g., Africa/Cape Town, entering the VPC ID). Once **accepted**, the two networks behave as one.

### Lecture: VPC Endpoints - Interface & Gateway (S3 & DynamoDB)

- All AWS services used so far are **public** — you connect to them over the **public internet**.
- A **VPC Endpoint** lets you connect to AWS services over the **private AWS network** instead.
- **Benefits**: **better security** (traffic never traverses the public internet) and **less latency** (no going through network hubs).

**Two endpoint types**

| Type | Used for |
|---|---|
| **Gateway Endpoint** | **Amazon S3 and DynamoDB ONLY** |
| **Interface Endpoint** | **Any other AWS service** (e.g., CloudWatch — to push a custom metric from a private EC2 instance) |

- Example: an EC2 instance in a **private subnet** reaches **S3/DynamoDB** through a **gateway endpoint**, privately.
- > **Exam Tip**: pretty much **every** AWS service has an **interface endpoint**, but **only S3 and DynamoDB also have a gateway endpoint**. (In the console, S3 and DynamoDB show both an interface and a gateway option.)
- Hands-on: `PrivateLink and Lattice → Endpoints → Create endpoint` → choose **AWS services** → pick the service from the list → specify the **VPC and subnets** (classic interface endpoint configuration).

### Lecture: PrivateLink

- **AWS PrivateLink** is part of the **VPC Endpoint Services** family.
- **Problem it solves**: a service owner (your own service, or a **vendor on the AWS Marketplace** running the service in their own account/VPC) wants to expose that service **privately** to potentially **thousands of customer VPCs**. **VPC peering doesn't scale and isn't very secure** for this.
- **PrivateLink** connects a service running in one VPC to **other VPCs directly and privately**.
- It requires **no VPC peering, no internet gateway, no NAT, no route tables** — everything is on the private network.

**How it is set up**
- **Service provider side**: create a **Network Load Balancer (NLB)** to expose the service.
- **Consumer side**: create an **Elastic Network Interface (ENI)**.
- Establish the **PrivateLink** between the two — you get private access to their NLB and therefore to their service.
- **No traffic goes over the public internet**; all communication stays private.
- For each new customer, the third party simply creates **another PrivateLink** — easy to manage and **far more scalable**.

### Lecture: Direct Connect & Site-to-Site VPN

This is **hybrid cloud** — connecting your **on-premises data center** to your VPC. **Two options:**

**1. Site-to-Site VPN**
- An **encrypted connection** between your on-premises data center and your VPC that goes **over the public internet**.
- **Very quick to set up — about 5 minutes.**
- Because it goes over the public internet: **limited bandwidth** and potential **security concerns** (though the traffic is encrypted).
- **Required components (remember for the exam):**
  - **Customer Gateway (CGW)** — on the on-premises side.
  - **Virtual Private Gateway (VGW)** — on the AWS side.
  - Once both are provisioned, connect them with the Site-to-Site VPN.

**2. Direct Connect (DX)**
- Establishes a **physical, dedicated connection** between your on-premises data center and AWS.
- The connection is **private, secure and fast**, and goes over a **private network**.
- **More expensive** (a physical connection through a Direct Connect partner) and takes **at least a month** to establish.
- **More private, faster and more reliable.**

| | Site-to-Site VPN | Direct Connect |
|---|---|---|
| Network path | **Public internet** (encrypted) | **Private** physical connection |
| Setup time | **~5 minutes** | **At least a month** |
| Cost | Cheaper | **More expensive** |
| Bandwidth / reliability | Limited bandwidth | Faster, more reliable |

- > **Exam Tip**: the choice between Site-to-Site VPN and Direct Connect depends on **two factors** — (1) does it need to be **fully private** or not, and (2) does it need to be established **fast** or not.

### Lecture: Client VPN

- **AWS Client VPN** connects **your own computer** privately into your **AWS VPC**, using an **OpenVPN** connection.
- The connection goes **over the public internet**.
- **Use case**: EC2 instances deployed in a **private VPC/subnet** can then be accessed using their **private IP** — as if your computer were inside the VPC network. Without a VPN this is difficult.
- **Bonus**: if the VPC also has a **Site-to-Site VPN** to your on-premises data center, your computer can privately reach your **on-premises servers** too.

---

### Lecture: Transit Gateway Overview

- With peering connections, Site-to-Site VPN and Direct Connect, a serious AWS network topology becomes **very complicated** (a mesh of connections and routes).
- **Transit Gateway** solves this with a **hub-and-spoke (star) topology**: peering-style connectivity between **thousands of VPCs and your on-premises systems** through **one central gateway**.
- The Transit Gateway sits in the middle; connected to it are **Amazon VPCs**, **Direct Connect gateways**, and **VPN connections**.
- You no longer need to peer VPCs with one another or maintain separate connections and routes to Direct Connect and Site-to-Site VPN — it's all handled by the single gateway.
- > **Exam Tip**: when the exam describes connecting **hundreds or thousands of VPCs together plus on-premises infrastructure**, the answer is **Transit Gateway**.

### Lecture: VPC & Networking Summary

- **VPC** = Virtual Private Cloud; contains **subnets**. A **subnet** is tied to a specific **Availability Zone** and is a **network partition** of the VPC.
- **Internet Gateway** — internet access at the VPC level.
- **NAT Gateway (managed) / NAT Instances (self-managed)** — internet access for **private subnets/instances**.
- **NACL (Network ACL)** — **stateless** firewall with **subnet-level** inbound and outbound rules.
- **Security Groups** — **stateful** rules operating at the **EC2 instance / ENI level**.
- **VPC Peering** — connect two VPCs with **non-overlapping IP ranges**; **non-transitive** (A↔B and B↔C does **not** let A talk to C).
- **Elastic IPs** — fixed public IPv4 with an **ongoing cost even when not in use**.
- **VPC Endpoints** — **private access to any AWS service** from within your VPC.
- **PrivateLink** — private connection to a **third-party service in a third-party VPC**.
- **VPC Flow Logs** — access to your **network traffic logs**.
- **Site-to-Site VPN** — connect your **on-premises data center** to AWS **over the public internet**.
- **Client VPN** — connect your **own personal computer** into your VPC via **OpenVPN**.
- **Direct Connect** — a **very private, direct** connection between AWS and your data center.
- **Transit Gateway** — connect **everything** together: thousands of VPCs, on-premises networks, Site-to-Site VPN, Direct Connect, etc.
- The exam asks you to **choose the correct VPC sub-service** for a scenario.

## Section: VPC & Networking — Key Takeaways

**Most important concepts**
- A **VPC** is a **regional**, private network with a **CIDR range**; it is divided into **subnets**, each tied to **one Availability Zone**. Public vs. private is determined by **routing**, not by a setting: a subnet whose **route table points to an Internet Gateway** is public.
- **Internet Gateway** = inbound/outbound internet for public subnets. **NAT Gateway (AWS-managed) / NAT Instance (self-managed)** = **outbound-only** internet for private subnets, placed **in a public subnet**.
- **Two layers of network security**: **NACL** (subnet level, ALLOW+DENY, **stateless**, IPs only) and **Security Groups** (instance/ENI level, ALLOW only, **stateful**, can reference other security groups).
- **IP addressing**: public IPv4 changes on stop/start, private IPv4 is stable for the instance's life, **Elastic IP** pins a public IPv4, **all public IPv4 costs $0.005/hour**, and **IPv6 in AWS is always public and free**.
- **Connecting VPCs**: **VPC Peering** (two VPCs, non-overlapping CIDRs, **non-transitive**) vs. **Transit Gateway** (hub-and-spoke for thousands of VPCs + VPN + Direct Connect).
- **Reaching AWS services privately**: **VPC Endpoints** — **Gateway** endpoints for **S3 and DynamoDB only**, **Interface** endpoints for everything else. **PrivateLink** does the same for **third-party/vendor services** (provider exposes an **NLB**, consumer creates an **ENI**).
- **Hybrid connectivity**: **Site-to-Site VPN** (encrypted, over the public internet, ~5 minutes, needs **CGW** + **VGW**) vs. **Direct Connect** (physical, private, fast, expensive, ~1 month). **Client VPN** connects an individual computer into the VPC over OpenVPN.
- **VPC Flow Logs** capture IP traffic at the VPC/subnet/ENI level for **connectivity troubleshooting**, and ship to **S3, CloudWatch Logs, or Amazon Data Firehose**.

**How the concepts relate**
- Subnet "publicness" is a chain: **route table → Internet Gateway**. Private subnets get outbound internet by chaining **private subnet → NAT Gateway (in a public subnet) → Internet Gateway**.
- NACL and Security Groups are **layered**: traffic hits the **NACL at the subnet boundary first**, then the **Security Group at the instance**.
- **VPC Endpoints, PrivateLink, VPN, Direct Connect and Transit Gateway** all exist to answer the same underlying question — *how do I reach something without using the public internet, and at what scale?* Endpoints/PrivateLink handle **service access**, VPN/Direct Connect handle **on-premises connectivity**, and Transit Gateway **consolidates all of them** when the topology grows.
- **Flow Logs** are the diagnostic layer for everything above — when a subnet, peering connection or endpoint doesn't work, flow logs show whether traffic was accepted or rejected. They feed the same destinations used by CloudWatch/monitoring services.
- Architecture pattern that ties it together: **load balancers in public subnets, databases in private subnets**, private subnets reaching the internet only through NAT, and reaching S3/DynamoDB through a gateway endpoint.

**Key terminology to remember**
- VPC, CIDR range, subnet, public subnet vs. private subnet, route table, Availability Zone
- Internet Gateway (IGW), NAT Gateway (managed) vs. NAT Instance (self-managed)
- Security Group (stateful, instance/ENI level), NACL / Network ACL (stateless, subnet level), rule numbers, `*` deny rule
- Public IPv4, private IPv4, Elastic IP, IPv6, $0.005 per hour per public IPv4
- VPC Peering (non-overlapping CIDRs, non-transitive), Transit Gateway (hub-and-spoke)
- VPC Endpoint — Gateway endpoint (S3, DynamoDB) vs. Interface endpoint (all other services)
- AWS PrivateLink, Network Load Balancer (provider side), Elastic Network Interface (consumer side)
- Site-to-Site VPN, Customer Gateway (CGW), Virtual Private Gateway (VGW), Direct Connect (DX), Client VPN (OpenVPN)
- VPC Flow Logs (VPC / subnet / ENI level), aggregation interval, accepted vs. rejected traffic

**Key distinctions/comparisons**
- **Security Group vs. NACL**: instance level vs. subnet level; ALLOW only vs. ALLOW + DENY; **stateful** vs. **stateless**; can reference security groups vs. IP addresses only.
- **Public subnet vs. private subnet**: has a route to an Internet Gateway (internet-reachable, hosts load balancers/public EC2) vs. no such route (not internet-reachable, hosts databases, more secure).
- **Internet Gateway vs. NAT Gateway**: two-way internet connectivity for public subnets vs. outbound-only internet access for private subnets while keeping them private.
- **NAT Gateway vs. NAT Instance**: managed by AWS vs. self-managed.
- **Public IPv4 vs. private IPv4**: internet-reachable and released on stop/start vs. private-network-only and fixed for the instance lifetime.
- **IPv4 vs. IPv6 in AWS**: paid, has a private range vs. **free, entirely public** (no private range).
- **Gateway endpoint vs. Interface endpoint**: S3 and DynamoDB only vs. essentially every other AWS service.
- **VPC Endpoint vs. PrivateLink**: private access to **AWS** services vs. private access to a **third-party/vendor** service in another VPC.
- **VPC Peering vs. Transit Gateway**: one-to-one, non-transitive links between two VPCs vs. a single hub connecting thousands of VPCs, VPNs and Direct Connect gateways.
- **Site-to-Site VPN vs. Direct Connect**: public internet, encrypted, minutes to set up, cheaper, limited bandwidth vs. dedicated physical private link, faster/more reliable, expensive, a month to provision.
- **Site-to-Site VPN vs. Client VPN**: connects an entire **corporate data center** to a VPC vs. connects an **individual computer** to a VPC.

**You should be able to explain:**
- What a VPC is, that it is regional, and how subnets relate to Availability Zones and to the VPC's CIDR range.
- Exactly what makes a subnet public or private, and how a private subnet can still download OS updates from the internet.
- The differences between Security Groups and NACLs, including stateful vs. stateless behavior and where each one applies.
- How AWS IP addressing behaves — what changes on stop/start, what an Elastic IP buys you, what public IPv4 costs, and why IPv6 is free.
- When to use VPC Peering versus Transit Gateway, and why peering is not transitive.
- The difference between Gateway and Interface VPC endpoints, and which services support gateway endpoints.
- What PrivateLink is for and the components each side must create (NLB vs. ENI).
- How to choose between Site-to-Site VPN and Direct Connect, and which two gateways a Site-to-Site VPN requires.
- What Client VPN enables, and what VPC Flow Logs are used for and where they can be sent.
