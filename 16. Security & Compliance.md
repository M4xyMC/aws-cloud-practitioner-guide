## Section: Security & Compliance

### Lecture: Shared Responsibility Model: Reminders & Examples

**The split**
- **AWS is responsible for the security OF the cloud** — all the infrastructure it provides: **hardware, software, facilities, networking**, plus the **managed services** themselves (S3, DynamoDB, RDS, …). This infrastructure runs every AWS service you use.
- **The customer is responsible for security IN the cloud** — how you use the service that AWS provides.

**Customer responsibilities (EC2 example)**
- **Operating system management** — including **patching and updates** of the OS.
- **Firewall configuration** — Network ACLs and Security Groups.
- Ensuring the instance has the correct IAM configuration (via an **IAM instance role**).
- **Encrypting application data** according to your compliance requirements.

**Shared controls**
- **Patch management** — AWS patches for managed services; e.g. **RDS: AWS does the patching**, **EC2: you patch your own OS**.
- **Configuration management.**
- **Awareness and training** — AWS trains its employees to use its facilities and adhere to its security guidelines; **you** must train your employees to use the cloud correctly (taking this course is one such way).

**Detailed example — Amazon RDS**

| AWS responsibility | Customer responsibility |
|---|---|
| Manage the **underlying EC2 instance**, disable SSH access | Configure **ports, IP, security group inbound rules** on the DB security group |
| **Automate database patching** | **In-database user creation** and their permissions |
| **Automate OS patching** | Decide whether the DB has **public access** or not |
| Audit the underlying instance and disk to guarantee it keeps functioning | Configure the DB via **parameter groups** (e.g., force only encrypted connections) |
| | **Enable encryption of data** in the database |

**Detailed example — Amazon S3**

| AWS responsibility | Customer responsibility |
|---|---|
| Guarantee **unlimited storage** | Configure the **bucket** as you want it |
| Guarantee **encryption when you enable it** | Ensure the **bucket policy** adheres to your standards |
| Ensure **separation of data between all AWS customers** | Use **IAM users and roles** accordingly |
| Ensure **AWS employees cannot access your data** | **Enable encryption** and choose the encryption scheme that works for you |

**The official AWS diagram**
- **Customer — "security IN the cloud"**: your **data**, applications, platform, **identity and access management**, operating system, **network and firewall configuration**, **client-side data encryption**, **server-side encryption**, **network traffic protection**.
- **AWS — "security OF the cloud"**: its **software** (the services), making sure **compute, storage, database, networking** work correctly, its **hardware and global infrastructure** (**Regions, Availability Zones, Edge Locations**).
- > **Exam Tip**: the shared responsibility model comes up in **at least two to three exam questions** — knowing what is your responsibility versus AWS's is very important.

### Lecture: DDoS Protection: WAF & Shield

**What a DDoS attack is**
- **DDoS = Distributed Denial-of-Service.** An attacker launches multiple **master servers**, which launch large numbers of **bots**; all bots send requests to your application server. The server is not built to handle that volume, becomes **overwhelmed and unresponsive**, so **normal users cannot reach the application** — the application is effectively down.

**How to protect yourself on AWS**
- **AWS Shield Standard** — enabled for **all customers at no additional cost**; protects websites and applications against DDoS.
- **AWS Shield Advanced** — premium **24/7** DDoS protection.
- **AWS WAF** — filters specific requests based on **rules** (Web Application Firewall).
- **CloudFront and Route 53** — protection using the **global edge network**; combined with Shield this provides **attack mitigation at the edge locations**.
- **Be ready to scale** during an attack — leverage **Auto Scaling**.

**Sample reference architecture for DDoS protection**
- Users → **Route 53** DNS (protected by Shield, so DNS is safe) → **CloudFront** distribution (content cached at the edge, also protected by Shield) → **WAF** (to filter and protect from attack) → **Load balancer** in the public subnet (scales for you) → **EC2 instances in an Auto Scaling Group** (scale to higher demand).

**AWS Shield — the two components**

| | Shield Standard | Shield Advanced |
|---|---|---|
| Cost | **Free**, activated for **every** AWS customer | **Optional**, about **$3,000 per month per organization** |
| Protects against | Common DDoS attacks: **SYN/UDP reflection floods, reflection attacks, other layer 3 / layer 4 attacks** | **More sophisticated attacks** on **EC2, ELB, CloudFront, Global Accelerator, Route 53** |
| Extra | — | Access to the **DDoS response team** when needed; **AWS covers any fees incurred during an attack** |

- > **Exam Tip**: the **free** version is activated **by default for every customer**; **Shield Advanced** is something **you enable yourself** (~$3,000/month) and is what gives you the **response team** and higher level of defense.

**AWS WAF (Web Application Firewall)**
- Protects **web applications from common web exploits** at **layer 7**.
- **Layer 7 = HTTP** (whereas layer 4 = TCP). Because it is layer 7, WAF can only be deployed on **HTTP-friendly devices**: **Application Load Balancer**, **API Gateway** (not covered — out of exam scope), **CloudFront**.
- You define a **Web ACL (Web Access Control List)** whose rules can filter on:
  - **IP addresses**
  - **HTTP headers**, **body**, specific **strings**
  - Protection against common attacks — **SQL injection**, **Cross-Site Scripting (XSS)**
  - **Size constraints** (requests not too big)
  - **Geo-match** — block certain countries
  - **Rate-based rules** — count occurrences of events (e.g., a user cannot make more than 5 requests per second) → helps protect against **DDoS**
- Remember: DDoS protection is the **combination of Shield + WAF + CloudFront + Route 53**.

### Lecture: AWS Network Firewall

- If the exam asks how to **protect your entire VPC**, the answer is **AWS Network Firewall**.
- Protects the **whole VPC at once**, with **layer 3 to layer 7 protection in any direction**.
- Can inspect **any traffic**: outbound to the internet, inbound from the internet, to and from **Direct Connect** and **Site-to-Site VPN**, and **peered VPCs**.
- A **much better protection mechanism than Network ACLs**, which only operate at the **subnet level** — Network Firewall operates at the **VPC level**.

### Lecture: AWS Firewall Manager

- Manages **all security rules in all accounts of an AWS Organization** from a **central place**.
- > **Exam Tip**: if a question asks about **managing VPC Security Groups across multiple accounts in an organization**, the answer is **AWS Firewall Manager**.
- Besides **VPC Security Groups**, it can manage **WAF rules**, **AWS Shield Advanced** rules, **AWS Network Firewall** and other services — but Security Groups is the most exam-relevant.
- Rules applied in Firewall Manager are applied to **all current AND future accounts**, and to **all resources as they are created** — guaranteeing the rules are enforced across all accounts at all times.

### Lecture: Penetration Testing

- **Penetration testing** = attacking your own infrastructure to test your security.
- AWS customers may perform security assessments and penetration testing against **their own infrastructure without prior approval** for **eight services**:
  1. Amazon **EC2** instances, **NAT Gateways** and **Elastic Load Balancers**
  2. Amazon **RDS**
  3. Amazon **CloudFront**
  4. Amazon **Aurora**
  5. Amazon **API Gateways**
  6. AWS **Lambda** and **Lambda@Edge** functions
  7. Amazon **Lightsail** resources
  8. Amazon **Elastic Beanstalk** environments
- The list can grow over time; the exact list is not something you will be tested on in detail.

**Prohibited activities (require contacting the AWS security team)**
- **DNS zone walking** via Amazon Route 53 Hosted Zones
- **DoS / DDoS**, or **simulated DoS / simulated DDoS**
- **Port flooding**
- **Protocol flooding**
- **Request flooding**
- Any other event → **contact the AWS security team** for approval.
- > **Exam Tip**: yes, you can pen test in the cloud — but anything that **looks like an actual attack** (DDoS, DNS zone walking, port flooding) is **not authorized**, because to AWS it would look like an attack on their infrastructure.

### Lecture: Encryption with KMS & CloudHSM

**Two types of encryption**

| | Encryption at rest | Encryption in transit |
|---|---|---|
| Meaning | Data is **stored or archived on a physical device** — it is not moving | Encryption **while data is being moved** from one place to another (in motion, on the network) |
| Examples | Hard drive/disk, **RDS** instance, **S3 Glacier Deep Archive**, any **S3 bucket**, **EFS** network drive | On-premises data center → AWS; EC2 instance ↔ DynamoDB table; EFS → Amazon S3 |

- The two use **different techniques**; ideally you **encrypt data in both states** so it is protected at all times.
- Encryption relies on **encryption keys**: someone without the key cannot decrypt or read the data even if they obtain it. (How the keys work internally is **not needed at CCP level**.)

**KMS (Key Management Service)**
- The **central encryption service** in AWS — anytime you hear "encryption" for a service, it is most likely KMS.
- **AWS manages the keys for you; you don't have access to the keys** — you define **who can access** them.
- **Opt-in encryption** (you choose to enable it): **EBS volumes**, **S3 buckets** (server-side encryption of objects), **Redshift** databases, **RDS**, **EFS**.
- **Automatic encryption, always on**: **CloudTrail Logs**, **S3 Glacier**, **Storage Gateway**.

**CloudHSM**
- With **KMS, AWS manages the encryption software**. With **CloudHSM, AWS provisions the encryption hardware, and YOU manage the keys yourself**.
- The dedicated hardware is an **HSM (Hardware Security Module)** module.
- The HSM device is **tamper resistant** — if someone tries to tamper with it, it fails — and has **FIPS 140-2 Level 3 compliance** (a security standard).
- How it works: **AWS manages the hardware**; you use the **CloudHSM service with CloudHSM clients** to manage the keys. The connection between your client and CloudHSM is **encrypted** so keys can be managed securely.

**Types of KMS keys**

| Key type | Who creates/manages/uses it | Notes |
|---|---|---|
| **Customer-managed key** | **Created, managed and used by you (the customer)** | Can **enable/disable** a key, define a **key rotation policy** (e.g., new key every year while the old key is preserved), and **bring your own key** |
| **AWS-managed key** | **Created, managed and used on your behalf by AWS** | Used when an AWS service has AWS-managed encryption; named **`aws/s3`, `aws/ebs`**, … — anything starting with **`aws/`** is AWS-managed |
| **AWS-owned key** | A collection of keys a **service owns and manages** for use across multiple accounts | AWS can use them to protect resources in your account; **you cannot view these keys** |
| **CloudHSM keys (custom key store)** | Keys generated from **your own CloudHSM hardware device** | All cryptographic operations are performed **within the CloudHSM cluster** |

### Lecture: Encryption with KMS & CloudHSM Hands On

- The **KMS console** shows the three key groupings: **customer managed keys** (you create them; they **cost money**), **AWS managed keys** (created for AWS services), and the **custom key store** (requires a **CloudHSM cluster** that you create, own and manage — CloudHSM is expensive, so it isn't demoed).
- **Using an AWS-managed key (opt-in encryption)**: `EC2 → Volumes → Create volume` (1 GiB) → tick **Encrypt this volume** → the only available master key is the **default AWS-managed key for the service** (`aws/ebs`), because no customer key exists yet → create → the volume is now **encrypted** and protected against decryption attempts.
- **Encryption that is on by default**: opening a CloudTrail trail shows encryption as "disabled" in the CloudTrail console, but inspecting the delivered log file in the **S3 bucket** shows the property **encryption: AES256** — **CloudTrail encrypts all files no matter what**.
- **Creating a customer-managed key** (costs ~$1/month):
  - Key type: **symmetric** or **asymmetric** (demo uses symmetric).
  - **Key material origin**: generated by **KMS**, **external** (import your own key), or from a **custom key store (CloudHSM)** — in which case all encryption/decryption happens in CloudHSM.
  - Give it an **alias** (e.g., `demokey`), optionally define **key administrators** and **key users**, review the **key policy**, finish. The key is then **enabled**.
  - **Key rotation**: tick the box so the key **changes every year** for enhanced security.
- Creating a second encrypted EBS volume now offers a choice of master key: the **default AWS-managed key** or **your own `demokey`** — both volumes end up encrypted, but with **different keys**.
- Cleanup: delete the volumes; a created key can be **disabled** and then **scheduled for deletion**.

### Lecture: AWS Certificate Manager (ACM) Overview

- **ACM (AWS Certificate Manager)** easily **provisions, manages and deploys SSL/TLS certificates**.
- Purpose of the certificates: provide **in-flight encryption** for your websites by exposing an **HTTPS endpoint**.
- **Example**: an Application Load Balancer talks to an Auto Scaling Group of EC2 instances over **HTTP** in the backend, but you want end users to reach **HTTPS**. ACM, once connected to your domain, provisions and maintains the TLS certificate; the certificate is **loaded onto the load balancer**, which can then serve **HTTPS** to clients — giving **in-flight encryption over the public web**.
- Features:
  - Supports **both public and private** TLS certificates.
  - **Free of charge for public TLS certificates.**
  - **Automatic TLS certificate renewal.**
  - **Integrations** that load the certificates onto: **Elastic Load Balancers**, **CloudFront distributions**, **APIs on API Gateway**.
- > **Exam Tip**: any question about which service performs **in-flight encryption** / generates these **certificates** → **ACM**.

### Lecture: Secrets Manager Overview

- **AWS Secrets Manager** stores **secrets**.
- Key capabilities:
  - **Force rotation of secrets** every X days (e.g., change passwords every 90 days).
  - **Automate the generation** of secrets **using Lambda**.
  - **Integration with Amazon RDS** — create RDS passwords automatically.
  - Secrets are **encrypted using KMS automatically**.
- > **Exam Tip**: anytime you see a **secret to be managed in RDS and rotated**, think **Secrets Manager**.
- **Paid service**: **$0.40 per secret per month** plus **per-API-call** charges; a **30-day free trial** is available.
- **Hands-on flow**: `Store a new secret` → secret type can be **credentials for a database** (RDS, Redshift, another database) or **another type of secret** → for an RDS database you specify **username, password**, the **encryption key**, and the **RDS database to link** → or store an arbitrary key/value secret (e.g., `password` / `MYSECRETPASSWORD`) → choose the encryption key → **name** the secret → configure **automatic rotation** (e.g., every 30 days) and select the **Lambda function** that will rotate it (must be created in advance) → review; the console also shows **sample code** to retrieve the secret in your applications.

### Lecture: Artifact Overview

- **AWS Artifact** is **not really a service** — it is presented as one in the console.
- It is a **portal giving customers on-demand access to compliance reports and AWS agreements**. It is a **global service**.
- **Artifact Reports** — downloadable **security and compliance documents from third-party auditors**, such as:
  - AWS **ISO certifications**
  - **PCI** (Payment Card Industry) reports
  - **SOC** reports
  - (Downloading requires **accepting an NDA**; dozens of reports are available.)
- **Artifact Agreements** — review, accept and **track the status of AWS agreements**, such as the **BAA** (Business Associate Addendum) or **HIPAA** (Health Insurance Portability and Accountability Act), for an **individual account or your organization**.
- Purpose: support **internal audit** capabilities in your company and **compliance needs** — proving you are compliant by using the AWS cloud.

### Lecture: GuardDuty Overview

- **Amazon GuardDuty** performs **intelligent threat discovery** to protect your AWS accounts.
- **How**: **machine learning algorithms**, **anomaly detection**, and **third-party data**.
- **One click to enable**, **30-day trial**, and **no software to install**.

**Input data sources (always analyzed)**
- **CloudTrail event logs** — unusual API calls, unauthorized deployments. Covers **management events** (e.g., create VPC subnet) and **data events** (e.g., S3 `GetObject`, `ListObjects`, `DeleteObject`).
- **VPC Flow Logs** — unusual internet traffic, unusual IP addresses.
- **DNS logs** — EC2 instances sending **encoded data inside DNS queries**, which would indicate they are compromised.

**Optional features (extra input sources you can enable)**
- **EKS audit logs** and runtime monitoring
- **RDS and Aurora login events**
- **EBS** volumes
- **Lambda** network activity
- **S3 data events**
- (More features are added over time.)

**Findings and automation**
- You can set up **EventBridge rules** to be notified automatically when there are findings; the rules can target anything EventBridge supports — e.g., **Lambda** or **SNS topics**.
- > **Exam Tip**: GuardDuty is very good at protecting against **cryptocurrency attacks** — there is a **dedicated finding** for it.
- Flow: input data → **GuardDuty** → **findings** → event in **Amazon EventBridge** → rules trigger **automations (Lambda)** or **notifications (SNS)**.

### Lecture: Inspector Overview

- **Amazon Inspector** runs **automated security assessments** on exactly **three** things:

| Target | What Inspector does |
|---|---|
| **EC2 instances** (running) | Uses the **Systems Manager agent**; analyzes **unintended network accessibility** and the **running operating system for known vulnerabilities** — **continuously** |
| **Container images pushed to Amazon ECR** (e.g., Docker images) | Analyzed **against known vulnerabilities as they are pushed** |
| **Lambda functions** | Analyzed for **software vulnerabilities in the function code and package dependencies**, **as the functions are deployed** |

- **Reporting**: findings go to **AWS Security Hub** and events are sent to **Amazon EventBridge** — giving one central view of vulnerabilities plus the ability to automate.
- **What it evaluates**:
  - A **database of vulnerabilities (CVE)** for **package vulnerabilities** on EC2, ECR and Lambda.
  - **Network reachability** on Amazon EC2.
  - **Continuous scanning of the infrastructure, only when needed** — and if the **CVE database is updated**, Inspector **automatically runs again** so all infrastructure is retested.
- Each run assigns a **risk score** to all vulnerabilities for **prioritization**.

### Lecture: Config Overview

- **AWS Config** helps with **auditing and recording compliance of your resources** by **recording configurations and their changes over time**. (Manual configuration changes previously left no list of what changed — Config provides it.)
- Configuration data can be stored in **Amazon S3**, to later be analyzed by **Athena** or recovered.
- **Questions Config (and Config Rules) can answer**:
  - Is there **unrestricted SSH access** to my security groups?
  - Do **buckets have any public access**?
  - Has my **ALB configuration changed** over time?
- **Alerts** via **SNS notifications** for any infrastructure changes.
- **Config is a per-region service**, but you can create multiple Config configurations and **aggregate results across all accounts and all regions**.

**What you can view**
- **Compliance of a resource over time** — e.g., a security group that was **non-compliant** and became **compliant** after changes.
- **Configuration of a resource over time** — how the security group's configuration changed.
- **Who made the changes** — based on **CloudTrail** (if CloudTrail is enabled in the account).

**Hands-on notes**
- **Config is not free** — enabling it incurs charges.
- Setup: choose resource types to record (demo records **all resources in the region including global resources**) → Config **creates an S3 bucket** to store configurations → optionally choose an **SNS topic** for change notifications → a **Config service-linked role** is created.
- **Config Rules** are then selected, e.g. `restricted-ssh`, `rds-instance-public-access-check`, `s3-bucket-logging-enabled`, `s3-account-level-public-access-blocks`. The demo enables **`restricted-ssh`** to check security group compliance.
- Config then shows an **inventory of all resources** (e.g., 5 security groups, 3 subnets, 1 internet gateway…) and which are **non-compliant** — here **3 of 5 security groups** fail `restricted-ssh` because SSH (port 22) is open to everyone.
- **Remediation demo**: delete the offending inbound SSH rule in the EC2 security group → either wait, or use **Actions → Re-evaluate** on the rule to force re-evaluation → the resource turns **compliant (green)**.
- **Resource Timeline** shows the **configuration timeline** and the **compliance timeline**; opening a change shows the rule that was deleted, and the **CloudTrail integration** shows that the **root user removed that security group ingress rule**, with a link to view the event in CloudTrail.
- Value: ensures that all resources created by employees in your company are **compliant with the security rules you decided**.

### Lecture: Macie Overview

- **Amazon Macie** is a **fully managed data security and data privacy service** that uses **machine learning and pattern matching** to **discover and protect sensitive data** in AWS.
- Specifically alerts you about **sensitive data such as PII (Personally Identifiable Information)**.
- Flow: **PII data in your S3 buckets** → analyzed by **Macie**, which **discovers and classifies** what is PII → notifies you through **EventBridge** → integrations to an **SNS topic**, **Lambda functions**, etc.
- Macie **only** finds sensitive data **in your S3 buckets** — that is the one thing it does.
- **One click to enable**; you just specify the S3 buckets to analyze.

### Lecture: Security Hub Overview

- **AWS Security Hub** is a **central security tool** to **manage security across several AWS accounts** and **automate security checks**.
- Provides an **integrated dashboard** showing current **security and compliance status** so you can take action quickly.
- **Aggregates alerts** across many AWS services and partner tools: **Config, GuardDuty, Inspector, Macie, IAM Access Analyzer, AWS Systems Manager, AWS Firewall Manager, AWS Health, AWS Partner Solutions** (and more over time).
- > **Exam Tip / requirement**: for Security Hub to work you **must first enable AWS Config**.
- Flow: Security Hub covers **multiple accounts**, gathers findings from Macie, GuardDuty, Inspector, Firewall Manager, IAM Access Analyzer, Systems Manager, Config and Health → **automatic checks** produce **Security Hub findings** in the dashboard → any security issue also generates an **event in EventBridge** → to **investigate the source** of the issues, use **Amazon Detective**.
- **Pricing**: **per check** (first 1,000 checks at one rate, then tiered) and **per ingestion event** (first 10,000 events free, then per finding). A **30-day trial** is available.
- Enabling it requires: enable **Config** first → choose the **security standards** to adhere to (three options) → configure **integrations** based on enabled services → **Enable Security Hub**.

### Lecture: Amazon Detective Overview

- Services like **GuardDuty, Macie and Security Hub** identify **potential security issues or findings** — but you still need to find **how they happened** and get to the **root cause**.
- Deeper analysis to isolate a root cause is **long and complicated**: analyzing data from different places and linking it together. With security, you want the root cause **as quickly as possible** because there may be a **security hole** in your architecture.
- **Amazon Detective** **analyzes, investigates and quickly identifies the root cause** of security issues or suspicious activities, using **machine learning and graphs** in the backend.
- It **automatically collects and processes events** from:
  - **VPC Flow Logs**
  - **CloudTrail** trails
  - **GuardDuty**
- It builds a **unified view** and provides **visualizations with details and context** so you can reach the root cause.

### Lecture: AWS Abuse

- If you suspect AWS resources (IPs, EC2 instances, …) are being used for **abusive or illegal purposes**, you can **report it to AWS**.
- **Abusive and prohibited behaviors**:
  - **Spam** — undesired emails from AWS-owned IPs; websites/forums spammed by AWS resources
  - **Port scanning** from AWS
  - **DDoS attack**
  - **Intrusion attempts** — someone trying to log into your resources
  - **Hosting objectionable or copyrighted content** (illegal content hosted on AWS)
  - **Distributing malware**
- **What to do**: contact the **AWS Abuse Team** — via the **online form** or by email at **abuse@amazonaws.com**.

### Lecture: Root User Privileges

- The **root user** is the **account owner** — the first user used when the account is created — and has **complete access to all AWS services and resources**.
- The root user can perform some actions that **even the most privileged created user cannot**.
- **Best practice**: **lock away the root account** and its **access keys / secret access keys**. **Do not use the root account for everyday tasks, not even administrative tasks** — create a specific **admin user** instead.

**Actions only the root user can perform**
- **Change account settings** — account name, email address, root user password, root user access keys **(important)**
- View certain **tax invoices**
- **Close your AWS account** **(important)**
- **Restore IAM user permissions**
- **Change or cancel your AWS Support plan** **(important)**
- **Register as a seller in the Reserved Instance Marketplace** **(important)**
  - *Example*: you bought a 3-year Reserved Instance but after 2 years no longer need it — you can **sell it back** on the marketplace, and only the root user can register as a seller.
- Configure an **Amazon S3 bucket to enable MFA** (MFA Delete)
- **Edit or delete an S3 bucket policy** that includes an **invalid VPC ID or VPC endpoint ID**
- **Sign up for AWS GovCloud**
- > **Exam Tip**: the exam may ask **which actions are only possible for the root user** — remember these, especially the four highlighted in the section summary (change account settings, close the account, change/cancel the support plan, register as a seller in the Reserved Instance Marketplace).

### Lecture: IAM Access Analyzer

- **IAM Access Analyzer** is a feature **inside the IAM console** used to find **which resources are shared externally**.
- **Resource types analyzed**: **S3 buckets, IAM Roles, KMS Keys, Lambda Functions and Layers, SQS Queues, Secrets Manager Secrets**.
- **Why it matters**: these resources can have **resource policies** or be **shared with other accounts**; people **forget** about the sharing, which becomes a **security risk** because resources may be accessible by external sources.
- **Zone of trust** — you define it as **your AWS account** or your **entire AWS Organization**. Anything **outside the zone of trust** that has access to those resources is reported as a **finding**.
- *Example*: an S3 bucket can be shared with a specific **role, user, account, external client by IP, or VPC endpoint**. If the zone of trust is your account, then the **role, user and VPC endpoint inside your account are fine**, while the **external account and external client are flagged as findings**.

**Hands-on notes**
- `IAM → Access Analyzer → Create analyzer` → name it, set the **zone of trust** (e.g., the current account) → **free to enable** → creates a **service-linked role** so the analyzer can inspect resources on your behalf.
- Example findings: **one SQS queue and two S3 buckets shared with all principals** (one via a bucket policy), with **read** or **write** access noted.
- Investigating a finding: open the resource (e.g., an SQS queue's **access policy** allowing **anyone** to send a message, including external accounts) → decide whether the access is **intended** (then **archive** the finding) or **not intended** (then **fix the policy** and **rescan**).
- After removing the offending policy and rescanning, the finding's status becomes **resolved**.
- **Archive rules**: create rules that **automatically archive** certain findings (e.g., intentionally public S3 buckets) based on criteria you define.

## Section: Security & Compliance — Key Takeaways

**Most important concepts**
- The **Shared Responsibility Model** splits **security OF the cloud (AWS: hardware, global infrastructure, managed services)** from **security IN the cloud (customer: data, OS patching on EC2, firewall config, IAM, encryption enablement)**, with **shared controls** for patch management, configuration management, and awareness/training.
- **DDoS defense is a stack**, not one service: **Shield Standard (free, automatic, layer 3/4)** + **Shield Advanced (~$3,000/month, 24/7 response team, cost protection)** + **WAF (layer 7 filtering, Web ACL)** + **CloudFront/Route 53 (edge mitigation)** + **Auto Scaling (absorb load)**.
- **Firewall scope ladder**: **Security Group** (instance/ENI) → **NACL** (subnet) → **AWS Network Firewall** (whole **VPC**, layers 3–7, any direction) → **AWS Firewall Manager** (rules across **all accounts in an Organization**, current and future).
- **Encryption**: at rest vs. in transit; **KMS** (AWS manages the software/keys, you control access) vs. **CloudHSM** (AWS provides tamper-resistant **FIPS 140-2 Level 3** hardware, **you** manage the keys). Four key types: **customer-managed, AWS-managed (`aws/…`), AWS-owned, CloudHSM/custom key store**.
- **ACM** provides free public **SSL/TLS certificates** with **auto-renewal** for **in-flight encryption**, loaded onto ELB, CloudFront and API Gateway. **Secrets Manager** stores secrets, **rotates them automatically via Lambda**, integrates with **RDS**, and encrypts with **KMS**.
- **Detection services** each have one clear specialty: **GuardDuty** (threat detection from CloudTrail/VPC Flow/DNS logs, ML-based, dedicated **cryptocurrency** finding), **Inspector** (vulnerability/CVE scanning of **EC2, ECR images, Lambda** only), **Macie** (**PII in S3**), **Config** (configuration recording and **compliance rules**), **Security Hub** (central aggregation, **requires Config**), **Detective** (root-cause analysis from VPC Flow Logs, CloudTrail and GuardDuty), **IAM Access Analyzer** (resources shared **outside your zone of trust**).
- **Penetration testing** is allowed **without approval on 8 service categories**, but anything resembling a real attack (**DoS/DDoS, DNS zone walking, port/protocol/request flooding**) is **prohibited** without contacting AWS.
- **Artifact** is the **compliance document portal** (ISO, PCI, SOC reports; BAA/HIPAA agreements).
- **Root user** has a small set of **exclusive actions** and must otherwise be locked away.
- **AWS Abuse Team** (form or **abuse@amazonaws.com**) handles reports of spam, port scanning, DDoS, intrusion attempts, illegal content and malware distribution.

**How the concepts relate**
- Almost every security service **feeds EventBridge**, which turns findings into **automation (Lambda)** or **notifications (SNS)** — the same monitoring plumbing from the Cloud Monitoring section.
- The detection services form a **pipeline**: **GuardDuty / Inspector / Macie / Config / IAM Access Analyzer / Firewall Manager / Health** produce findings → **Security Hub** aggregates them into one dashboard (and **needs Config enabled**) → **Detective** investigates a chosen finding down to its root cause using **CloudTrail + VPC Flow Logs + GuardDuty** data.
- **Config + CloudTrail** together answer both "what changed and is it compliant?" (Config) and "who changed it?" (CloudTrail) — the Config console links directly to the CloudTrail event.
- **KMS underpins other services**: EBS/S3/RDS/Redshift/EFS opt-in encryption, and Secrets Manager's automatic secret encryption.
- **DDoS protection reuses the global infrastructure** services (Route 53, CloudFront) and the scaling services (ELB, Auto Scaling) from earlier sections, wrapped with Shield and WAF.

**Key distinctions/comparisons**
- **AWS responsibility vs. customer responsibility**: infrastructure, hardware, managed-service internals, employee training vs. data, OS patching (EC2), firewall rules, IAM, enabling encryption, your own employee training.
- **RDS vs. EC2 patching**: AWS patches the DB and OS for RDS; **you** patch the OS for EC2 — the classic "shared control" example.
- **Shield Standard vs. Shield Advanced**: free and automatic for everyone, common layer 3/4 attacks vs. paid (~$3,000/month/org), sophisticated attacks on EC2/ELB/CloudFront/Global Accelerator/Route 53, 24/7 response team, AWS absorbs attack-related fees.
- **Shield vs. WAF**: DDoS (layer 3/4 volumetric) protection vs. layer 7 web exploit filtering with rule-based Web ACLs.
- **NACL vs. AWS Network Firewall**: subnet-level, IP-based, stateless vs. VPC-wide, layer 3–7, all directions including Direct Connect/VPN/peered VPCs.
- **Network Firewall vs. Firewall Manager**: protects one VPC's traffic vs. centrally manages security rules across all accounts in an Organization.
- **KMS vs. CloudHSM**: AWS manages the encryption **software and keys** (you manage access) vs. AWS provides the **hardware**, you manage the **keys** entirely.
- **Opt-in encryption vs. always-on encryption**: EBS, S3, Redshift, RDS, EFS (you enable) vs. CloudTrail Logs, S3 Glacier, Storage Gateway (automatic).
- **ACM vs. Secrets Manager vs. KMS**: TLS certificates for in-flight encryption vs. application secrets with rotation vs. the encryption keys themselves.
- **GuardDuty vs. Inspector vs. Macie**: threat/anomaly detection from logs vs. vulnerability (CVE) scanning of EC2/ECR/Lambda vs. sensitive-data (PII) discovery in S3.
- **Config vs. CloudTrail**: resource **configuration** and compliance over time vs. the **API calls** and who made them.
- **Security Hub vs. Detective**: aggregate and centralize findings from many services/accounts vs. drill into one finding to establish its root cause.
- **IAM Access Analyzer vs. Config**: detects **external sharing** outside a zone of trust vs. checks resource configuration against **compliance rules**.
- **Allowed vs. prohibited penetration testing**: assessments against the 8 permitted service categories vs. DoS/DDoS, DNS zone walking, and flooding attacks (need AWS approval).
- **Root user vs. admin IAM user**: exclusive account-level actions (close account, change support plan, RI Marketplace seller, account settings) vs. everything else, which should be done by a created admin user.
