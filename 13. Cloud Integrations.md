## Section: Cloud Integrations

### Lecture: Cloud Integrations Overview

- When multiple applications need to communicate, there are **two patterns**:

**1. Synchronous communication**
- One application talks **directly** to another.
- Example: a "buying" service needs to talk directly to a "shipping" service to have a purchased item shipped.

**2. Asynchronous / event-based communication**
- Applications communicate indirectly, via a **queue** (or similar mechanism) in between.
- Example: the buying service places an order into a **queue**; the shipping service reads orders from that queue. The buying and shipping services are **not** directly integrated — they are **decoupled**, since a queue sits between them.

**Why decoupling matters**
- Synchronous communication can be problematic under a **sudden spike in traffic** — e.g., needing to encode 1,000 videos instead of the usual 10 could overwhelm the downstream service, causing failures.
- **Decoupling** applications (via SQS, SNS, or Kinesis) lets each side **scale independently**, which is much more resilient.

**Services covered in this section**
- **SQS** — a queue model.
- **SNS** — a pub/sub (publish/subscribe) model.
- **Kinesis** — real-time data streaming.
- This section focuses primarily on **SQS** and **SNS**.

### Lecture: SQS Overview

- **Amazon SQS (Simple Queue Service)** is a way to **decouple applications** using a **queue**.

**How it works**
- **Producers** send messages into the queue (can be one or multiple producers).
- **Consumers** poll the queue (request messages from it) — can be one or multiple consumers.
- When multiple consumers poll, they **share the work** — each consumer gets different messages.
- Once a consumer finishes processing a message, it **deletes** it from the queue.
- Producers and consumers are fully **decoupled** and can process at different speeds.

**Key facts**
- SQS is **AWS's oldest offering** — over 10 years old, one of the first AWS services.
- **Fully managed / serverless** — no servers to provision.
- > **Exam Tip**: whenever you see "**decouple**," think **SQS**.
- Scales seamlessly — from one message per second to **tens of thousands of messages per second**.
- **Message retention**: default is **4 days**, maximum **14 days** — messages must be processed within that window.
- **No limit** to how many messages can be in a queue.
- Once read and processed, consumers must **delete** messages — they're then gone.
- **Low latency**: less than **10 milliseconds** to publish and subscribe.
- Consumers **share the work** of reading messages, allowing horizontal scaling.

**Example architecture using SQS**
- Web servers (behind a load balancer, in an Auto Scaling Group) receive user requests → instead of processing video requests directly, they insert messages into an **SQS queue** → a separate **video processing layer** (its own Auto Scaling Group of EC2 instances) reads from the queue and processes the videos.
- The two Auto Scaling Groups (web tier and video-processing tier) can scale **independently** of each other — this is decoupling in practice.
- Scaling can be based on **queue depth** (how many messages are waiting) — this gives the best user experience and the best cost efficiency.

**FIFO Queues**
- **FIFO = First In, First Out** — governs the **ordering** of messages.
- With a **normal (Standard) SQS queue**, consumers may read messages in a different order than they were sent.
- With an **SQS FIFO queue**, messages are guaranteed to be read in the **exact order** they were sent (e.g., 1, 2, 3, 4 in → 1, 2, 3, 4 out).
- This distinction (Standard vs. FIFO) is a feature to remember for the exam.

### Lecture: SQS Hands On

- SQS is described as a **high-throughput, system-to-system messaging service**.
- **Creating a queue**: choose between **Standard** or **FIFO** queue type (the difference is noted as beyond the Cloud Practitioner exam's scope) → this demo uses **Standard**, named "demo-sqs." Configuration and access policy settings are left at their defaults.
- **Queue details view**: shows the queue type, name, encryption status, and (under "More") stats like number of messages available, messages in flight, and delayed messages.
- **Sending messages**: use "Send and receive messages" → type a message body (e.g., "Hello World") → Send. The message becomes available; sending a second message (e.g., "Another Hello") increases "Messages available" to 2.
- **Receiving messages**: click "Poll for messages" to retrieve them — both messages appear and can be opened to view their body (confirming the exact text sent) and any attributes.
- **Processing**: after handling a message (which an application would implement in code), you **delete** it from the queue — "Messages available" returns to 0.
- **Cleanup**: delete the queue by typing "delete" to confirm — no cost either way, but good practice.

### Lecture: Kinesis Overview

- > **Exam Tip**: whenever you see **Kinesis**, think **real-time big data streaming**.
- **Amazon Kinesis Data Streams** is used to **collect, process, and analyze real-time streaming data** at any scale — this is the main Kinesis concept needed for the Cloud Practitioner exam.
- **Amazon Data Firehose** is a related service used to load streaming data **from** Kinesis Data Streams **into target destinations**, such as Amazon S3, Amazon Redshift, OpenSearch, etc.

**Example flow**
- **Fast data sources** (data created in real time — e.g., website clicks, IoT device data, application server metrics/logs) → sent into **Kinesis Data Streams** → analyzed → optionally, **Amazon Data Firehose** delivers the data into destinations like S3 or Redshift.

- The instructor notes this level of detail (Kinesis = a service to stream data) is sufficient for the Cloud Practitioner exam.

### Lecture: SNS Overview

- **SNS (Simple Notification Service)** is a second way to decouple applications, used when you need to **send one message to many receivers**.

**Why not use direct integration?**
- Sending a message via **direct integration** to multiple services (e.g., a buying service directly notifying an email service, a fraud service, a shipping service, and an SQS queue) requires writing **four separate direct integrations** — complex to build and maintain.

**Pub/Sub model with SNS**
- Instead, use an **SNS Topic**: the buying service sends **one message to the topic**, and the topic automatically distributes it to all its subscribers (e.g., email, fraud service, shipping service, an SQS queue) — no need for direct point-to-point integrations.
- **Event publishers** send messages to **one SNS topic**; you can have **as many event subscribers as you want** listening to that topic.
- **Each subscriber receives all messages** published to the topic — this is different from SQS, where multiple consumers **share** (split) the messages.

**Limits**
- Each SNS topic can have more than **12 million subscriptions**.
- A soft limit of **100,000 topics** per account.

**Supported subscriber/destination types**
- AWS targets: **Amazon SQS**, **Lambda**, **Amazon Data Firehose**.
- Also: direct **email**, **SMS**, **mobile push notifications**, and **HTTP/HTTPS endpoints**.

> **Exam Tip**: whenever you see "**notification**," "**publish/subscribe**," or "**subscribers**," think **Amazon SNS**.

---

### Lecture: SNS Hands On

- **Creating a topic**: SNS console → Create topic → name it (e.g., "demo-SNS") → leave all options at default → Create.
- **Creating a subscription**: choose a protocol — options include **HTTP, HTTPS, Email, Email-JSON, SQS, and Lambda**.
  - This demo uses **Email**, entering a temporary email address (via Mailinator, a service providing temporary/disposable mailboxes) as the endpoint.
- After creating the subscription, its status shows **"pending confirmation."** Confirming requires opening the confirmation email (sent by AWS to the subscribed address) and clicking confirm — after which the subscription becomes **confirmed**.
- (Additional/more complex subscription types beyond email are possible, but not demonstrated here — a topic can have many subscribers of different types.)
- **Publishing a message**: Publish message → enter a subject line (e.g., "demo subject line") and a message payload/body (e.g., "Hello World") → Publish.
- **Result**: all subscribers to the topic receive the message — confirmed here by checking the Mailinator inbox and finding the new email with the matching subject line and body content.
- **Cleanup**: delete the topic when done (no cost either way).

### Lecture: Amazon MQ Overview

- **SQS and SNS** are **cloud-native** services using AWS's own **proprietary protocols/APIs**.
- Traditional **on-premises** applications often use **open protocols** instead: **MQTT, AMQP, STOMP, OpenWire, WSS**.
- When migrating such an application to the cloud, you may **not** want to re-engineer it to use SQS/SNS APIs — instead, you want to keep using the protocols it already relies on.
- **Amazon MQ** solves this: it's a **managed message broker service** for two well-known on-premises broker technologies: **RabbitMQ** and **ActiveMQ** — both of which support the open protocols mentioned above.

**Implications**
- Amazon MQ does **not** scale as much as SQS/SNS, which offer near-infinite scaling.
- Because Amazon MQ **runs on servers**, it can experience server issues — you can set up a **Multi-AZ deployment with failover** for high availability.
- Amazon MQ combines **both** queue features (like SQS) and topic features (like SNS) within a **single broker**.

**When to use Amazon MQ**
- **Only** when a company is migrating to the cloud and specifically needs to keep using an **open protocol** (MQTT, AMQP, STOMP, etc.).
- Otherwise, prefer **SQS and SNS** — they scale better and integrate more deeply with the rest of AWS.

### Lecture: Cloud Integrations Summary

- **SQS**: a queuing service; multiple **producers** can send messages into a queue; messages are retained up to **14 days**, then deleted; **consumers share the reads** (splitting messages among themselves), and once a message is processed, it's deleted. Used to **decouple applications** within AWS.
  - > Anytime you see **"queuing"** or **"decoupling,"** think **SQS**.
- **SNS**: a notification service; has **producers** and **subscribers** (email, Lambda, SQS queues, HTTP, mobile, etc.). If multiple subscribers exist on one topic, **SNS sends the message to all of them**. SNS does **not** retain messages — it is **not** a durable message store. Used for **pub/sub**, subscribers, topics, and notifications within AWS.
- **Kinesis**: a **real-time data streaming** service, with some data persistence, that also supports running **real-time analytics** on the data.
- **Amazon MQ**: a managed **message broker** for **ActiveMQ** and **RabbitMQ** in the cloud — used when migrating from on-premises applications that rely on protocols like **MQTT, AMQP,** or others.

## Section: Cloud Integrations — Key Takeaways

**Most important concepts**
- Applications can communicate **synchronously** (direct, tightly coupled) or **asynchronously/event-based** (decoupled, typically via a queue or topic) — decoupling improves resilience and lets each side scale independently.
- **SQS** implements the **queue** model: producers send messages, consumers **share** (split) the work of reading and deleting them; supports Standard (unordered) and **FIFO** (strictly ordered) queues.
- **SNS** implements the **pub/sub** model: producers publish to a **topic**, and **every** subscriber receives **every** message — the opposite sharing behavior from SQS.
- **Kinesis** handles **real-time data streaming** at scale, with **Data Firehose** delivering that streamed data into storage/analytics destinations like S3 or Redshift.
- **Amazon MQ** is the migration-friendly option for teams that need to keep using traditional **open messaging protocols** (MQTT, AMQP, STOMP, etc.) rather than adopting AWS's proprietary SQS/SNS APIs.

**How the concepts relate**
- SQS and SNS are AWS's two core **decoupling** mechanisms, and they're often combined: an SNS topic can **fan out** a single message to multiple SQS queues (among other subscriber types), enabling both the "one message → one topic → many subscribers" pattern (SNS) and the "queue of work items shared across workers" pattern (SQS) in the same architecture.
- **Kinesis** solves a related but distinct problem — continuous, high-volume **streaming** data (e.g., clickstreams, IoT, logs) rather than discrete messages/notifications — with **Data Firehose** acting as the delivery mechanism into long-term storage or analytics tools.
- **Amazon MQ** exists specifically to bridge the gap between **legacy, protocol-dependent on-premises messaging systems** and the cloud, trading some of SQS/SNS's scalability for protocol compatibility during a migration.

**Key terminology to remember**
- Synchronous vs. asynchronous/event-based communication, decoupling
- SQS: producer, consumer, polling, message retention (default 4 days, max 14 days), Standard queue vs. FIFO queue
- SNS: topic, publisher, subscriber, pub/sub, fan-out
- Kinesis Data Streams, Amazon Data Firehose, fast data sources
- Amazon MQ: message broker, RabbitMQ, ActiveMQ, open protocols (MQTT, AMQP, STOMP, OpenWire, WSS)

**Key distinctions/comparisons**
- **SQS vs. SNS**: consumers **share/split** messages from a queue (SQS) vs. **every** subscriber receives **every** message from a topic (SNS).
- **SQS Standard vs. FIFO**: messages may be delivered out of order vs. strictly First-In-First-Out ordering.
- **SQS/SNS vs. Kinesis**: discrete message/notification delivery vs. continuous, high-volume real-time data streaming.
- **SQS/SNS vs. Amazon MQ**: AWS-proprietary, near-infinitely scalable, deeply AWS-integrated vs. managed broker (RabbitMQ/ActiveMQ) supporting open protocols, with more limited scaling and a server-based (not fully serverless) model.
- **Synchronous vs. asynchronous communication**: direct application-to-application calls (tightly coupled, vulnerable to traffic spikes) vs. queue/topic-mediated communication (decoupled, independently scalable).

**You should be able to explain:**
- The difference between synchronous and asynchronous (event-based) application communication, and why decoupling helps with traffic spikes.
- How SQS works (producers, consumers, polling, deletion), its key facts (retention period, latency, scaling), and the difference between Standard and FIFO queues.
- How SNS works (topics, publishers, subscribers, fan-out), its supported subscriber/destination types, and how it differs from SQS in terms of message distribution.
- What Kinesis Data Streams and Amazon Data Firehose are used for.
- What Amazon MQ is, which technologies it supports (RabbitMQ, ActiveMQ), which protocols it enables (MQTT, AMQP, STOMP, etc.), and when it should be used instead of SQS/SNS.
