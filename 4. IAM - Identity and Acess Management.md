## Section: IAM - Identity and Access Management

### Lecture: IAM Introduction: Users, Groups, Policies

- **IAM** = **Identity and Access Management**. It is a **global service** — users and groups you create apply across all regions (no region selection needed).
- **Root user**: created automatically when you create an AWS account. Should be used **only** to initially set up the account — should not be used regularly or shared with anyone.
- **IAM Users**: represent one physical person within an organization.
- **IAM Groups**: used to organize users.
  - Groups can contain **only users** — a group cannot contain another group.
  - A user does **not** have to belong to a group (possible, but not best practice — example: a standalone user with no group).
  - A user **can** belong to **multiple groups** at once (e.g., a user in both a "Developers" group and an "Audit Team" group inherits permissions from both).
- **Example scenario:** Alice, Bob, Charles → "Developers" group; David, Edward → "Operations" group; a lone user has no group; Charles and David also both belong to a shared "Audit Team" group.
- **IAM Policies**: JSON documents attached to users or groups that define **permissions** — i.e., what actions a user/group is allowed (or not allowed) to do.
  - Example: a policy might allow using EC2 (Describe), Elastic Load Balancing (Describe), and CloudWatch.
- **Principle of Least Privilege**: never grant more permissions than a user actually needs (e.g., if a user only needs access to 3 services, only grant those 3) — a core AWS security principle, since over-permissioned users can accidentally cause high costs or security issues.

---

### Lecture: IAM Users & Groups Hands On

- IAM console dashboard shows security recommendations; **Users** section is on the left sidebar.
- Confirms IAM is a **global service** — no region selector is active in the IAM console.
- The **root user** only shows an Account ID (no separate username) — reinforces that it shouldn't be used for daily work.
- **Creating a user**: provide a username; grant Management Console access.
  - Two options: **IAM Identity Center** (AWS-recommended) or a classic **IAM user** (simpler, and the one relevant for the exam).
  - Password options: auto-generated password + force change at next sign-in (for other people), or a custom password (e.g., for yourself).
- **Permissions during user creation**: attach directly, or add the user to a group.
  - Example: create an "admin" group, attach the **AdministratorAccess** policy to it, and add the new user to that group.
- **Tags**: optional key-value metadata that can be attached to many AWS resources (e.g., `Department = Engineering`).
- After creation, you can email sign-in instructions or download a CSV of credentials.
- Users **inherit** permissions from the group(s) they belong to — a permission attached via a group is not "directly attached" to the user, but the user still effectively has it.
- **Account alias**: customizes your account's sign-in URL; must be globally unique across AWS.
- **Simultaneous multi-account sign-in trick**: use a private/incognito browser window to sign in as a different identity, since normally signing in with a new identity in the same window logs out the previous one. This lets you have (e.g.) the root user in a normal window and an IAM user in a private window at the same time.
- The AWS sign-in page offers a choice between **Root user** sign-in and **IAM user** sign-in (the latter requires the account ID or alias).
- **Best practice reminder:** keep your root account and admin IAM credentials safe — losing access to both means you'll need AWS Support to regain access to your account.
- Course recommendation: generally use your IAM user rather than root going forward (root is only used when specifically required).

### Lecture: AWS Console Simultaneous Sign-in

- **Multi-session support**: a console feature that lets you sign into **multiple AWS identities within the same browser window** (rather than needing separate private windows).
- You can "add a session" and sign in with a different account ID or as root, then switch between sessions in the same browser.
- Each session's console view is **isolated** — e.g., a resource created in one session (such as an EBS volume) is not visible when viewing the same service in a different session.
- Useful when working with AWS at scale (multiple accounts).

### Lecture: IAM Policies

**Policy inheritance model**
- A policy attached at the **group level** applies to every member of that group.
- An **inline policy** is a policy attached directly to a single user — that user may or may not also belong to a group.
- A user belonging to multiple groups inherits the policies from **all** of those groups (e.g., a user in both "Developers" and "Audit Team" ends up with both groups' policies).

**IAM Policy (JSON) structure**
| Element | Description | Required? |
|---|---|---|
| Version | Policy language version (usually `2012-10-17`) | Yes |
| Id | Identifier for the policy | Optional |
| Statement | One or more statements (the core of the policy) | Yes |
| Sid | Statement ID — identifier for an individual statement | Optional |
| Effect | Whether the statement `Allow`s or `Deny`s access | Yes |
| Principal | The account/user/role the policy applies to | Yes |
| Action | List of API calls allowed or denied | Yes |
| Resource | List of resources the actions apply to | Yes |
| Condition | When the statement should apply | Optional |

> **Exam Tip:** For the exam, make sure you clearly understand **Effect, Principal, Action, and Resource** — these are the core parts of an IAM policy statement.

### Lecture: IAM Policies Hands On

- **Removing a user from a group removes any permissions inherited from that group.** Demonstrated by removing a user from the "admin" group (which had `AdministratorAccess`) — the user immediately loses access and receives "Access Denied" errors (e.g., cannot call `iam:ListUsers`).
- Permissions can be attached **directly** to a user instead of via a group (e.g., attaching the `IAMReadOnlyAccess` managed policy directly to a user).
- **Read-only access** allows *viewing* resources but not *creating* them (e.g., a user with `IAMReadOnlyAccess` can view groups but cannot create a new group — creating a group requires broader access such as full IAM access).
- A user can accumulate permissions from **multiple sources at once**: inherited from one or more groups, plus directly attached policies. Each permission shows where it was inherited from (a specific group vs. attached directly).

**Managed policy examples (JSON)**
- **AdministratorAccess**: `Effect: Allow`, `Action: "*"`, `Resource: "*"` — the `*` wildcard means "anything," so this allows all actions on all resources = full admin access.
- **IAMReadOnlyAccess**: `Effect: Allow` on a specific list of read/list API calls, using wildcards like `Get*` (any action starting with "Get," e.g., `GetUser`) and `List*` (any action starting with "List," e.g., `ListUsers`) to group many related API calls together, applied to `Resource: "*"`.

**Creating custom policies**
- Can be built with a **Visual Editor** or written directly as **JSON**.
- Example: a custom policy granting only `iam:ListUsers` and `iam:GetUser` on all resources — demonstrates building a minimal, least-privilege policy.
- Custom policies, once created, can be attached to users or groups just like managed policies.

### Lecture: IAM MFA Overview

Two defense mechanisms to protect accounts from compromise:

**1. Password Policy** — configurable options in AWS:
- Minimum password length
- Require specific character types (uppercase, lowercase, number, non-alphanumeric)
- Allow/disallow IAM users to change their own password
- Require password expiration / rotation (e.g., every 90 days)
- Prevent password reuse
- Purpose: protects against brute-force attacks.

**2. Multi-Factor Authentication (MFA)**
- Combines **something you know** (password) with **something you own** (a security device).
- Even if a password is stolen/hacked, the account stays protected because the attacker would also need the physical/virtual MFA device.
- Strongly recommended for at least the root account, and ideally all IAM users — especially administrators, who can change configurations and delete resources.

> **Exam Tip:** Know the MFA device options in AWS:

| MFA Device Type | Description | Provider |
|---|---|---|
| Virtual MFA device | Software-based app; e.g., Google Authenticator (one device at a time) or Authy (supports multiple tokens — root + multiple IAM users — on a single device) | Third-party apps |
| Universal 2nd Factor (U2F) Security Key | Physical device (e.g., a key fob); a single key can support multiple root/IAM users | YubiKey, by Yubico (third-party to AWS) |
| Hardware Key Fob MFA Device | Physical hardware device | Gemalto (third-party to AWS) |
| Hardware Key Fob for AWS GovCloud (US) | Special device for the US government cloud | SurePassID (third-party to AWS) |

---

### Lecture: IAM MFA Hands On

- **Setting a password policy**: IAM console → Account Settings → Password Policy — use the AWS default policy or customize it (length, character requirements, expiration, reuse prevention).
- **Enabling MFA on the root account**: click account name → Security Credentials → assign an MFA device.
- Device type choices during setup: authenticator app, security key, or hardware TOTP token.
- **Virtual MFA setup process (authenticator app)**: scan the AWS-provided QR code with a compatible authenticator app, then enter **two consecutive MFA codes** generated by the app to confirm the device is set up correctly.
- AWS supports registering **multiple MFA devices** on an account (demoed showing up to 8 devices).
- **Caution:** losing access to your MFA device (e.g., losing your phone) without a backup can lock you out of your account.
- Once MFA is enabled, logging in requires both the password **and** a valid MFA code.

### Lecture: AWS Access Keys, CLI and SDK

**Three ways to access/manage AWS**
| Method | Protected by |
|---|---|
| Management Console | Username + password (+ optional MFA) |
| CLI (Command Line Interface) | Access Keys |
| SDK (Software Development Kit) | Access Keys |

- **Access Keys**: generated via the Management Console; consist of an **Access Key ID** (like a username) and a **Secret Access Key** (like a password).
  - Users are responsible for their own access keys.
  - They are **private/secret** — never share them; a colleague should generate their own rather than use yours.
  - The secret key can only be viewed/downloaded once, at creation time.

- **AWS CLI**: a tool to interact with AWS services via commands in a terminal (all commands start with `aws`).
  - Gives direct access to AWS's public APIs.
  - Enables scripting/automation of AWS resource management.
  - Open-source (source available on GitHub).
  - An alternative to the Management Console — some users work exclusively via the CLI.

- **AWS SDK**: a set of **language-specific libraries** for programmatic access to AWS services/APIs, embedded within application code (not run from a terminal).
  - Supports many languages: JavaScript, Python, PHP, .NET, Ruby, Java, Go, Node.js, C++, etc.
  - Also includes a Mobile SDK (Android/iOS) and an IoT Device SDK.
  - Example: the AWS CLI itself is built on the AWS SDK for Python, named **Boto**.

### Lecture: AWS CLI Setup on Windows

- Install **AWS CLI v2** using the official MSI installer (found via AWS documentation/Google).
- v2 vs. v1: same API, but v2 has improved performance/capability and installer.
- Verify installation in Command Prompt with `aws --version` — should return a version starting with `2`, plus Python and Windows details.
- To upgrade: re-download and re-run the MSI installer.

### Lecture: AWS CLI Setup on Mac

- Install **AWS CLI v2** using the downloadable `.pkg` graphical installer.
- During install, choose to install for all users on the computer.
- Verify installation in Terminal (or an alternative terminal app like iTerm) with `aws --version`.

### Lecture: AWS CLI Setup on Linux

- Install **AWS CLI v2** via three terminal commands:
  1. Download the zip installer file.
  2. Unzip it.
  3. Run the installer as root (using `sudo`).
- Verify with `aws --version` (use the full path, e.g. `/usr/local/bin/aws --version`, if the command isn't found directly).

### Lecture: AWS CLI Hands On

- **Create Access Keys**: user profile → Security Credentials → Create Access Key.
  - AWS may suggest alternatives depending on your use case (e.g., **CloudShell** instead of long-lived keys, or authentication via **IAM Identity Center**) — but access keys can still be created for direct CLI use.
  - The Access Key ID and Secret Access Key are shown **only once** at creation — must be saved immediately.
- **Configure the CLI**: run `aws configure`, then provide:
  - Access Key ID
  - Secret Access Key
  - Default region name (choose one close to you)
  - Default output format
- Example command: `aws iam list-users` — returns similar information to what's shown in the Management Console.
- **CLI permissions exactly mirror IAM console permissions**: removing a user's permissions (e.g., removing them from a group) blocks equivalent CLI calls too (e.g., `aws iam list-users` returns nothing / is denied).
- **Key takeaway:** access via the Console and access via Access Keys/CLI are governed by the **exact same IAM permissions**.

### Lecture: AWS CloudShell

- **CloudShell**: a free, browser-based terminal built directly into the AWS Console (icon in the top-right corner).
- An alternative to installing/configuring a local terminal for CLI use.
- **Availability**: not available in all regions — check the CloudShell region availability list if you plan to use it.
- Automatically uses the credentials of whichever identity you are currently logged in as in the console — so API calls run with those permissions with no extra setup.
- **Default region** for CLI commands in CloudShell = the region you are currently viewing/logged into in the console (instead of needing to pass a region argument).
- Comes with **persistent file storage** — files created in CloudShell (e.g., via `echo test > demo.txt`) persist even after restarting the CloudShell session.
- Customizable: font size, theme (light/dark).
- Supports **uploading and downloading files** directly through the CloudShell UI.
- Supports multiple tabs / split-screen terminals within the same environment.
- If CloudShell isn't available in your region or isn't working for you, using a regular local terminal with the CLI works just as well for the course.

### Lecture: IAM Roles for AWS Services

- **IAM Roles**: similar to users, but intended to be used by **AWS services**, not physical people.
- Purpose: grant an AWS service permission to perform actions on your behalf/account.
- Example: an **EC2 Instance** (a virtual server) may need to call other AWS services — you attach an IAM Role to the instance so it can do so, using the permissions defined in that role.
- Other common examples of roles: **Lambda Function Roles**, **CloudFormation** roles, and roles for many other AWS services.
- The service + its attached role effectively act as one entity when AWS authorizes an action.

---

### Lecture: IAM Roles Hands On

- Create a role: IAM console → Roles → Create Role.
- Multiple role types exist; the one most relevant for this hands-on and the exam is a **Role for an AWS service**.
- Choose the target service (e.g., EC2, Lambda, or virtually any AWS service).
- **Example**: create a role named `DemoRoleForEC2` — choose EC2 as the trusted service, attach the `IAMReadOnlyAccess` policy, name the role, and create it.
- The **trusted entity** defines which service (e.g., EC2) is permitted to "assume" (use) this role.
- The role is not usable yet until an actual EC2 instance is created and the role is attached to it (covered later in the course, in the EC2 section).

### Lecture: IAM Security Tools

Two key IAM auditing/security tools:

| Tool | Scope | What it shows |
|---|---|---|
| **IAM Credentials Report** | Account-level | Lists all users in the account and the status of their various credentials |
| **IAM Access Advisor** | User-level | Shows service permissions granted to a specific user and when those services were last accessed |

- Access Advisor supports the **principle of least privilege** by revealing unused permissions that can be safely removed.

---

### Lecture: IAM Security Tools Hands On

- **Generating a Credentials Report**: IAM console → Credential Report → Download credential report (produces a CSV file).
  - Report includes, per user: creation date, whether a password is enabled, when the password was last used/changed, next expected password rotation (if enabled), whether MFA is active, whether access keys exist and when they were last rotated/used, and more.
  - Useful for identifying users/accounts that need security attention (e.g., stale passwords, no MFA enabled).
- **Using Access Advisor**: go to a specific user → Access Advisor tab.
  - Shows which services were accessed and when (e.g., IAM, EC2, Resource Explorer) versus services never accessed (e.g., Alexa for Business).
  - Can drill down to see which specific policy granted access to a given service.
  - Helps decide whether to reduce a user's granted permissions down to only what is actually used — reinforcing least privilege.

### Lecture: IAM Best Practices

- Do **not** use the root account except for initial account setup.
- **One AWS user = one physical person** — never share credentials; create a separate user for each person.
- Assign users to **groups** and manage permissions at the group level.
- Create a **strong password policy**.
- Enable and **enforce MFA**.
- Create and use **IAM Roles** for AWS services (e.g., EC2 instances) rather than embedding long-lived credentials.
- If accessing AWS programmatically (CLI/SDK), use **Access Keys** — treat them like passwords and keep them private.
- Use the **IAM Credentials Report** and **IAM Access Advisor** to regularly audit and review permissions.
- **Never** share IAM users or access keys, under any circumstances.

### Lecture: Shared Responsibility Model for IAM

> **Exam Tip:** The CCP exam includes many questions on the Shared Responsibility Model.

| Responsibility | Owner |
|---|---|
| Infrastructure, global network security | AWS |
| Configuration and vulnerability analysis of the services AWS offers | AWS |
| Compliance validation | AWS |
| Creating and managing users, groups, roles, and policies | **You (customer)** |
| Monitoring users, groups, roles, and policies | **You (customer)** |
| Enabling and enforcing MFA on all accounts | **You (customer)** |
| Rotating access/secret keys regularly | **You (customer)** |
| Applying appropriate permissions using IAM tools | **You (customer)** |
| Analyzing access patterns and reviewing permissions | **You (customer)** |

- In short: AWS is responsible for the infrastructure; **you** are responsible for how you configure and manage identities and access within it.

- **IAM Users** — map to an actual physical person; have a console password.
- **IAM Groups** — contain only users; used to organize permissions.

## Section: IAM - Identity and Access Management — Key Takeaways

**Most important concepts**
- IAM manages **who** (users, groups, roles) can do **what** (via policies) in an AWS account, and is a **global** service.
- Four core IAM identity types: **Users** (people), **Groups** (collections of users), **Roles** (for AWS services), and the underlying **Policies** (JSON documents) that grant permissions to any of them.
- Security is reinforced through a **Password Policy** and **MFA**, and audited through the **IAM Credentials Report** and **IAM Access Advisor**.
- Access to AWS happens through three channels — **Management Console**, **CLI**, and **SDK** — with the Console using username/password(+MFA) and the CLI/SDK using **Access Keys**; all three are governed by the exact same underlying IAM permissions.
- **CloudShell** is a browser-based alternative to a local CLI terminal, using your current console session's credentials automatically.
- The **Shared Responsibility Model** applies to IAM specifically: AWS secures the infrastructure; the customer is fully responsible for creating/managing/monitoring users, groups, roles, policies, MFA, and key rotation.

**How the concepts relate**
- A **Policy** (JSON) is attached to a **User**, a **Group**, or a **Role** to define permissions → Users can be organized into **Groups** for easier permission management → Users can also get **inline** (direct) policies → A **Role** serves the same permission-granting purpose as a policy attachment, but for AWS services (like EC2) instead of people → **MFA** and **password policies** protect the login step, independent of what permissions are granted → **Access Keys** extend a user's permissions to the CLI/SDK, using the same underlying IAM permission set as the Console → **Credentials Report** and **Access Advisor** are used to audit whether the permissions granted (via policies, groups, or roles) still align with the **principle of least privilege**.

**Key terminology to remember**
- IAM, root user, IAM user, IAM group, inline policy, managed policy, principle of least privilege
- Policy structure: Version, Id, Statement, Sid, Effect (Allow/Deny), Principal, Action, Resource, Condition
- MFA (Multi-Factor Authentication), password policy
- Virtual MFA device, U2F Security Key, Hardware Key Fob MFA device
- Access Key ID, Secret Access Key
- CLI (Command Line Interface), SDK (Software Development Kit), CloudShell
- IAM Role, trusted entity
- IAM Credentials Report, IAM Access Advisor
- Shared Responsibility Model: "security of the cloud" (AWS) vs. "security in the cloud" (customer), applied specifically to IAM

**Key distinctions/comparisons**
- **Groups vs. Roles**: groups contain only users and organize human permissions; roles are assumed by AWS services (e.g., EC2, Lambda), not people.
- **Group-attached policy vs. inline policy**: a group policy applies to every member of the group; an inline policy is attached directly to one specific user.
- **AdministratorAccess vs. IAMReadOnlyAccess**: `Action: "*", Resource: "*"` (full access) vs. specific `Get*`/`List*` read-only actions.
- **Console vs. CLI vs. SDK**: how you access AWS (web UI vs. terminal commands vs. embedded application code) — but all governed by the same IAM permissions.
- **Access Keys vs. Password**: Access Keys authenticate CLI/SDK access; passwords (+MFA) authenticate Console access — both must be kept private and never shared.
- **IAM Credentials Report (account-level) vs. IAM Access Advisor (user-level)**: overall credential status for all users vs. per-user service access history.
- **Customer responsibility vs. AWS responsibility** for IAM under the Shared Responsibility Model.

**You should be able to explain:**
- The difference between IAM users, groups, roles, and policies, and how they relate to each other.
- Why the root account should not be used day-to-day, and what best practices apply instead.
- The structure of an IAM policy (Version, Statement, Effect, Principal, Action, Resource, Condition) and what each part means.
- How permission inheritance works when a user belongs to multiple groups and/or has directly attached (inline) policies.
- The two account-protection mechanisms — password policy and MFA — and the available MFA device types.
- The three ways to access AWS (Console, CLI, SDK) and what credentials protect each.
- What Access Keys are, how they're generated, and why they must be kept private.
- What CloudShell is and how it differs from a local CLI setup.
- The purpose of IAM Roles for AWS services, with EC2 as the primary example, and how they differ from IAM users.
- The purpose and output of the IAM Credentials Report and IAM Access Advisor, and how they support the principle of least privilege.
- The IAM-specific breakdown of the Shared Responsibility Model — what AWS handles vs. what the customer must handle.
