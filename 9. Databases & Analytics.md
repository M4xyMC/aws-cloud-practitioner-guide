## Section: Databases & Analytics

### Lecture: Databases Introduction

- Storing data on disk (EBS, EC2 Instance Store, S3) has limits — if you want to store data in a **structured** way, with indexes for efficient querying/searching, you want a **database**. Unlike per-file storage (EFS/EBS/EC2 Instance Store/S3), databases are structured and can define **relationships** between datasets.
- Databases today are each **optimized for a purpose**, with different features, shapes, and constraints. For the exam, you need to match the right database to the right use case.

**Relational databases**
- *Analogy:* like Excel spreadsheets, but with **links between tables**.
  - Example: a "students" table (columns: student ID, department ID, name, email) links to a "departments" table via the department ID — this link is the "relation," hence **relational database**.
  - Additional relations can be defined (e.g., linking students to a "subjects" table).
- Key characteristic: you use the **SQL** language to query/look up data.
- > Whenever you hear **SQL**, think **relational database**.

**NoSQL databases**
- NoSQL = **non-relational** databases; more modern, built for a specific purpose/data model, with a **flexible schema** for modern applications (schema = the shape of the data).
- Benefits: more flexibility, easier to evolve the data model, **scalable** — designed to **scale out** by adding distributed servers (unlike relational databases, which are harder to add servers to and typically scale **up**/vertically instead).
- High performance and highly functional, since data types are optimized for the specific model.
- Examples of NoSQL types: key-value, document, graph, in-memory, search databases (all covered in this section).
- NoSQL data is commonly stored in **JSON** (JavaScript Object Notation) format — the same format used for IAM policies.
  - JSON supports **nesting** (e.g., an "address" field nested within a larger object) and fields that can **change over time**.
  - JSON supports **arrays** (e.g., a person having multiple cars: Ford, BMW, Fiat).

**Managed databases and the Shared Responsibility Model**
- AWS offers many managed database services. Benefits of a managed database:
  - Quick to provision.
  - Designed with **high availability** in mind.
  - Easy **vertical and horizontal scaling**.
  - Includes **automated backup and restore** utilities.
  - AWS handles **operations, upgrades, and OS patching** of the underlying instance — this is **no longer your responsibility**.
  - Integrated **monitoring and alerting**.
- Alternative: you *can* run your own database technology on an EC2 instance, but then **you** must handle resiliency, backup, patching, high availability, fault tolerance, and scaling yourself.
- This section covers AWS's managed database offerings and the use cases each fits.

### Lecture: RDS & Aurora Overview

**RDS (Relational Database Service)**
- A managed database service for databases using **SQL** as the query language.
- Supported engines: **Postgres, MySQL, MariaDB, Oracle, Microsoft SQL Server, IBM DB2**, and **Aurora** (AWS's proprietary database, covered below).

**Why use RDS instead of deploying your own database on EC2?**
- Automatic provisioning.
- OS patching handled by AWS.
- Continuous backups and restore options, including **point-in-time restore**.
- Monitoring dashboards.
- **Read Replicas** to scale reads and improve read performance.
- **Multi-AZ** setups for disaster recovery against an entire AZ outage.
- Maintenance windows for upgrades.
- Both vertical and horizontal scaling.
- Storage is backed by **EBS**.
- **Key limitation**: you **cannot SSH** into an RDS database instance — AWS manages the database entirely; you only interact with it as a service.

**Where RDS fits in an architecture**
- Classic 3-tier setup: Load Balancer (web tier) → backend EC2 instances, possibly in an Auto Scaling Group (application tier) → a relational (SQL) database (data tier) that the EC2 instances read from and write to.

**Aurora**
- A database technology **created by AWS** (not open source); works similarly to RDS in that your EC2 instances connect directly to it.
- Supports two database engines: **PostgreSQL** and **MySQL**.
- **Cloud-optimized**: offers a **5x performance improvement** over MySQL on RDS, and a **3x performance improvement** over PostgreSQL on RDS.
- Storage grows **automatically**, in increments of 10 GB, up to **256 TB** — no need to manage storage yourself.
- Costs roughly **20% more** than RDS, but tends to be more cost-effective overall due to its efficiency.
- > **Exam takeaway**: RDS and Aurora are both ways to create relational databases on AWS, both fully managed — Aurora is more cloud-native, while RDS runs familiar database technologies as a managed service.

**Aurora Serverless**
- Database instantiation is automated, with **autoscaling** based on actual usage.
- Supports both PostgreSQL and MySQL engines.
- No capacity planning needed; no server management; you pay **per second** — can be far more cost-effective than provisioning a full Aurora cluster.
- Best suited for **infrequent, intermittent, or unpredictable workloads**.
- How it works: clients connect to a **proxy fleet** managed by Aurora; behind the scenes, Aurora instantiates database instances to scale up/down as needed, and all instances share the **same underlying storage volume**.
- > **Exam Tip**: if you see "Aurora with no management overhead," think **Aurora Serverless**.

### Lecture: RDS Hands On

- Creating a database via the Aurora and RDS console: Databases → Create database → **Full configuration** (vs. Easy create).
- Engine options: Aurora (MySQL- or Postgres-compatible), MySQL, Postgres, and others — this demo uses **MySQL**.
- **Templates**: **Production** (unlocks Multi-AZ DB instance deployment with 2 instances, or Multi-AZ DB cluster deployment with 3 instances), **Dev/Test**, or **Free Tier** (used here — only allows Single-AZ DB instance deployment with 1 instance).
- **Credential management**: either self-managed password (used here) or password managed by **AWS Secrets Manager** (more secure, but has an added cost). Also possible to authenticate via **IAM**.
- **Instance configuration**: free-tier eligible instance class (e.g., `db.t4g.micro`), 20 GB storage; **Storage Autoscaling** can be enabled to grow storage automatically (e.g., up to 1,000 GB) as needed.
- **Connectivity**: chose not to connect to an EC2 compute resource; default VPC; **Public access: Yes** (to allow connecting via a public IP); a new dedicated VPC security group created (e.g., "demo-rds"); default port for MySQL: **3306**.
- **Monitoring**: standard insights chosen; enhanced monitoring and log export are optional.
- **Estimated monthly cost**: the console shows free-tier eligibility info (available for **12 months** for eligible instance types).
- After creation, the database summary shows: the AZ it launched in, its **endpoint** and **port** (used to connect), its attached VPC security group and inbound rules (e.g., port 3306 open).
- **Monitoring tab**: shows CPU utilization, login events, configuration, backups, and tags — illustrating the benefit of a managed service having built-in observability.

**Snapshots**
- **Take a snapshot**: Actions → Take snapshot (must wait until the DB is "Available," not still in a backup state) — creates a point-in-time backup.
- **Restore a snapshot**: Actions → Restore snapshot → creates a **new** database from the snapshot — useful for creating a bigger database, a copy with different settings, etc.
- **Copy a snapshot**: can copy it to a **different region** — helpful for disaster recovery.
- **Share a snapshot**: can share it with **other AWS accounts**, so they can restore their own database directly from your snapshot.
- **Cleanup**: delete the snapshot, then delete the database (Actions → Delete) — choosing not to create a final snapshot or retain automated backups, and typing "delete me" to confirm.

### Lecture: RDS Deployments Options

**RDS Read Replicas**
- Purpose: **scale read workloads**.
- You create copies (replicas) of your RDS database — applications can read from the main database **and** from up to **15 Read Replicas**.
- **Writes** still go **only** to the main (central) database — Read Replicas are read-only.

**Multi-AZ**
- Purpose: **failover / high availability** in case of an AZ outage.
- Applications read and write **only** to the main database; a **replicated failover database** is maintained in a **different AZ**.
- If the main database crashes (or its AZ has issues), RDS automatically triggers a **failover** to the standby database in the other AZ.
- The failover database is **passive** and not accessible until a failover event occurs.
- You can only have **one other AZ** as the failover AZ.

**Multi-Region**
- Purpose: a variant of Read Replicas, but replicated **across different regions** rather than within the same region.
- Example: main RDS database in `eu-west-1`, with a Read Replica in `us-east-2` (and potentially another in `ap-southeast-2`). Local applications in each region can **read locally** from their nearby replica, but **writes** must always go across region, back to the primary (`eu-west-1`).
- **Why use Multi-Region:**
  - **Disaster recovery** — if the primary region has an outage, a replica exists elsewhere.
  - **Better performance** for geographically distributed applications, since reads happen from a local, low-latency replica.
- **Trade-off**: cross-region replication incurs a **network transfer (replication) cost**.

> **Exam Tip:** Exam scenarios will make clear which deployment option (Read Replica, Multi-AZ, or Multi-Region) fits the described need — know their distinct purposes.

### Lecture: ElastiCache Overview

- **Amazon ElastiCache** is the managed equivalent for **Redis** or **Memcached** databases — the same way RDS gives you managed relational databases.
- ElastiCache databases are **in-memory** — high performance, low latency.
- > Whenever the exam mentions needing an **in-memory database**, think **ElastiCache**.
- **Purpose**: reduce load on databases with **read-intensive workloads** — instead of repeatedly querying RDS for the same data, cache the results in ElastiCache so future reads hit the (much faster) cache instead.
- As a managed service, AWS handles OS maintenance/patching, optimization, setup/configuration, monitoring, failure recovery, and backups.

**Architecture**
- Load Balancer → EC2 instances (possibly in an ASG) → read/write to RDS (slower) **and** cache values in ElastiCache (very fast, in-memory) — taking read pressure off the main RDS database.

### Lecture: DynamoDB Overview

- **DynamoDB** is a fully managed, highly available **NoSQL** database, with replication across **3 Availability Zones**.
- One of AWS's flagship products — scales to **massive workloads**.
- **Serverless / distributed**: no servers to provision (though servers exist behind the scenes, they're invisible to you).
- Scales to **millions of requests per second**, **trillions of rows**, and **hundreds of terabytes** of storage.
- Fast, consistent performance — **single-digit millisecond latency**.
- > **Exam keywords**: "serverless" + "low latency" (e.g., single-digit millisecond) → think **DynamoDB**.
- Integrated with **IAM** for security, authorization, and administration.
- Low cost, with **auto scaling** capabilities.
- Offers **Standard** and **Infrequent Access (IA)** table classes for cost optimization based on data access patterns.

**Data model**
- A **key-value** database.
- Each item has a **primary key** made of one or two columns: a **partition key**, and optionally a **sort key**.
- Additional **attributes** (your own custom columns) can be added per item.
- Data is stored **row by row** within a table.

**DynamoDB Accelerator (DAX)**
- A fully managed **in-memory cache specifically for DynamoDB** (distinct from ElastiCache).
- Used to cache the most frequently read items from a DynamoDB table.
- Because DAX is purpose-built and tightly integrated with DynamoDB, you'd use DAX (not ElastiCache) for this — even though ElastiCache *could* technically be used.
- Provides a **10x performance improvement**: instead of single-digit millisecond latency, you get **microsecond** latency.
- Fully secure, highly scalable, highly available.
- > **Key distinction**: DAX is exclusively for DynamoDB; ElastiCache can provide caching for other types of databases too.

### Lecture: DynamoDB Hands On

- **Creating a table**: specify a table name (e.g., "DemoTable") and a **partition key** (e.g., `user_id`) — sort keys are noted as **out of scope for the exam**.
- Settings left as default; clicking Create table shows the table being created **without ever creating or provisioning a database** — DynamoDB is serverless, so you just define the table and AWS handles everything else.
- **Inserting items** (View items → Create item):
  - Item 1: `user_id = 1234`, `first_name = Stephane`, `last_name = Maarek`, a number attribute (e.g., favorite number = 42).
  - Item 2: `user_id = 45678`, `first_name = Alice` — **no** last name or favorite number specified, and DynamoDB **still accepts it** — demonstrating DynamoDB's flexible schema (attributes/columns are not fixed and are inferred automatically per item).
- **Key distinction from RDS**: all data in DynamoDB lives within **one single table**, with **no way to join** it with another table — this is why DynamoDB is **NoSQL** (non-relational). All relevant data must be well-structured within the main table itself, which changes how you approach database design.
- Deeper DynamoDB knowledge (data modeling, indexes, etc.) is the focus of the **AWS Certified Developer** exam, not the Cloud Practitioner exam.
- Cleanup: delete the table (and any associated CloudWatch alarms) by typing "delete" to confirm.

### Lecture: DynamoDB Global Tables

- **DynamoDB Global Tables**: makes a DynamoDB table accessible with **low latency** in **multiple regions**.
- Example: a table exists in `us-east-1` (Northern Virginia). You can set up a **Global Table** with replication to, say, `eu-west-3` (Paris) — data is kept in sync via **two-way replication**, and users near Paris can access the table with low latency locally.
- Supported for **1 to 10 regions**.
- Since users can **read AND write** to the table in **any** configured region (with changes replicating to the others), this is called **active-active replication** — you can actively write to any region, and it will actively replicate to the others.

### Lecture: Redshift Overview

- **Redshift** is a database based on **PostgreSQL**, but it is **not** used for **OLTP** (Online Transaction Processing — what RDS is good for). Instead, Redshift is used for **OLAP** (**O**nline **A**nalytical **P**rocessing) — analytics and data warehousing.
- > **Exam Tip**: whenever you see "data warehouse" + "analytics," think **Redshift**.
- Data is typically **not loaded continuously** — it's loaded periodically (e.g., every hour).
- Boasts **10x better performance** than other data warehouses; scales to **petabytes** of data.
- Data is stored in **columns** (**columnar storage**), rather than rows.
- > Whenever you see "columnar," think **Redshift**.
- Uses a **Massively Parallel Query Execution (MPP)** engine for fast computations.
- Pay-as-you-go pricing based on provisioned instances; uses a **SQL** interface for queries.
- Integrates with **Business Intelligence (BI)** tools like **QuickSight** or **Tableau** for dashboards.

**Redshift Serverless**
- Runs Redshift without needing to worry about scaling or provisioning the data warehouse — AWS handles it automatically.
- Use cases: reporting/dashboarding applications, real-time analytics — all without managing underlying infrastructure.
- How it works: enable Amazon Redshift Serverless on your account → connect via the Redshift Query Editor (or another tool) → Redshift Serverless automatically runs queries and provisions/scales capacity based on the workload.
- You only pay for the **compute and storage actually used** during analysis — a cost-efficient option, and one the exam can test on.

### Lecture: EMR Overview

- **Amazon EMR** (Elastic MapReduce) is **not really a database** — it's used to create a **Hadoop cluster** for big data processing on AWS.
- A **Hadoop cluster** analyzes and processes vast amounts of data using multiple servers working together; Hadoop is an **open-source technology**.
- With EMR, you can create a cluster of **hundreds of EC2 instances** collaborating to analyze data.
- Related Hadoop/big-data ecosystem projects that run on top of an EMR cluster: **Apache Spark, HBase, Presto, Flink**.
- EMR provisions and configures all the EC2 instances needed so they work together.
- Includes **auto-scaling** and integration with **Spot Instances**.
- **Use cases**: data processing, machine learning, web indexing, big data in general.
- > **Exam Tip**: whenever you see "Hadoop cluster," think **Amazon EMR**.

---

### Lecture: Athena Overview

- **Amazon Athena** is a **serverless query service** to run analytics directly against objects stored in **Amazon S3**.
- Uses the **SQL** query language; there's no need to **load** the data anywhere — it just needs to already be in S3.
- Supported file formats: **CSV, JSON, ORC, Avro, Parquet**. Built on the **Presto** engine.
- **How it works**: users load data into S3 → Athena is used to query and analyze it directly → optionally, use **Amazon QuickSight** on top for reporting/visualization.
- **Pricing**: roughly **$5 per terabyte of data scanned**; using compressed or **columnar** formats reduces the amount of data scanned, saving cost.
- **Use cases**: business intelligence, analytics, reporting, analyzing VPC Flow Logs, ELB logs, CloudTrail logs, and other AWS platform logs.
- > **Exam Tip**: "serverless" + "analyze data in S3" + "SQL" → think **Amazon Athena**.

### Lecture: QuickSight Overview

- **Amazon QuickSight** is a **serverless, machine-learning-powered business intelligence** service for creating **interactive dashboards**.
- Lets you visually represent data and surface insights for business users — charts, graphs, and interactive dashboards.
- Fast, automatically scalable, embeddable, with **per-session pricing** — no servers to provision.
- **Use cases**: business analytics, building visualizations, ad-hoc analysis, gaining business insights from data.
- **Integrations**: can run on top of RDS, Aurora, Athena, Redshift, Amazon S3, and more.
- QuickSight is the **go-to tool for BI (Business Intelligence) in AWS**.

### Lecture: DocumentDB Overview

- **DocumentDB** is essentially "**Aurora for MongoDB**" — the same way Aurora is AWS's cloud-native reimplementation of PostgreSQL/MySQL, DocumentDB is AWS's implementation compatible with **MongoDB**.
- **MongoDB** is a NoSQL database used to store, query, and index **JSON** data — remember this connection for the exam.
- DocumentDB is a **NoSQL** database, **compatible with MongoDB**.
- Same deployment philosophy as Aurora: fully managed, highly available, data replicated across **3 Availability Zones**.
- Storage automatically grows in increments of **10 GB**.
- Engineered to scale to workloads with **millions of requests per second**.
- > **Exam Tip**: anything related to **MongoDB** → think **DocumentDB**. Anything related to **NoSQL** in general → think **DocumentDB** and/or **DynamoDB**.

### Lecture: Neptune Overview

- **Amazon Neptune** is a fully managed **graph database**.
- *Example of graph data*: a social network — people are friends, like/comment/share posts, etc. — everything is interconnected, forming a **graph**.
- Replication across **3 AZs**; up to **15 Read Replicas**.
- Used to build and run applications with **highly connected datasets** (e.g., social networks); optimized for complex, hard queries on graph data.
- Can store **billions of relations** and query the graph with **millisecond latency**.
- Highly available across multiple Availability Zones.
- **Use cases**: knowledge graphs (e.g., Wikipedia, where articles are interconnected), fraud detection, recommendation engines, social networking.
- > **Exam Tip**: anything related to **graph databases** → think **Neptune**.

### Lecture: Timestream Overview

- **Amazon Timestream** is a fully managed, fast, scalable, **serverless** database for **time series data** — data that evolves/changes over time (e.g., a value plotted against dates from older to newer).
- **Automatic scaling** up and down based on capacity/compute needs.
- Can store and analyze **trillions of events per day**.
- Roughly **1,000x faster** and **1/10th the cost** of relational databases for this use case.
- Includes **time series analytics functions** to find patterns in the data in real time.
- > **Exam Tip**: anything related to **time series data** → think **Amazon Timestream**.

### Lecture: Managed Blockchain Overview

- **Blockchain** enables applications where multiple parties can execute transactions **without a trusted central authority** — a decentralized model.
- **Amazon Managed Blockchain** lets you **join public blockchain networks** or **create your own scalable private blockchain network** within AWS.
- Compatible with two frameworks: **Hyperledger Fabric** and **Ethereum**.
- > **Exam Tip**: anything related to **Blockchain**, **Hyperledger Fabric**, or **Ethereum** → think **Amazon Managed Blockchain** (a decentralized blockchain service). You do not need deep blockchain expertise for this exam.

### Lecture: Glue Overview

- **AWS Glue** is a managed **ETL (Extract, Transform, Load)** service — that's the key fact for the exam.
- **ETL** is used when datasets aren't in the right form/format for analytics — Glue is used to prepare and transform that data.
- Unlike traditional ETL (which requires managing servers), Glue is **fully serverless** — you focus only on the data transformation logic.

**Example workflow**
- Glue ETL sits "in the middle": it can **extract** data from sources like an S3 bucket and an RDS database → you write a script to **transform** the data within Glue → the transformed data is then **loaded** into a target such as Amazon Redshift for proper analytics.

**AWS Glue Data Catalog**
- Noted as likely **not on the exam**, but useful to know as part of the Glue family.
- A **catalog of your datasets** across your AWS infrastructure — stores metadata like column names, field names, field types, etc.
- Used by services such as **Athena, Redshift, and EMR** to discover datasets and build the proper schemas for them.

### Lecture: DMS Overview

- **DMS (Database Migration Service)**: used to migrate data from one database to another.
- **How it works**: an EC2 instance runs the DMS software, extracts data from a **source database**, and inserts it into a **target database** located elsewhere.
- Benefits: quick, secure, **resilient and self-healing** migration into AWS; the **source database remains available/online during the migration** — no downtime required.

**Types of migration**
| Type | Description | Example |
|---|---|---|
| **Homogeneous migration** | Source and target use the **same** database technology | Oracle → Oracle |
| **Heterogeneous migration** | Source and target use **different** database technologies; DMS is smart enough to convert the data accordingly | Microsoft SQL Server → Aurora |

> **Exam Tip**: anytime you see "migration of a database" → think **DMS**.

## Section: Databases & Analytics — Key Takeaways

**Most important concepts**
- AWS offers a wide range of **managed databases**, each optimized for a specific data model and use case — matching the right database to the right scenario is the core exam skill for this section.
- **Relational (SQL) databases**: RDS (multiple engines) and Aurora (AWS's cloud-native, faster, auto-growing option), used for **OLTP**.
- **NoSQL databases**: DynamoDB (key-value, serverless), DocumentDB (MongoDB-compatible, document-based), Neptune (graph).
- **Caching**: ElastiCache (general-purpose in-memory cache, Redis/Memcached) and DAX (DynamoDB-specific cache).
- **Analytics & data warehousing**: Redshift (OLAP data warehouse), EMR (Hadoop big-data clusters), Athena (serverless SQL over S3 data), QuickSight (BI dashboards), Glue (serverless ETL + Data Catalog).
- **Specialized databases**: Timestream (time series), Managed Blockchain (decentralized ledgers).
- **Migration**: DMS moves data between databases (same or different technologies), with the source remaining online throughout.
- Managed databases shift responsibility for provisioning, patching, backups, and monitoring from the customer to AWS.

**How the concepts relate**
- RDS/Aurora (OLTP, transactional) and Redshift (OLAP, analytical) represent two different purposes for structured/relational data — OLTP handles day-to-day transactions, while OLAP handles bulk analysis of historical data. Data often flows from an OLTP source (RDS) through an ETL step (**Glue**) into an OLAP target (**Redshift**) for analysis, and can then be visualized in **QuickSight**.
- RDS's three deployment options (**Read Replicas**, **Multi-AZ**, **Multi-Region**) address three different needs: scaling reads, surviving an AZ failure, and surviving a regional failure / reducing latency for global users — each with its own trade-offs (replica limits, passive vs. active use, replication cost).
- **ElastiCache** and **DAX** both reduce database read pressure via in-memory caching, but ElastiCache is general-purpose (works with RDS or other databases) while DAX is purpose-built exclusively for DynamoDB.
- **Athena**, **EMR**, and **Glue** all relate to processing data that lives in **S3**: Athena queries it directly with SQL, EMR runs full Hadoop-ecosystem big-data processing on it, and Glue prepares/transforms it (and catalogs its schema) for use by the others.
- **DynamoDB Global Tables** extend DynamoDB across regions with active-active replication, paralleling how RDS Multi-Region extends relational databases across regions (though DynamoDB's version allows writes in *any* region, unlike RDS Multi-Region's single-primary-write model).

**Key terminology to remember**
- OLTP vs. OLAP, SQL vs. NoSQL, structured vs. flexible schema
- RDS (engines: Postgres, MySQL, MariaDB, Oracle, SQL Server, IBM DB2), Aurora, Aurora Serverless
- Read Replica, Multi-AZ (failover), Multi-Region
- ElastiCache (Redis/Memcached), in-memory database
- DynamoDB (partition key, sort key, attributes), serverless, DAX, DynamoDB Global Tables, active-active replication
- Redshift (columnar storage, MPP engine), Redshift Serverless
- EMR (Hadoop cluster, Apache Spark, HBase, Presto, Flink)
- Athena (serverless SQL over S3, Presto engine)
- QuickSight (BI dashboards)
- DocumentDB (MongoDB-compatible)
- Neptune (graph database)
- Timestream (time series database)
- Managed Blockchain (Hyperledger Fabric, Ethereum)
- Glue (ETL, Glue Data Catalog)
- DMS (homogeneous vs. heterogeneous migration)

**Key distinctions/comparisons**
- **RDS vs. Aurora**: RDS runs familiar third-party engines as a managed service; Aurora is AWS's own cloud-optimized, faster (5x MySQL / 3x Postgres), auto-scaling-storage database, at a higher base cost.
- **Read Replica vs. Multi-AZ vs. Multi-Region**: scale reads (up to 15 replicas, same region) vs. failover for AZ outage (1 passive standby, same region) vs. disaster recovery/global low-latency reads (replicas in other regions, main region still handles writes).
- **ElastiCache vs. DAX**: general-purpose in-memory cache for various databases vs. cache built specifically for DynamoDB.
- **DynamoDB vs. RDS/Aurora**: NoSQL, single-table, no joins, serverless, key-value model vs. SQL, relational, joinable tables, provisioned instances.
- **DynamoDB vs. DocumentDB**: both NoSQL, but DynamoDB is key-value while DocumentDB is a MongoDB-compatible document database.
- **Redshift vs. RDS/Aurora**: OLAP/data warehousing/analytics (periodic loads, columnar storage) vs. OLTP/transactional (continuous reads/writes, row storage).
- **EMR vs. Redshift vs. Athena**: run a full Hadoop cluster for custom big-data processing vs. a dedicated SQL data warehouse vs. serverless ad-hoc SQL queries directly on S3 data (no infrastructure, no loading required).
- **Homogeneous vs. Heterogeneous migration (DMS)**: same database technology on both ends vs. different technologies (DMS handles the conversion).

**You should be able to explain:**
- The difference between relational (SQL) and NoSQL databases, and why each type exists.
- What RDS and Aurora are, their supported engines, and the performance/cost differences between them.
- The three RDS deployment options (Read Replicas, Multi-AZ, Multi-Region) and when to use each.
- What ElastiCache is and why/when you'd use it.
- The core features of DynamoDB (serverless, key-value, partition/sort keys), what DAX is for, and how DynamoDB Global Tables provide multi-region active-active replication.
- What Redshift is, how it differs from RDS/Aurora (OLAP vs. OLTP), and what Redshift Serverless offers.
- What EMR is used for and its relationship to Hadoop.
- What Athena is used for and how it differs from Redshift/EMR.
- What QuickSight is used for and which services it can visualize data from.
- What DocumentDB and Neptune are, and their respective data models (MongoDB-compatible documents vs. graphs).
- What Timestream and Managed Blockchain are used for.
- What Glue does (ETL + Data Catalog) and how it fits into a broader analytics pipeline.
- What DMS is used for, and the difference between homogeneous and heterogeneous migrations.
