## Section: Cloud Monitoring

### Lecture: CloudWatch Metrics & CloudWatch Alarms Overview

**CloudWatch Metrics**
- CloudWatch provides **metrics for every service in AWS**.
- A **metric** is a **variable to monitor** (e.g., `CPUUtilization`, `NetworkIn`).
- Metrics are **time-based** — every data point has a **timestamp**.
- To visualize many metrics at once, create a **CloudWatch dashboard**.

**The Billing metric (special case)**
- Represents the **total estimated charge for your entire account**.
- > **Exam Tip**: the Billing metric is **only available in us-east-1** (one region only). This can come up in the exam.
- Resets to zero at the start of each month.

**Common metrics by service**

| Service | Metrics available |
|---|---|
| **EC2 instances** | CPU Utilization, Status Checks, Network In/Out — **RAM is NOT an available metric** |
| **EBS volumes** | Disk read / disk write |
| **S3 buckets** | Bucket size (bytes), number of objects, number of requests |
| **Billing** | Total estimated charge (us-east-1 only, account-wide) |
| **Service Limits** | How much of a service API you have been using |
| **Custom** | You can **push your own custom metrics** if the metric you need doesn't exist |

**EC2 metric frequency**
- **Default: every 5 minutes.**
- **Detailed Monitoring** (more expensive): metrics **every 1 minute**.

**CloudWatch Alarms**
- Alarms are used to **trigger notifications for any metric** — when the metric crosses a **threshold**, the alarm fires an action.
- **Alarm actions:**
  - **Auto Scaling** — increase/decrease the ASG's desired EC2 instance count (this is how an ASG scales automatically).
  - **EC2 Actions** — stop, terminate, reboot, or recover an EC2 instance.
  - **SNS notifications** — send a notification into an SNS topic (e.g., email the team if CPU > 90%).
- Options when creating an alarm: statistic (sampling, percentage, max, min, average, etc.) and the **evaluation period** (5 min, 10 min, 1 hour, …).
- A **billing alarm** can be created on the CloudWatch **Billing metric** to be notified if spend exceeds e.g. $10 or $20.

**Alarm states (3)**

| State | Meaning |
|---|---|
| **OK** | Metric is within the threshold — everything is fine |
| **INSUFFICIENT_DATA** | Not enough data points to decide |
| **ALARM** | Metric breached the threshold — something is wrong |

### Lecture: CloudWatch Metrics & CloudWatch Alarms Hands On

- **Metrics console**: `CloudWatch → Metrics → All metrics` lists metrics grouped by service. AWS services publish metrics automatically (e.g., SQS queue metrics: number of messages received / deleted / sent / empty receives; EC2 → Per-Instance Metrics → CPU Utilization).
- **Creating an alarm (CloudWatch console)**: `All alarms → Create alarm` → select a metric (e.g., EC2 `CPUUtilization`) → choose the statistic (average) and period (5 minutes) → set the condition (e.g., **greater than 80%**) → choose which state to treat as the alarm → configure the action (send a notification to an SNS topic, which then emails the subscriber) → name and create. The graph shows the threshold as a **red line** and the actual metric values as data points.
- **Other alarm actions available**: Auto Scaling actions, EC2 actions, Systems Manager actions.
- **Creating an alarm from the EC2 console**: `EC2 → instance → Monitoring` tab shows CPU utilization, status checks, etc. Under the instance's **alarm status** column, the **+** button creates a CloudWatch alarm directly. Examples built in the demo:
  - **Recover** the instance when a **Status check failed: system** metric triggers.
  - **Reboot** the instance if **CPU utilization > 95% for 3 consecutive 5-minute periods** (assumes the instance is stuck in a CPU loop).
- Multiple alarms can be attached to the same EC2 instance.
- **Billing alarm**: the *billing* section only appears in the console after switching the region to **us-east-1**. Create alarm → metric **Estimated Charges (USD)** → e.g., greater than 8 USD → notify a new SNS topic. Because **almost every AWS resource is scoped by region**, the SNS topic must be recreated in us-east-1.
- Cleanup: delete the alarms (including the billing alarm in us-east-1) and terminate the EC2 instance.

### Lecture: CloudWatch Logs Overview

- **CloudWatch Logs** collects **log files**.
- A **log file** is text an application running on a server writes about what it is doing (actions performed for a user, cleanups, errors, …). Users read logs to **troubleshoot** what the application did.
- **Log sources** that can send logs to CloudWatch Logs:
  - **Elastic Beanstalk**
  - **ECS**
  - **Lambda**
  - **CloudTrail**
  - **CloudWatch Logs agents** (installed on an EC2 instance or an **on-premises** server)
  - **Route 53** (logging DNS queries)
- Capabilities: **real-time monitoring** of logs so you can react to what's happening, and **adjustable retention** — keep logs for 1 week, 30 days, a year, or **indefinitely**.

**How it works for EC2**
- **By default, EC2 instances send NO log files to CloudWatch Logs.**
- You must install the **CloudWatch Logs agent** on the instance; the agent pushes the chosen log files to the CloudWatch Logs service.
- The EC2 instance needs an **instance role with the correct IAM permissions** to send log data to CloudWatch Logs.
- The log agent is a **hybrid agent** — it also works on **on-premises servers**, so logs from both EC2 and on-premises can be centralized in CloudWatch Logs.

---

### Lecture: CloudWatch Logs Hands On

- **Log groups**: `CloudWatch → Log groups`. A Lambda function that has run automatically created a log group (e.g., `/aws/lambda/demo-lambda`).
- **Structure**: a **log group** contains one or more **log streams**; a log stream contains the **log lines** produced by an execution (e.g., request ID, "loading function", printed values, end of request, report).
- Any log line printed by the Lambda function appears in CloudWatch Logs — adding a `print` statement, deploying, and re-testing produces a **new log stream** containing the extra line.
- **Exceptions are captured too**: raising an exception in the function makes the exception appear in a new log stream, so you can see why the function failed.
- This applies to **any** logs you want in CloudWatch Logs, not only Lambda. Use it to troubleshoot program/application errors, and to do log analytics and monitoring.

### Lecture: EventBridge Overview (formerly CloudWatch Events)

- **Amazon EventBridge** was previously called **CloudWatch Events** — if you see "CloudWatch Events" online, think EventBridge (EventBridge is the new name).
- Purpose: **react to events happening within your AWS account**.

**Use case 1 — Schedule cron jobs**
- Create a rule such as "every 1 hour, create an event" that **triggers a Lambda function** running a script → effectively a **serverless cron job**.

**Use case 2 — React to a service doing something**
- Example: alert the security team whenever someone signs in with the **root user** (root should be used rarely or never). React to the **IAM root user sign-in event** → send to an **SNS topic** with an email subscription → the team receives an email on every root sign-in.

**Sources and destinations**
- **Sources** can be almost anything: EC2 instances, CodeBuild, S3 events, Trusted Advisor, and of course a **schedule**.
- **Destinations** are many kinds of targets — compute (**Lambda**), integration (**SNS**, **SQS**), orchestration, maintenance, and more.

**Event buses (3 types)**

| Event bus | What it carries |
|---|---|
| **Default event bus** | Events from **within AWS services**, plus your own schedules |
| **Partner event bus** | Events from **AWS partners** (e.g., Zendesk, Datadog) — lets you react to events happening **outside** AWS |
| **Custom event bus** | Events sent by **your own custom applications** — fully customizable integrations |

**Additional capabilities**
- **Schema Registry** — model the event schema (structure, data types) to see what an event looks like.
- **Archive & replay** — archive all events sent to an event bus **indefinitely or for a set period**, and later **replay** the archived events.
- For the Cloud Practitioner exam, remember **conceptually** what EventBridge is.

---

### Lecture: EventBridge Hands On

- **EventBridge Schedule** (the current AWS-supported way; the old "Scheduled rule" is legacy): create a schedule, e.g. `InvokeLambdaFunctionEveryOneHour`.
  - Schedule types: **one-time** or **recurring**. Recurring can be **cron-based** (cron expression) or **rate-based** (e.g., every 1 hour).
  - Extra options: flexible time window, daylight-saving handling.
  - **Target**: templated targets (or any defined API) — here, invoke the Lambda function `demo-lambda`; optionally pass a JSON input document, configure retries, dead-letter queues, encryption.
  - EventBridge Scheduler creates an **IAM role** with permission to invoke the function.
- **EventBridge Rule with event pattern** (react to things happening in the account):
  - Example 1 — **Console sign-in alert**: source = AWS Service Events → **AWS Console Sign In via CloudTrail**; target = **SNS topic**; rule named `DemoSignInAlert` on the **default event bus**. An **execution role** is created so EventBridge can publish to the SNS topic.
  - For any event you can inspect the **schema** (tree/code view), get a **sample event**, and **test the event pattern**.
  - Example 2 — **EC2 instance terminated alert**: source = **EC2 Instance State-change Notification** with an **event pattern filter** on `state` equals `terminated`; target = SNS topic; rule named `InstanceTerminatedNotification`.
- Rules can be **enabled or disabled**.

### Lecture: CloudTrail Overview

- **AWS CloudTrail** provides **governance, compliance and audit** for your AWS account.
- It is **enabled by default** in every account and records a **history of all API calls and events** made in the account.
- **Everything is logged**, regardless of how it was done:
  - Actions in the **Console**
  - Calls via the **SDK**
  - Commands via the **CLI**
  - **Service activity**
  - Activity of **IAM users and IAM roles**
- For audit and security, CloudTrail logs can be sent to **two destinations** for **long-term retention**:
  - **CloudWatch Logs**
  - **Amazon S3**
- A **trail** can be applied to **all regions** (monitor activity everywhere) or scoped to a **single region**.
- > **Exam Tip**: if a resource was deleted and you need to know **what** was deleted, **who** did it and **when** — the answer is **CloudTrail**. Anytime an **API call** must be looked up, CloudTrail is the right answer.

---

### Lecture: CloudTrail Hands On

- CloudTrail intercepts any API call or user activity in the account.
- **Event history** (left panel) shows **management events for the last 90 days** — all API calls made over time in the account.
- Demo: terminating an EC2 instance, then after ~5 minutes the **`TerminateInstances` API call** appears in CloudTrail with the **event source** (EC2), where it was done from, the **access key used**, the **region**, and the **full event** detail.

### Lecture: X-Ray Overview

**The problem X-Ray solves**
- Traditional "debugging in production": test locally, add log statements everywhere, redeploy, and hope to find the problem.
- Logs come from **different services and different applications**, so **log analysis is very hard** — everything has to be combined manually.
- A single **monolith** is relatively easy to debug; **distributed services** (connected via SQS queues, SNS topics, decoupled components) are very hard to trace. There is **no common view of the entire architecture**.

**What AWS X-Ray does**
- Provides **tracing** and **visual analysis** of your application.
- Once enabled on your services, it gives a full picture of what each service is doing, where they fail, and their performance; a single failing request can be **visualized in the X-Ray console**.

**X-Ray advantages**
- Troubleshoot **performance bottlenecks**.
- Understand **dependencies in a microservice architecture**.
- **Pinpoint a service issue** with tracing.
- Review a **specific request's behavior** and find its errors and exceptions.
- Know whether you are **meeting your SLA** (replying on time to all requests).
- See **where throttling / slowdown** is happening — in which service.
- Identify **which users are impacted** by an outage.
- > **Exam Tip**: when you see **distributed tracing**, **troubleshooting**, or **service graph** → think **X-Ray**.

### Lecture: AWS Health Dashboard

The AWS Health Dashboard has **two parts**:

| Part | Formerly called | What it shows |
|---|---|---|
| **Service History** (Service health) | AWS **Service** Health Dashboard | Health of **all services in all regions** — general information, day-by-day history, with an **RSS feed** to subscribe to |
| **AWS Health Dashboard — Your Account** | AWS **Personal** Health Dashboard (**PHD**) | **Alerts and remediation guidance** for AWS events that **impact you directly** — the performance and availability of the services and resources **you actually use** |

**Your Account dashboard details**
- Gives **relevant and timely information** plus notifications so you can **proactively** prepare for **scheduled maintenance activities**.
- Can **aggregate data for your entire AWS Organization** (organizational view).
- It is a **global service** and shows the outages that directly impact you, plus an **event log** of past events (e.g., an EC2 issue in us-east-2 that could have impacted you).
- Access: top-right corner of the console, next to the bell icon.

---

### Lecture: AWS Health Dashboard - Hands On

- **Service History**: service health of all AWS services **by region and by day** (e.g., check Amazon EventBridge Scheduler for North America over recent days). Open issues affecting many customers appear here. This is **general information**.
- **Your account health**: shown under **Open and Recent Issues** — a **bell icon** appears when there is an open issue. Tabs cover **open issues**, **Scheduled Changes** (e.g., planned maintenance on EBS volumes that will impact you), and **Other Notifications**.
- **Event Log**: past issues that were opened and closed, with start time and last update time — only issues that applied to **you** because you were using the underlying services. Each issue shows start/resolution time, description, impact, and **Affected Resources**.
- **Organizational Health**: configure organization-wide visibility into the health of all your accounts.
- For automation, **integrate Health with Amazon EventBridge**.

### Lecture: Cloud Monitoring Summary

**CloudWatch — multiple flavors**
- **CloudWatch Metrics** — monitor the performance of AWS services and **billing** metrics.
- **CloudWatch Alarms** — automate notifications when a metric goes outside a specific range; can perform **EC2 actions** (e.g., reboot) or send notifications to **SNS** when a metric exceeds a limit.
- **CloudWatch Logs** — collect and **centralize** log files from EC2 instances, servers and Lambda functions.
- **CloudWatch Events / EventBridge** — react to events in AWS, or trigger a rule on a **specific schedule**.

**Auditing**
- **CloudTrail** — audit **API calls** made within your account.
- **CloudTrail Insights** — automated analysis of your CloudTrail events.

**Tracing**
- **AWS X-Ray** — trace requests through **distributed applications**; helpful for **performance analysis** and **root cause analysis**, especially when applications talk to one another and errors occur.

**Health**
- **AWS Health Dashboard** — status of all AWS services across all regions.
- **AWS Account Health Dashboard** — AWS events that impact **your specific infrastructure** only.

## Section: Cloud Monitoring — Key Takeaways

**Most important concepts**
- **CloudWatch** is the umbrella monitoring service with three distinct pieces: **Metrics** (numeric variables over time, per service), **Alarms** (thresholds on metrics that trigger actions), and **Logs** (centralized collection of application/service log files).
- **CloudWatch Metrics** exist for every AWS service; EC2 exposes CPU, status checks and network but **not RAM**, and delivers metrics every **5 minutes** by default or every **1 minute** with **Detailed Monitoring**. Custom metrics can be pushed.
- The **Billing metric** is account-wide and exists **only in us-east-1** — a **billing alarm** must therefore be created in us-east-1.
- **CloudWatch Alarms** have three states (**OK / INSUFFICIENT_DATA / ALARM**) and can act on **Auto Scaling** (scale in/out), **EC2** (stop, terminate, reboot, recover), or **SNS** (notifications).
- **CloudWatch Logs** requires the **CloudWatch Logs agent** on EC2/on-premises servers (EC2 sends nothing by default) plus an **IAM instance role**; retention is configurable from days to indefinitely; structure is **log group → log stream → log lines**.
- **EventBridge** (formerly CloudWatch Events) is the **event router**: schedule-driven (serverless cron) or event-pattern-driven (react to AWS/partner/custom events) with many possible targets. Three bus types: **default**, **partner**, **custom**.
- **CloudTrail** is the **audit/governance** service — enabled by default, records **who did what, when** for every API call (Console, CLI, SDK, service activity), and can ship logs to **CloudWatch Logs or S3** for long-term retention. **CloudTrail Insights** analyzes those events automatically.
- **X-Ray** provides **distributed tracing** and a **service graph** for microservice architectures — bottlenecks, dependencies, per-request behavior, SLA compliance, throttling, impacted users.
- The **AWS Health Dashboard** separates **global service health** (Service History) from **events impacting your own account/resources** (Your Account, formerly Personal Health Dashboard), with an organizational view and EventBridge integration.

**How the concepts relate**
- Metrics feed **Alarms**, and Alarms drive **automation** — this is exactly the mechanism behind **Auto Scaling Group** scaling and EC2 self-healing (recover/reboot).
- Alarms typically publish to **SNS**, which then fans the notification out to email or other subscribers — monitoring depends on the integration services from the previous section.
- **CloudTrail** can send its events into **CloudWatch Logs**, and **EventBridge** can match CloudTrail events (e.g., "AWS Console Sign In via CloudTrail") to trigger alerts — so audit, logging and eventing chain together.
- **CloudWatch Logs** answers "what did my application say?", **CloudTrail** answers "who called which API?", **X-Ray** answers "where in my distributed system did the request slow down or fail?", and the **Health Dashboard** answers "is the problem AWS's, and does it affect me?".

**Key terminology to remember**
- Metric, dashboard, timestamp, Detailed Monitoring (1 minute) vs. default (5 minutes), custom metrics, Billing metric (us-east-1 only), Service Limits metric
- Alarm threshold, evaluation period, alarm states OK / INSUFFICIENT_DATA / ALARM, billing alarm, alarm actions (Auto Scaling, EC2, SNS, Systems Manager)
- CloudWatch Logs agent (hybrid: EC2 + on-premises), instance role, log group, log stream, retention
- EventBridge (formerly CloudWatch Events), rule, event pattern, schedule (cron-based vs. rate-based), default / partner / custom event bus, Schema Registry, archive & replay
- CloudTrail, trail, management events, 90-day event history, CloudTrail Insights
- X-Ray: tracing, service graph, distributed tracing, SLA, throttling
- AWS Health Dashboard: Service History (formerly Service Health Dashboard) vs. Your Account (formerly Personal Health Dashboard), Scheduled Changes, Event Log, Affected Resources, Organizational Health

**Key distinctions/comparisons**
- **CloudWatch Metrics vs. CloudWatch Logs**: numeric variables tracked over time vs. textual log files collected from applications and services.
- **CloudWatch (Logs/Metrics) vs. CloudTrail**: application/service performance and output vs. **API call auditing** ("who deleted this resource?").
- **CloudTrail vs. X-Ray**: audit trail of API calls for governance/compliance vs. **request tracing** through a distributed application for performance and root-cause analysis.
- **Default EC2 monitoring vs. Detailed Monitoring**: 5-minute granularity, cheaper vs. 1-minute granularity, more expensive.
- **EC2 metrics available vs. not available**: CPU, status checks, network **are** available; **RAM is not**.
- **EventBridge schedule vs. event pattern rule**: time-driven (serverless cron job) vs. reaction to something happening in the account.
- **Default vs. partner vs. custom event bus**: AWS-internal events vs. third-party SaaS partner events vs. your own application events.
- **Service History vs. Your Account Health Dashboard**: general status of all AWS services in all regions vs. only the events/outages that impact your own resources, with remediation guidance.
- **CloudWatch Logs destinations for CloudTrail vs. S3**: both provide long-term retention; S3 for durable storage, CloudWatch Logs for real-time monitoring/analysis.

**You should be able to explain:**
- What a CloudWatch metric is, which metrics EC2 exposes (and that RAM is not one), the default vs. detailed monitoring intervals, and why the Billing metric is special.
- How a CloudWatch Alarm works: threshold, evaluation period, the three alarm states, and the actions it can trigger (Auto Scaling, EC2 stop/terminate/reboot/recover, SNS).
- Why a billing alarm must be created in us-east-1, and that AWS resources (like SNS topics) are region-scoped.
- What CloudWatch Logs collects, which sources can send logs, and why an EC2 instance needs the CloudWatch Logs agent plus an IAM role.
- What EventBridge is (and its old name), the two main rule styles (schedule vs. event pattern), the three event bus types, and typical targets.
- What CloudTrail records, that it is on by default, where its logs can be sent, and why it is the answer to "who did what, when" questions.
- What X-Ray is for, and the specific problems it solves in a microservices/distributed architecture.
- The difference between the AWS Health Dashboard's Service History view and the Your Account (Personal Health Dashboard) view.
