## Section: Amazon S3

### Lecture: S3 Overview

- Amazon **S3** is one of AWS's main building blocks — advertised as **infinitely scaling storage**. Much of the web relies on S3, both directly (as a backbone for websites) and indirectly (many AWS services integrate with it).

**Use cases**
- Backup and storage (files, disks, etc.)
- Disaster recovery (replicate data to another region so it survives a regional outage)
- Archival (store files cheaply and retrieve them later)
- Hybrid cloud storage (extend on-premises storage into the cloud)
- Hosting applications and media (video, images)
- Data lakes and big data analytics
- Software update delivery
- Static website hosting
- Real-world examples: NASDAQ stores seven years of data in S3 Glacier (the archival service); Sysco runs analytics and gains business insights from data stored in S3.

**Buckets**
- S3 lets you store objects/files into **buckets** — essentially directories in the cloud.
- Buckets are defined at the **region level** — you create a bucket for a specific AWS region, even though the S3 console has a global interface showing buckets from all regions.
- **Naming**: previously, bucket names had to be **globally unique** across all AWS accounts/regions. A newer feature, the **Account Regional Namespace**, now lets you reuse the same bucket name across regions and accounts — AWS automatically appends a suffix (based on your account and region) to guarantee uniqueness.
- **Naming constraints**: no uppercase letters, no underscores, not formatted as an IP address; must start with a lowercase letter or number; must not start with prefix `xn--`; must not end with suffix `-s3alias`. In short: keep it simple with letters and numbers.

**Objects**
- Objects are files, identified by a **key** — the full path of the file within the bucket.
  - Example: for `my_folder1/another_folder/my_file.txt`, the key is the entire path.
  - The key is composed of a **prefix** (e.g., `my_folder1/another_folder`) and an **object name** (e.g., `my_file.txt`).
  - S3 has **no true concept of directories** — the console UI makes it look like there are folders, but everything is actually just a (very long) key containing slashes.
- The **value** is the content/body of the object.
  - **Max object size: 5 terabytes.**
  - If a file is **larger than 5 gigabytes**, you must use **multi-part upload**, splitting it into multiple parts (e.g., a 5 TB file would need to be uploaded in at least 1,000 parts of 5 GB each).
- Objects can have:
  - **Metadata** — a list of key/value pairs, set by the system or the user, describing the file.
  - **Tags** — Unicode key/value pairs (up to 10) useful for security and lifecycle management.
  - A **Version ID**, if versioning is enabled on the bucket.

### Lecture: S3 Hands On

- Creating a bucket: choose a region (e.g., Europe/Ireland — `eu-west-1`); choose a **bucket type** — **General Purpose** (recommended for most access patterns) vs. **Directory** (for low-latency use cases, not used in this demo).
- **Namespace** options when naming: **Global** (the traditional fully-unique-name approach — demonstrated failing when a name like "test" is already taken) vs. **Account Regional Namespace** (lets you freely reuse simple names like "demo," since AWS appends a suffix based on your account number and region to guarantee uniqueness) — this is now the **recommended approach**.
- Other bucket settings (left as defaults in the demo):
  - **Object Ownership**: ACLs disabled (recommended, a security setting).
  - **Block Public Access**: left enabled — blocks all public access for maximum security.
  - **Bucket Versioning**: disabled for now (covered in a later lecture).
  - **Default encryption**: server-side encryption with an Amazon S3–managed key, with **Bucket Key** enabled.
- Buckets are created **per region**, but the console's bucket list view shows buckets across **all regions** (searchable).
- **Uploading objects**: use the Upload button to add files (e.g., `coffee.jpg`). Once uploaded, clicking the object shows its properties (size, type) and an **Object URL**.
- **Opening an object**: clicking "Open" in the console works (since you're authenticated), and shows the file.
- **Public URL vs. pre-signed URL**:
  - Visiting the plain **Object URL** directly gives an **AccessDenied** error — the bucket/object isn't public.
  - The "Open" link actually uses an **S3 pre-signed URL** — a long URL containing an embedded **signature/credentials** proving who is making the request, which is why it works only for the signed-in user.
  - Making the object truly public (so the plain public URL works) is covered in a later lecture.
- **Folders**: can be created in the console (e.g., an "images" folder) and used to organize uploads — behaves similarly to a familiar cloud storage UI (e.g., Google Drive/Dropbox), even though S3 doesn't have real folders under the hood.
- **Deleting**: a folder can be deleted (which deletes everything inside it) by typing "permanently delete" to confirm.

### Lecture: S3 Security: Bucket Policy

**Ways to secure Amazon S3**
| Method | Description |
|---|---|
| **User-based (IAM Policies)** | Authorize which API calls a specific IAM user is allowed to make. |
| **Resource-based (S3 Bucket Policies)** | Bucket-wide rules assigned directly from the S3 console — can allow a specific user, or a user from **another account** (cross-account access), or make a bucket public. |
| **Object Access Control List (ACL)** | Finer-grained, per-object security; can be disabled. |
| **Bucket ACL** | Less common, bucket-level ACL; can also be disabled. |
| **Encryption** | Encrypt objects using encryption keys as an additional layer of security. |

- The most common way to secure an S3 bucket today is via **Bucket Policies**.
- An IAM principal can access an S3 object if: the **IAM permissions allow it**, OR the **resource (bucket) policy allows it** — AND there is **no explicit deny** anywhere in the applicable policies.

**Bucket Policy structure (JSON)**
- **Resource** — which bucket(s)/object(s) the policy applies to (e.g., `arn:aws:s3:::example-bucket/*` applies to every object in the bucket, via the `*` wildcard).
- **Effect** — `Allow` or `Deny`.
- **Action** — the specific API call(s) allowed/denied (e.g., `GetObject`).
- **Principal** — who the policy applies to (e.g., `*` = anyone).
- Example: `Effect: Allow`, `Principal: *`, `Action: GetObject`, `Resource: example-bucket/*` → grants **public read** access to every object in the bucket.

**Common bucket policy use cases**
- Grant **public access** to a bucket.
- Force objects to be **encrypted at upload**.
- Grant access to **another AWS account**.

**Access scenarios**
| Scenario | Mechanism |
|---|---|
| A website visitor (public/anonymous user) needs to access files in your bucket | Attach an S3 **Bucket Policy** allowing public access |
| An IAM user within your account needs S3 access | Attach an **IAM policy/permission** to that user |
| An EC2 instance needs S3 access | Use an **IAM Role** attached to the instance (IAM users are not appropriate for this) |
| A user in **another AWS account** needs access (cross-account) | Attach an S3 **Bucket Policy** granting cross-account access to that specific IAM user |

**Block Public Access settings**
- A separate, bucket-level (or account-level) setting, enabled **by default** when creating a bucket.
- Acts as an extra layer of security to prevent data leaks: even if a Bucket Policy would technically make the bucket public, **Block Public Access will override it and keep the bucket private** if left enabled.
- If you know a bucket (or all your buckets) should never be public, leave this setting on — it protects against an accidental public bucket policy. It can also be set at the **account level** for all buckets.

---

### Lecture: S3 Security: Bucket Policy Hands On

- **Step 1**: disable "Block Public Access" at the bucket level (Permissions tab → Edit → untick) — described as a **dangerous action** to only take when you deliberately want a public bucket.
- **Step 2**: create a bucket policy using the **AWS Policy Generator**:
  - Type: S3 Bucket Policy.
  - Effect: Allow.
  - Principal: `*` (anyone).
  - Action: `GetObject`.
  - Amazon Resource Name (ARN): the bucket's ARN + `/` + `*` (to apply to every object inside the bucket).
  - Generate the policy JSON and paste it into the bucket's Bucket Policy editor, then save.
- Once applied, the object's **plain public URL** (e.g., for `coffee.jpg`) becomes fully accessible without needing a pre-signed URL — proving the bucket and its objects are now public.

### Lecture: S3 Website Overview

- S3 can **host static websites**, accessible over the internet via a website URL that depends on the AWS region (URL formats differ slightly by using a dash vs. a dot, but this detail doesn't need to be memorized).
- Setup: put website files (HTML, images, etc.) in a bucket, then **enable static website hosting** — this generates a corresponding website URL.
- This will **not work** unless **public reads** are enabled on the bucket — which is exactly why S3 Bucket Policies (previous lecture) matter here.
- > If you get a **403 Forbidden** error after enabling static website hosting, it means the bucket is not public — you must attach a Bucket Policy that allows public reads.

---

### Lecture: S3 Website Hands On

- Upload an additional file (e.g., `beach.jpg`) to the bucket.
- Enable static website hosting: Properties → scroll to **Static website hosting** → Edit → enable, specify an **index document** (e.g., `index.html`).
  - A warning notes that for the website endpoint to work, **all content must be publicly readable** (already handled via the earlier public bucket policy).
- Upload the specified `index.html` file (must exist for the site to load correctly).
- After saving, the **Bucket website endpoint** URL appears under Properties → Static website hosting.
- Visiting this endpoint loads the `index.html` content (e.g., "I love coffee. Hello world!") along with any linked images (e.g., `coffee.jpg`), confirming the bucket is functioning as a static website, thanks to the earlier public bucket policy.

### Lecture: S3 Versioning Overview

- **Versioning** allows updating files in an S3 bucket **safely**, by keeping multiple versions of an object.
- Must be **enabled at the bucket level**.
- Once enabled: uploading a file to an existing key creates **version 1**; re-uploading (overwriting) the same key creates **version 2**, then **version 3**, and so on.
- **Best practice**: enable versioning on your buckets. Benefits:
  - Protects against **unintended deletes** — deleting a file actually just adds a **delete marker**, so previous versions can be restored.
  - Enables easy **rollback** to a previous version (e.g., restoring the state from two days ago).
- Notes:
  - Any file that existed **before** versioning was enabled will show a version ID of **null**.
  - **Suspending** versioning does **not** delete previous versions — it's a safe operation.

---

### Lecture: S3 Versioning Hands On

- Enable versioning: Properties → Bucket Versioning → Edit → Enable.
- **Overwriting demo**: editing and re-uploading `index.html` (changing "I love coffee" to "I really love coffee") overwrites the file and the live website reflects the new content.
- **"Show versions" toggle**: reveals version IDs for all objects.
  - Objects uploaded **before** versioning was enabled (e.g., the original `beach.jpg`, `coffee.jpg`) show a **null** version ID.
  - `index.html` now shows two versions: the original (null) and the newly uploaded one (with a real version ID).
- **Rolling back**: with "Show versions" enabled, select the older version ID of `index.html` and delete the newer version — this is a **permanent delete of a specific version ID** (destructive, requires typing "permanently delete" to confirm, and **cannot be undone**). After this, the website reverts to showing "I love coffee."
- **Delete marker demo**: with "Show versions" disabled, deleting `coffee.jpg` (typing just "delete," not "permanently delete") does **not** actually erase the underlying object — it adds a **delete marker** on top of it.
  - The live website then fails to show the image (a forced refresh shows it's unavailable; visiting the object URL directly gives a **404 Not Found**).
  - Enabling "Show versions" reveals the delete marker sitting on top of the original (still-present) object.
  - **Restoring**: deleting the **delete marker itself** (permanently) restores the previous version, and the image becomes visible again on the website.

### Lecture: S3 Replication Overview

- Two flavors of Amazon S3 Replication:
  - **CRR** — Cross-Region Replication (source and destination buckets are in **different** regions).
  - **SRR** — Same-Region Replication (source and destination buckets are in the **same** region).
- **Requirements**:
  - **Versioning must be enabled** on both the source and destination buckets.
  - Buckets **can** belong to different AWS accounts.
  - Replication is **asynchronous** — it happens automatically in the background.
  - You must grant the S3 service the proper **IAM permissions** to read from the source and write to the destination bucket.

**Use cases**
| Type | Use cases |
|---|---|
| CRR (Cross-Region) | Compliance requirements; providing lower-latency access to data in another region; replicating data across accounts |
| SRR (Same-Region) | Aggregating logs from multiple S3 buckets; live replication between production and test environments |

---

### Lecture: S3 Replication Hands On

- Create an **origin bucket** (e.g., "S3 Stephane bucket origin V2") in one region (e.g., `eu-west-1`) with **versioning enabled**.
- Create a **target/replica bucket** (e.g., "S3 Stephane bucket replica V2") — its region can be the same (SRR) or different (CRR, e.g., `us-east-1`) — also with **versioning enabled**.
- Upload a test file to the origin bucket (e.g., `beach.jpeg`) **before** setting up replication — this file will **not** be replicated automatically (replication only applies going forward, from the moment the rule is created).
- **Create a Replication Rule** (Management tab → Replication rules → Create):
  - Enable the rule; scope: apply to all objects.
  - Destination: choose the target bucket (same account or another account) — AWS auto-detects if this makes it CRR or SRR based on region.
  - IAM Role: create a new role to grant the necessary permissions.
  - Prompt: "Replicate existing objects?" — this is a **separate feature** (an **S3 Batch Operation**) from live replication; answering "No" here means only future uploads get replicated.
- **Verifying replication**: uploading a new file (e.g., `coffee.jpeg`) to the origin bucket results in it appearing in the target bucket after a short delay (~5–10 seconds in the demo) — including the **same version ID** as in the origin bucket, since version IDs are replicated too.
- Uploading a new version of an existing file (e.g., re-uploading `beach.jpeg`) also replicates that new version to the target bucket, again preserving the version ID.

### Lecture: S3 Storage Classes Overview

**The seven storage classes** (must know for the exam):
1. Amazon S3 Standard – General Purpose
2. Amazon S3 Standard-Infrequent Access (Standard-IA)
3. Amazon S3 One Zone-Infrequent Access (One Zone-IA)
4. S3 Glacier Instant Retrieval
5. S3 Glacier Flexible Retrieval
6. S3 Glacier Deep Archive
7. Amazon S3 Intelligent-Tiering

- You choose an object's storage class at creation, can change it manually afterward, or use **S3 Lifecycle configurations** to move objects automatically between classes over time.

**Durability vs. Availability**
- **Durability**: how likely an object is to be lost. S3 offers **11 nines (99.999999999%)** durability across **all** storage classes — on average, if you store 10 million objects, you'd expect to lose a single object once every 10,000 years.
- **Availability**: how readily accessible the service is — this **varies by storage class**. E.g., S3 Standard has **99.99%** availability (~53 minutes of downtime per year).

**Storage classes in detail**

| Class | Availability | Key characteristics | Use cases |
|---|---|---|---|
| **S3 Standard** | 99.99% | Frequently accessed data; low latency, high throughput; can sustain the concurrent loss of 2 facilities | Big data analytics, mobile and gaming applications, content distribution |
| **S3 Standard-IA** | 99.9% | Infrequently accessed but needs rapid access when needed; lower storage cost than Standard, but a retrieval cost applies | Disaster recovery, backups |
| **S3 One Zone-IA** | 99.5% | High durability within a **single AZ only**; data is lost if that AZ is destroyed | Storing secondary copies of backups (e.g., of on-premises data), or data you can recreate |
| **S3 Glacier Instant Retrieval** | — | Millisecond retrieval; minimum storage duration **90 days** | Archival data accessed rarely (e.g., quarterly) but needing instant access |
| **S3 Glacier Flexible Retrieval** (formerly "S3 Glacier") | — | Three retrieval speed tiers: **Expedited** (1–5 minutes), **Standard** (3–5 hours), **Bulk** (5–12 hours, free); minimum storage duration **90 days** | Backups you're willing to wait a bit to retrieve |
| **S3 Glacier Deep Archive** | — | Long-term storage; two retrieval tiers: **Standard** (12 hours), **Bulk** (48 hours); lowest cost; minimum storage duration **180 days** | Long-term archives where retrieval time isn't critical |
| **S3 Intelligent-Tiering** | — | Automatically moves objects between access tiers based on usage patterns; small monthly monitoring/auto-tiering fee; **no retrieval charges** | Data with unknown or changing access patterns |

**S3 Intelligent-Tiering access tiers**
| Tier | Trigger | Automatic? |
|---|---|---|
| Frequent Access | Default tier | Automatic |
| Infrequent Access | Not accessed for 30 days | Automatic |
| Archive Instant Access | Not accessed for 90 days | Automatic |
| Archive Access | Configurable, 90 to 700+ days | Optional |
| Deep Archive Access | Configurable, 180 to 700+ days | Optional |

- Note from the instructor: you are **not** expected to memorize exact numbers (durability %, minimum durations, pricing) — the goal is to understand what each class represents and when to use it.

### Lecture: S3 Storage Classes Hands On

- When uploading an object, you can choose its **Storage Class** directly (Standard, Intelligent-Tiering, Standard-IA, One Zone-IA, the three Glacier tiers, and a deprecated "**Reduced Redundancy**" tier that isn't covered in the course).
- The storage class of an existing object **can be changed after upload**: Properties → edit Storage Class → choose a new class (e.g., moving from Standard-IA to One Zone-IA, then to Glacier Instant Retrieval, then to Intelligent-Tiering).
- **Automating transitions with Lifecycle Rules**: Management tab → Create lifecycle rule (e.g., "DemoRule") → apply to all objects → define transitions for **current versions**, e.g.:
  - Move to Standard-IA after 30 days.
  - Move to Intelligent-Tiering after 60 days.
  - Move to Glacier Flexible Retrieval after 180 days.
- Lifecycle rules let you automate moving objects between storage tiers over time without manual intervention.

### Lecture: S3 Express One Zone

- **S3 Express One Zone** is a distinct, high-performance storage class for a **single Availability Zone**.
- Objects are stored in a special kind of bucket called a **directory bucket** (rather than a standard S3 bucket) — located in a single AZ of your choosing, instead of being distributed/replicated across multiple AZs.
- **Performance**: can handle hundreds of thousands of requests per second with **single-digit millisecond latency** — about **10x the performance of S3 Standard**, at roughly **50% lower cost**.
- **Durability** remains high, but **availability is lower** than the standard classes, since there's no cross-AZ replication — if a problem occurs in that AZ, you're directly affected.
- Key idea: **co-locate storage and compute** in the same Availability Zone to reduce latency and potentially reduce networking costs.
- **Use cases**: latency-sensitive applications, data-intensive applications, AI/ML training, financial modeling, media processing, and high-performance computing.
- Integrates well with data services such as **SageMaker Model Training, Athena, EMR, and Glue**.

### Lecture: S3 Encryption

| Type | Description |
|---|---|
| **Server-side encryption** | The default: the user uploads an object, and Amazon S3 itself encrypts it upon arrival in the bucket. The "server" (S3) performs the encryption. **On by default.** |
| **Client-side encryption** | The user encrypts the file themselves ("locks" it) before uploading it to the bucket. |

- Both models exist in AWS, but **server-side encryption is always on by default**.

### Lecture: IAM Access Analyzer for S3

- **IAM Access Analyzer for S3** is a **monitoring feature** ensuring that only the intended people have access to your S3 buckets.
- How it works: analyzes **Bucket Policies**, **S3 ACLs**, and **S3 Access Point Policies**, then surfaces:
  - Which buckets are **publicly accessible**.
  - Which buckets have been **shared with other AWS accounts**.
- You review the findings and decide whether the sharing is expected/normal, or a potential **security issue** requiring action.
- This feature is powered by the broader **IAM Access Analyzer**, which finds resources in your account shared with other entities.

### Lecture: AWS Snow Family Overview

- **AWS Snowball**: a highly secure, portable device used to collect/process data at the edge and migrate large volumes of data in and out of AWS.
- Two types of Snowball Edge devices:

| Device | Storage | Purpose |
|---|---|---|
| Snowball Edge **Storage Optimized** | 210 TB | Data migration/storage |
| Snowball Edge **Compute Optimized** | 28 TB | Edge computing |

**Data migration use case**
- Transferring large amounts of data over a network can take a very long time — e.g., transferring 100 TB over a 1 Gbps connection would take **12 days**.
- Challenges that make Snowball attractive: slow/limited connectivity, limited bandwidth, high network costs, shared bandwidth with other applications, unstable connections — generally, if a transfer would take **over a week**, consider Snowball.
- Process: AWS ships you a physical Snowball device → you load your data onto it locally → you ship it back to AWS → AWS exports the data (e.g., into an S3 bucket).

**Edge computing use case**
- For processing data as it's created **at the edge** — e.g., on a truck on the road, a ship at sea, or a mining station — locations with no or very limited internet access/compute power.
- Uses the **Compute Optimized** device, which supports running **EC2 instances** or **Lambda functions** directly on the device.
- Enables pre-processing data, running machine learning, or transcoding media at the edge, before (optionally) sending results back to AWS.

- Walkthrough of the **ordering process** for a Snow Family device (not actually completed/ordered in the demo):

### Lecture: AWS Snowball Edge - Pricing

- **Data transfer**:
  - Transferring data **out of AWS** onto your Snowball Edge (then receiving the physical device) incurs a cost.
  - Transferring data **from** your Snowball Edge **into Amazon S3** is **free — $0 per GB**.
- **Device usage pricing** — two models:
  - **On-demand**: a one-time service fee per job, which includes a set number of days of usage (e.g., **10 days** for the 80 TB Storage Optimized device, or **15 days** for the 210 TB device). Shipping time does **not** count against this usage window (shipping is free both ways); usage-day charges apply only after the included days are exceeded.
  - **Committed upfront**: pay in advance for monthly, 1-year, or 3-year usage (for edge computing use cases) — offers up to **62% discounted pricing** for committing long-term.
- > **Exam takeaway**: you pay for essentially everything **except** transferring data into Amazon S3, which is **$0 per GB**.

### Lecture: Storage Gateway Overview

- Amazon S3 can be used in a **hybrid cloud** setup, bridging on-premises infrastructure with AWS — useful for gradual migrations, security/compliance requirements, or a deliberate strategy of splitting infrastructure between on-premises and cloud.
- S3 is a **proprietary storage technology** — unlike EFS (which uses the standard NFS protocol and can be mounted directly on-premises), S3 cannot be accessed on-premises the same way.
- **Storage Gateway** is the AWS service used to expose S3 data on-premises, bridging on-premises data and AWS cloud data.

**AWS storage options recap**
| Storage type | AWS service(s) |
|---|---|
| Block storage | EBS, EC2 Instance Store |
| File storage (NFS) | Amazon EFS |
| Object storage | Amazon S3, Glacier |

- Storage Gateway lets on-premises systems seamlessly use the cloud to **extend their storage capability** — useful for disaster recovery, backup and restore, or tiered storage.
- Types of Storage Gateway: **File Gateway**, **Volume Gateway**, and **Tape Gateway** — for the Cloud Practitioner exam, you don't need to know the details of each type, just that **Storage Gateway bridges on-premises systems into the AWS Cloud**.
- Behind the scenes, Storage Gateway uses **Amazon EBS, Amazon S3, and Glacier**.
- (Note: deeper Storage Gateway knowledge is required for the AWS Certified Solutions Architect Associate exam, but not for the Cloud Practitioner exam.)

### Lecture: S3 Summary

- **Buckets vs. Objects**: buckets have a globally unique (or account-regional-namespace-unique) name and are tied to a specific region; objects live within buckets.
- **S3 Security**: IAM policies (attached to users/roles), S3 Bucket Policies (e.g., to grant public access), and S3 encryption to protect files.
- **Websites**: S3 buckets can host static websites — the bucket must be public, and static hosting must be enabled.
- **Versioning**: keeps multiple versions of a file to protect against accidental deletes and allow rollback to previous versions.
- **Replication**: two kinds — Same-Region Replication (SRR) and Cross-Region Replication (CRR) — both require versioning to be enabled first.
- **Storage Classes**: Standard, Infrequent Access, One Zone-Infrequent Access, Intelligent-Tiering, and three Glacier classes for archival purposes.
- **Snowball**: a physical device service for importing/exporting data to/from Amazon S3, and for doing edge computing.
- **Storage Gateway**: a hybrid solution to extend on-premises storage to Amazon S3.

## Section: Amazon S3 — Key Takeaways

**Most important concepts**
- S3 stores **objects** (identified by a **key**) inside **buckets** (region-scoped, globally/account-regionally unique names) — an essentially infinitely scalable object storage service.
- Security in S3 combines **IAM policies** (user-based), **Bucket Policies** (resource-based, JSON, the most common method), **ACLs** (less common, can be disabled), and **Block Public Access** (an overriding safety net against accidental public exposure).
- **Versioning** protects against accidental deletion/overwrites and enables rollback; it's also a **prerequisite for Replication** (SRR/CRR).
- **Storage Classes** trade off cost, availability, and retrieval time/speed — from S3 Standard (frequent access) down through Infrequent Access, One Zone-IA, the Glacier tiers (archival), and the special-purpose S3 Express One Zone and Intelligent-Tiering classes.
- **Encryption** is server-side by default, with client-side as an alternative.
- **Snowball** (physical device migration/edge computing) and **Storage Gateway** (hybrid on-premises/cloud bridge) extend S3's reach beyond pure cloud-native use cases.
- The **Shared Responsibility Model** for S3: AWS guarantees the underlying durability/availability/infrastructure; the customer is responsible for configuring versioning, bucket policies, encryption, logging/monitoring, and choosing cost-optimal storage classes.

**How the concepts relate**
- A bucket's **Bucket Policy** and **Block Public Access** setting work together: Block Public Access acts as an override that keeps a bucket private even if the policy would otherwise make it public — this is why making a bucket/website public requires *both* disabling Block Public Access *and* attaching a permissive Bucket Policy (as seen in the Website and Bucket Policy hands-on lectures).
- **Versioning** underlies both safe file updates (rollback, delete markers) and **Replication** — you cannot replicate a bucket without first enabling versioning on both source and destination.
- **Storage Classes** and **Lifecycle Rules** work together: lifecycle rules automate the movement of objects between storage classes over time (e.g., Standard → Standard-IA → Intelligent-Tiering → Glacier Flexible Retrieval), balancing cost against access patterns automatically.
- **Snowball** and **Storage Gateway** both address moving data between "outside AWS" and S3, but for different needs: Snowball for **bulk, one-time physical data transfer** (or edge compute) when network transfer is too slow; Storage Gateway for **ongoing, seamless hybrid access** to cloud storage from on-premises systems.

**Key terminology to remember**
- Bucket, Object, Key, Prefix, Value, Metadata, Tags, Version ID
- Multi-part upload (for objects > 5 GB), max object size (5 TB)

**Key distinctions/comparisons**
- **IAM Policy vs. Bucket Policy**: attached to a user/role vs. attached directly to the bucket (resource-based); Bucket Policy is needed for public access and cross-account access.
- **Public URL vs. Pre-signed URL**: a plain object URL (works only if public) vs. a signed URL containing embedded credentials (works for the specific authenticated user, regardless of public access settings).
- **Versioned delete vs. permanent delete**: adding a delete marker (recoverable) vs. deleting a specific version ID (destructive, irreversible).
- **SRR vs. CRR**: same region vs. different regions — both require versioning; use cases differ (log aggregation/test-prod sync vs. compliance/latency/cross-account).
- **S3 Standard vs. Standard-IA vs. One Zone-IA**: decreasing availability and multi-AZ redundancy in exchange for lower storage cost, at the expense of retrieval cost or durability risk.
- **Glacier Instant Retrieval vs. Flexible Retrieval vs. Deep Archive**: increasing retrieval time (milliseconds → hours) in exchange for decreasing cost and increasing minimum storage duration (90 → 90 → 180 days).
- **S3 Express One Zone vs. standard S3 classes**: single-AZ, ultra-high performance, lower availability vs. multi-AZ, standard performance, higher availability.
- **Server-side vs. client-side encryption**: S3 encrypts on arrival (default) vs. the user encrypts before upload.
- **Snowball Edge Storage Optimized vs. Compute Optimized**: large storage capacity for data migration vs. smaller storage but compute capability (EC2/Lambda) for edge processing.
- **Snowball vs. Storage Gateway**: one-time/periodic physical bulk transfer & edge compute vs. ongoing hybrid cloud storage access.
- **Customer responsibility vs. AWS responsibility** under the S3 Shared Responsibility Model.
